## Common Pitfalls

### Pitfall 1: `game_id`/`play_id` dtype mismatch breaks the join silently

**What goes wrong:** `video_sync.csv` gets hand-edited with `play_id` values that a naive CSV reader infers as strings (e.g., a stray leading zero like `"03"`), while `plays.parquet` has `play_id: Int32`. A `polars.join` on mismatched dtypes either raises (good — but only if the loader path is explicit) or, with permissive reading, produces zero matches with no error.
**Why it happens:** CSVs have no native types; polars/pandas infer dtypes column-by-column from observed values, and a small hand-maintained file with only a few rows is especially prone to ambiguous inference (e.g., a column that's all-blank in early rows).
**How to avoid:** Document explicit expected dtypes in `docs/sync-convention.md` (mirroring `_TEAM_MAPPING_SCHEMA`-style dicts in `src/flag_football_ep/reference.py` even without writing a loader) and add a pytest that reads the CSV with an explicit `schema_overrides={"game_id": pl.Utf8, "play_id": pl.Int32}` and asserts a non-empty join against a small fixture slice of `plays.parquet` columns.
**Warning signs:** A join that always returns 0 rows with no exception; `git diff` on `video_sync.csv` shows a `play_id` value with a leading zero or extra whitespace.

### Pitfall 2: Full-file hashing on multi-gigabyte 4K clips silently stalls or is skipped

**What goes wrong:** A 20–25 minute 4K drone clip (battery-cycle length per C-11) can be several GB; if the doc doesn't set an expectation for how long `shasum -a 256` takes, the user may assume it hung and kill it, or skip hashing entirely, defeating D-08's re-location/verification purpose.
**Why it happens:** SHA-256 over multi-GB files is CPU-bound and, depending on disk (external SD card reader vs. internal SSD), can take from seconds to a few minutes per file — not instant, but also not prohibitive for the "2–3 sample clips per domain" (D-07) scope of this phase.
**How to avoid:** Document the command and a realistic time expectation in `docs/material-inventory.md` ("wenige Minuten pro Clip, abhängig vom Speichermedium"); scope this phase's inventory to the sample clips only (2–3 per domain, per success criterion 1), not a full archive — a full-archive hash pass is future work, not this phase's deliverable.
**Warning signs:** An inventory CSV with a `content_hash` column left empty for rows that do have a `local_path` — the doc should flag this as incomplete, not silently acceptable.

### Pitfall 3: `.gitignore` pattern for the video directory doesn't actually block re-inclusion

**What goes wrong:** Following `data/raw/hudl/*` too literally (ignore contents, not directory) for a directory that also needs a `.gitkeep` can silently leave large binaries trackable if a plan adds files before the `.gitignore` entry, or if the pattern is anchored incorrectly (same class of bug the existing `.gitignore` comment for `/reports/` explicitly calls out — an unanchored pattern can accidentally match an unrelated same-named directory under `src/`).
**Why it happens:** Git's `.gitignore` semantics are non-obvious around directory-vs-contents patterns and anchoring (`/foo/` vs `foo/`).
**How to avoid:** Reuse the exact `data/raw/hudl/*` + `!data/raw/hudl/.gitkeep` pattern verbatim for the new video directory (e.g., `data/video/*` + `!data/video/.gitkeep`), and add a `git check-ignore` test (see Validation Architecture) rather than eyeballing the pattern.
**Warning signs:** `git status` shows an untracked-but-not-ignored video file after adding a test clip; `git check-ignore -v data/video/sample.mp4` returns nothing.

### Pitfall 4: Numeric capture tiers presented as settled fact rather than reasoned targets

**What goes wrong:** The Ideal/Brauchbar/Unbrauchbar boundaries (exact altitude cutoffs, minimum fps, etc.) get written into `docs/capture-protocol.md` with unwarranted precision, making the Wunschzettel read as a demand (violates D-03's tone) or as more scientifically grounded than the evidence supports.
**Why it happens:** `docs/research-notes.md` gives strong qualitative evidence (oblique > top-down, drone is its own small-object regime, SAHI helps) but no flag-football-specific numeric thresholds — those have to be extrapolated from the locked D-03 range (~30–60 m) and general small-object-detection heuristics, not read off a benchmark table.
**How to avoid:** Tag every numeric boundary `[ASSUMED]` in `RESEARCH.md`'s Assumptions Log (already done below) and carry that framing into the doc's tone — "grobe Richtwerte, kein Messprotokoll" — consistent with D-03's "so wäre es ideal, falls machbar" register.
**Warning signs:** A tier boundary stated as if benchmarked (e.g., "exactly 45 m") without a reasoning footnote.

### Explicit-dtype CSV read + join smoke test pattern (mirrors `src/flag_football_ep/reference.py`)
```python
# Source: pattern read directly from src/flag_football_ep/reference.py's
# _TEAM_MAPPING_SCHEMA-style dicts and tests/test_reference.py's loader tests
# (both read 2026-08-22). This phase does NOT add this loader to src/ --
# shown here only as the dtype contract a validation test should assert against.
import polars as pl

SYNC_SCHEMA = {
    "game_id": pl.Utf8,
    "play_id": pl.Int32,
    "video_file": pl.Utf8,
    "snap_frame": pl.Int64,
    "snap_seconds": pl.Float64,
    "notes": pl.Utf8,
}

def test_video_sync_joins_against_plays_fixture(tmp_path):
    sync = pl.read_csv("data/reference/video_sync.csv", schema_overrides=SYNC_SCHEMA)
    # plays fixture: minimal (game_id, play_id, dn, dist, result) slice, not the full parquet
    plays = pl.DataFrame({
        "game_id": ["2026-06-14_GER-vs-AUT_EM-QUALI"],
        "play_id": [3],
    }).cast({"game_id": pl.Utf8, "play_id": pl.Int32})
    joined = sync.join(plays, on=["game_id", "play_id"], how="inner")
```

## Open Questions

1. **Should the second-domain (elevated tripod/side camera/Veo-class) Wunschzettel block share the exact same tier boundaries as the drone block, or does it need its own numeric targets?**
   - What we know: D-05 says "same three tiers," and `docs/research-notes.md` treats side/elevated views as generally *more* detection-friendly than top-down drone (TeamTrack: side mAP 52.7 vs top-view mAP 23.5 in the cited source's benchmark), so the second domain likely has looser altitude/angle constraints but similar resolution/fps/exposure asks.
   - What's unclear: Exact altitude/distance range for "elevated tripod" is not locked anywhere in PROJECT.md or CONTEXT.md — only "drone banned at official games, second domain needed" (C-01) is fixed.
   - Recommendation: Planner should derive second-domain tiers primarily from "no drone-specific small-object penalty applies" (so resolution/fps/exposure/coverage asks stay parallel to the drone tier, but altitude/angle wording changes to reflect a stationary elevated position, e.g. sideline scaffolding/stand height) and flag this as [ASSUMED] in the doc itself, inviting analyst correction via the DEFERRED-ANALYST block.

2. **Does the material-inventory CSV need a row for footage the analyst holds but the user has never seen (i.e., known-to-exist-but-unregistered rows), or only for footage the user has physically secured?**
   - What we know: Success criterion 1 requires "which games/trainings exist per camera domain" (broader than just the secured samples) plus "2–3 sample clips secured per domain" (narrower, concrete).
   - What's unclear: Whether the CSV should have placeholder/DEFERRED-ANALYST rows for footage inventory that only the analyst can supply, or whether that inventory-of-existence lives purely in `docs/material-inventory.md` prose and the CSV is scoped strictly to secured samples.
   - Recommendation: CSV scoped to secured samples only (rows the user can actually hash/verify); broader "what exists" inventory goes in the doc's prose with an explicit DEFERRED-ANALYST block for anything not yet secured — keeps the CSV's row-level guarantee (every row has a verifiable hash) intact rather than mixing verified and unverified rows.
