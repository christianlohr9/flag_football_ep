# Phase 2.0 — Validation Strategy

> Per-phase validation contract for feedback sampling during execution.

---

## Test Infrastructure

| Property | Value |
|----------|-------|
| **Framework** | pytest ≥8 (`pyproject.toml` `dev = ["pytest>=8"]`) |
| **Config file** | `pyproject.toml` `[tool.pytest.ini_options]` (`testpaths = ["tests"]`) |
| **Quick run command** | `uv run pytest -q -k capture` |
| **Full suite command** | `uv run pytest -q` |
| **Estimated runtime** | quick: < 1 s (measured 0.2 s for a comparable single-file run, 2026-08-22) · full suite: ~510 s / 8.5 min, 2468 tests green (measured 2026-08-22) |

`-k capture` selects every test in `tests/test_capture_artifacts.py`, `tests/test_capture_reference_docs.py` and `tests/test_capture_protocol_docs.py`, and stays a valid command at every point of the phase (it simply matches fewer tests before the later files exist).

**Verbatim commands:** the authoritative wording of every gate is the `<verify><automated>` block of the owning task in the plan file. The map below names the command and, for the multi-line inline gates, its unique success token (`INVENTORY_DOC_OK`, `SYNC_DOC_OK`, `PROTOCOL_DOC_OK`, `LEGAL_DOC_OK`, `CSV_HEADERS_OK`, `GITIGNORE_OK`) so a run can be identified unambiguously without duplicating the source here.

---

## Sampling Rate

- **After every task commit:** Run the task's own `<verify><automated>` gate (sub-second for all four doc tasks and both Plan 01 artifact tasks), then `uv run pytest -q -k capture`
- **After every plan wave:** Run `uv run pytest -q` (full suite; ~8.5 min, run once per wave, not per task)
- **Before `/gsd:verify-work`:** Full suite must be green
- **Max feedback latency:** < 1 s per task gate (the 8.5 min full-suite run is a per-wave gate, never the per-task feedback loop)

## Wave 0 Requirements

Keine Wave-0-Lücken. Jede Phase-Testdatei wird von genau dem Task erzeugt, dessen Gate sie ausführt; kein Task-Gate referenziert eine Datei, die erst ein späterer Task anlegt:

- `tests/test_capture_artifacts.py` — erzeugt und ausgeführt von 02.0-01-03 (10 Gates für beide Referenz-CSVs, `.gitignore`, Git-Hygiene, Dependency-Grenze)
- `tests/test_capture_reference_docs.py` — erzeugt und ausgeführt von 02.0-02-03 (7 Gates für Materialinventur und Sync-Konvention)
- `tests/test_capture_protocol_docs.py` — erzeugt und ausgeführt von 02.0-03-03 (10 Gates für Wunschzettel und Rechtsnotiz)
- Fixtures: keine neuen nötig — `plays.parquet`-förmige Frames werden inline als `pl.DataFrame(...).cast(...)` gebaut (`data/processed/*` ist gitignored und darf von Tests nie gelesen werden)
- Framework-Install: keiner — pytest ≥8 ist bereits in `pyproject.toml` `dev`

Die vier dokumenterzeugenden Tasks (02.0-02-01, -02, 02.0-03-01, -02) verifizieren sich über self-contained `python3 -c`-Gates gegen das jeweils geschriebene Dokument und die bereits committeten CSV-Header. Sie hängen von keiner erst später erzeugten Datei ab; die pytest-Datei desselben Plans zieht dieselben Prüfungen anschließend als dauerhafte Regressionsschicht nach und ergänzt die dokumentübergreifenden Drift-Gates.
