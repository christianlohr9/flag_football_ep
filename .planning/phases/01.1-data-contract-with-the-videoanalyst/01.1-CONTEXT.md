<domain>
## Phase Boundary

Define the Hudl yearly export as a written data contract so every game parses through the pipeline identically, and settle the path to time data. Deliverables are agreements and documents (contract spec + machine-readable schema + charting-protocol decisions), not pipeline code — derivation and validation code lands in Phase 1.2.

**Critical framing correction from discussion:** The user has Hudl access and exports all data themselves. The contract is NOT a negotiation about export mechanics with the Videoanalyst — the export format is a given baseline. The analyst conversation is only about *charting* (what gets tagged per play and with what vocabulary).

**The real export format (baseline, "damit muss ich einfach arbeiten"):**
`PLAY #, ODK, DN, DIST, HASH, YARD LN, PLAY TYPE, RESULT, GN/LS, OFF FORM, OFF PLAY, OFF STR, PLAY DIR, GAP, PASS ZONE, DEF FRONT, COVERAGE, BLITZ, QTR`

Note this differs from `data_raw.csv` (which lacks HASH, PLAY TYPE, PLAY DIR, GAP, PASS ZONE, DEF FRONT, COVERAGE, BLITZ, QTR and instead carries manually appended columns). `QTR` exists but is essentially never filled.

<decisions>
## Implementation Decisions

### Manual fields: chart vs derive
- **Ownership split:** Pipeline derives the maximum; nobody charts extra per-play ID columns. Mapping: `play_id` ← `PLAY #`, `yardline_50` ← `YARD LN`, `drive_id` ← ODK possession flips (+ TD/turnover results), `half` ← manually maintained halftime boundary (see Time data), `game_id` ← filename convention. Derivation logic is Phase 1.2 code; Phase 1.1 documents each rule in the contract.
- **Game identification:** One export file per game, filename naming convention (date + teams + competition) parsed into `game_id` and metadata. Matches the Phase 1.2 ingest-CLI "folder of exports" design.
- **OPEN — resolve in analyst conversation:** `posteam` derivation for exchanged opponent-vs-opponent film. ODK is charted from a perspective; whose perspective exchanged film uses is unknown. Proposal to bring: filename carries both teams and the contract defines whose perspective ODK is charted from. Do NOT lock this in planning — record it as an explicit conversation item whose outcome goes into the contract.

### Contract artifact & export scope
- **Form:** Two artifacts: a human-readable markdown spec (e.g., `docs/data-contract.md`) plus a machine-readable schema file (column names, dtypes, RESULT vocabulary — YAML/JSON) that the Phase 1.2 ingest validator consumes directly, so contract and validation cannot drift.
- **Language:** Markdown spec in German (working language with the analyst, matches `docs/plan-*.md`); schema file and column names stay English/technical.
- **Scope:** Forward-only. The existing 47 games in `data_raw.csv` are grandfathered — no re-export. Consequence Phase 1.2 must plan for: two ingest paths (legacy `data_raw.csv` format + new contract format).
- **Preset ownership:** The user owns and maintains the Hudl export preset themselves (they have Hudl access and export everything). No analyst-side export sync risk.

### Time data (REQ-S1-02)
- **Status: not available.** The export contains no time information; `QTR` is essentially never filled. The contract records this explicitly (satisfies success criterion 3: "unavailability explicitly recorded").
- **Manual fallback:** The user manually maintains only the halftime boundary per game (which `PLAY #` starts half 2). `half` is derived from it. Format of this per-game record is Claude's discretion (see below), but it must be a defined input the 1.2 ingest consumes.
- **Consequence:** `half_seconds_remaining` stays synthetic (uniform per half); Phase 1.4 WP charts must be explicitly flagged as synthetic-time. This was already anticipated in STATE.md blockers — now confirmed as the actual path.

### Defense fields (REQ-S1-03)
- **Existing columns, partially filled:** `DEF FRONT`, `COVERAGE`, `BLITZ` already exist in the export and are partially filled. The contract documents the actually-used vocabulary and normalizes it; the analyst is asked only about gaps/consistency going forward.
- **COVERAGE vocabulary:** Sight the real distinct values from existing exports FIRST, derive the canonical vocabulary from that, then fix it in the contract. No premature schema (no Cover 0/1/2/3 vs man/zone decision before seeing the data).
- **Flag-pull causer:** Explicitly skipped — recorded as a deliberate skip in the charting protocol (satisfies success criterion 4). Can be revisited in a later phase.

### Claude's Discretion
- Exact filename convention format (order/separator of date, teams, competition tag) — propose one in the contract.
- File format and location of the per-game halftime-boundary record (e.g., a small CSV/YAML under `data/`).
- Schema file format choice (YAML vs JSON) and exact structure, as long as the 1.2 validator can consume it.
- How to document derivation rules (per-field table in the markdown spec is the expectation).

</decisions>
