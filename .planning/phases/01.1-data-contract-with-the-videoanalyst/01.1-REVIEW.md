# Phase 01.1: Code Review Report

**Reviewed:** 2026-08-17T06:15:00Z

## Summary

Reviewed the data-contract artifacts: German markdown spec (`docs/data-contract.md`), machine-readable counterpart (`docs/data-contract.schema.json`), the half-boundaries record CSV, and the PII gitignore rule. Verification performed beyond reading: JSON parses (19 columns, matching the spec's column list in name and order); `data/half_boundaries.csv` is comma-delimited UTF-8 without BOM with LF terminator, exactly as the spec mandates for hand-maintained repo CSVs; `data/samples/` exists on disk with three sample exports, is untracked, and `git check-ignore` confirms the ignore rule works; the source-code references in the spec check out against `Python/helper_add_hudl_mutations.py` (`prepare_wp_data` at line 384, `.otherwise(pl.lit("pass"))` at line 53, synthetic-time logic at lines 399-400); `data_raw.csv` confirms the claimed semicolon+BOM dialect. All fill-rate percentages and the 13-token count were recomputed and are arithmetically correct except one range claim (WR-01). No player names appear in any of the four reviewed artifacts. No leftover PENDING markers; the DEFERRED-ANALYST block and `status: provisional` are intentional design per phase context and were not flagged.

The findings below are internal contradictions and underspecifications that would mislead the Phase 1.2 ingest-validator, plus PII-policy gaps around the contract's own forward-looking rules. The spec's headline claim — "Spec und Validierung können nicht auseinanderlaufen" (data-contract.md:3) — is already false in two places (WR-05, WR-06).

## Warnings

### WR-01: Own-game fill-rate claim "73–95 %" contradicted by the document's own table

**File:** `docs/data-contract.md:94` (claim) vs `docs/data-contract.md:88` (table)
**Issue:** Befund 1 states own games are filled at "73–95 %", but the table two lines up shows `BLITZ` for GER vs. SLO at 36/81 = **44 %**. The stated range silently excludes a data point from the same table. Anyone using this range as an expectation baseline (e.g., a fill-rate sanity check in the 1.2 validator) would flag valid own-game files as anomalous or, worse, hardcode a wrong threshold.
**Fix:** Change line 94 to reflect the actual own-game range, e.g. "44–95 % (BLITZ in GER vs. SLO ist mit 44 % der Ausreißer) vs. 9–17 %", or scope the claim to `COVERAGE`/`DEF FRONT` explicitly.

### WR-02: `drive_id` rule depends on "Fumble falls Turnover" but the contract provides no way to decide it

**File:** `docs/data-contract.md:59`; `docs/data-contract.schema.json:168-172`
**Issue:** The drive-close rule includes "`Fumble` falls Turnover" ("Fumble-if-turnover" in the schema), but the RESULT vocabulary has no token distinguishing a lost fumble from a recovered one, and no other column carries recovery information. The row is marked "Regel dokumentiert, Implementierung 1.2" — i.e., presented as implementable — yet Phase 1.2 cannot evaluate the condition from contract data. The deferred Fumble ratification is intentional, but the derivation rule as written is not machine-decidable, which is a different defect: the rule pretends to a precision the data cannot support.
**Fix:** Make the interim behavior explicit in both files, e.g.: "Bis zur Ratifizierung gilt: `Fumble` schließt einen Drive **nur**, wenn zusätzlich der `ODK`-Flip ihn schließt (d. h. Fumble allein ist kein Drive-Ende)." Alternatively add a `Fumble Lost` token. Either way, Phase 1.2 needs a deterministic rule, not a conditional it cannot test.

### WR-03: RESULT grammar underspecified — modifier cardinality, order, and the dual-listed `Penalty` token

**File:** `docs/data-contract.md:40-43`; `docs/data-contract.schema.json:75-79`
**Issue:** The grammar says "ein Basis-Token plus optionale Modifier" but never specifies: (a) how many modifiers are allowed, (b) whether the base token must come first, (c) whether modifiers may repeat, (d) whether mutually exclusive combinations exist (`TD` + `Def TD`?). Because `Penalty` appears in both the base and modifier lists, `Penalty, Penalty` parses as valid under exact-token matching, and `Good, TD` or `KNEEL, TD` are also formally valid. Two independent validator implementations would legitimately disagree on what to accept.
**Fix:** Add to both files: base token mandatory and in first position; modifiers ≥ 0, each at most once; `TD` and `Def TD` mutually exclusive; `Penalty` may appear as base or as modifier but not twice. If certain base+modifier combinations are known-invalid, say so or explicitly state that semantic combination checks are out of scope for the validator.

### WR-04: Datenschutz-Hinweis lists PII columns that are not in the contract export and omits the one that is

**File:** `docs/data-contract.md:163` vs `docs/data-contract.md:17` and `docs/data-contract.md:115`
**Issue:** The privacy section states the export contains name columns `RECEIVED BY`, `Thrown By`, `QB` — none of which appear in the 19-column contract baseline (they exist only in the legacy `data_raw.csv` and the richer sample presets). Meanwhile `BLITZ`, which §7 explicitly declares a PII column ("gilt `BLITZ` als PII-Spalte") and which IS one of the 19 contract columns, is missing from the privacy section. Anyone applying DSGVO handling based on §Datenschutz alone would treat contract-format exports as PII-free.
**Fix:** Rewrite line 163 to distinguish: (1) contract-format exports contain PII via `BLITZ` (person names, per §7); (2) legacy/rich-preset exports additionally contain `RECEIVED BY`, `Thrown By`, `QB`.

### WR-05: Spec/schema normalization drift for `DEF FRONT` — hyphen-whitespace rule missing in the schema

**File:** `docs/data-contract.md:125` vs `docs/data-contract.schema.json:129`
**Issue:** The markdown's general rule for the defense columns is "Großschreibung, Leerzeichen um Bindestriche in numerischen Mustern entfernen" — which applies to the `DEF FRONT` numeric tuples too. The schema's `DEF FRONT` `normalization` field says only `"uppercase (...)"`. A validator consuming the schema directly (the stated design at md:3) will not normalize `5 - 6-6-5` to `5-6-6-5`, while the spec says it should. This is exactly the spec/validation divergence the contract claims is impossible.
**Fix:** In schema line 129: `"normalization": "uppercase; collapse whitespace around hyphens in numeric patterns ('Line 5 --> 7' -> 'LINE 5 --> 7', '5 - 6-6-5' -> '5-6-6-5')"`.

### WR-06: `values`/`values_open` enforcement semantics undefined; BLITZ placeholder breaks uniform machine interpretation of `values`

**File:** `docs/data-contract.schema.json:127-128, 136-137, 145-147`
**Issue:** Two related problems for a validator that consumes this file directly. (1) All three defense columns carry `values` plus `values_open: true`, but nothing defines what the validator should do with a non-listed value: accept silently, warn, or normalize-then-check? For `DEF FRONT` the note implies only tuples matching `^\d+(-\d+){3}$` are open while the `LINE n` sub-vocabulary is fixed — but that constraint lives in prose, not in a machine field. (2) `BLITZ.values` is `["<BLITZERIN-NAME>"]`, a semantic placeholder distinguishable from a literal enum value only by reading the English `note`. A generic consumer of `values` will treat `<BLITZERIN-NAME>` as an accepted literal and every real name as a vocabulary miss.
**Fix:** Add an explicit contract-wide key, e.g. `"values_semantics": "warn-on-unlisted"` (or per-column `"on_unlisted": "accept" | "warn"`), move the open-pattern into a machine field (`"open_pattern": "^\\d+(-\\d+){3}$"` on `DEF FRONT`), and replace BLITZ's `values` with `"free_text": true` / `"pii": true` instead of a placeholder inside an enum array.

### WR-07: PII protection incomplete: no ignore rule for forward contract-format exports; contract endorses committing a player-name CSV

**File:** `.gitignore:1-2`; `docs/data-contract.md:21, 34, 115`
**Issue:** The gitignore fulfills T-1.1-03 for `data/samples/` (verified: rule active, samples untracked). But the contract itself creates two uncovered PII paths: (1) Forward exports per the filename convention (md:25) will contain person names in `BLITZ` (md:115) and land in an "Ingest-Ordner" (md:34) whose location is undefined and not ignored — nothing prevents `git add data/2026-06-14_GER-vs-AUT_EM-QUALI.csv`. (2) md:21 designates `team_roster.csv` as a hand-maintained **repo** CSV; that file is git-tracked and contains `player_name` for every player — directly at odds with the gitignore's own rationale "player names (PII) — never commit". (Context: `data_raw.csv` with `RECEIVED BY`/`Thrown By`/`QB` columns is also already tracked; pre-existing legacy, but the contract text should not compound it.)
**Fix:** Define the ingest folder in the contract (e.g. `data/exports/`) and add it to `.gitignore` now, in this phase, before any export exists. Reconcile the `team_roster.csv` mention: either scope T-1.1-03 explicitly ("keine Hudl-Export-PII; Roster-Stammdaten sind ausgenommen weil …") or move roster handling to the Strang-2 DSGVO scope referenced at md:163.

### WR-08: `YARD LN` range `[-50, 50]` admits values that contradict the stated sign semantics; goal-line encoding unspecified forward

**File:** `docs/data-contract.schema.json:62-64`; `docs/data-contract.md:58`
**Issue:** With `yardline_50` defined as 0–50 yards from own goal line (50-yard field, midfield 25), the sign convention "negativ = eigene Hälfte" is only self-consistent for magnitudes ≤ 25: e.g. `-40` maps via `-x` to yardline_50 = 40 — opponent territory, contradicting the "own half" semantics — yet passes the schema range check silently. Symmetrically `+40` (40 yards to opponent goal) maps to 10, own territory. The extremes are degenerate: both `0` and `-50` map to 50 while `+50` maps to 0. The legacy data needed 2 manual goal-line fixes (md:58), and the contract does not say what the export emits at goal lines forward, so the 1.2 validator has no correct acceptance rule at exactly the boundary that already broke once.
**Fix:** Specify the forward goal-line encoding explicitly (which of `0`/`±50` the export produces, and what the validator must do with the others: reject vs auto-normalize), and tighten the range or add a constraint note if magnitudes > 25 for one sign are impossible in practice.

## Info

### IN-01: `values_open: true` on COVERAGE/BLITZ not mirrored in the markdown spec

**File:** `docs/data-contract.schema.json:137, 146` vs `docs/data-contract.md:107`
**Issue:** The markdown declares only the `DEF FRONT` tuple enumeration open ("kein geschlossenes Enum"); it is silent on whether the COVERAGE vocabulary is open or closed, while the schema marks it open.
**Fix:** Add one sentence to §7 stating COVERAGE is likewise an open enumeration (or make it closed in the schema if that was the intent).

### IN-02: Three inconsistent dtype vocabularies in one machine-consumed file

**File:** `docs/data-contract.schema.json:29, 160, 181`
**Issue:** Columns use `"int"`/`"str"`, derived fields use polars-style `"Int32"`, and `game_id` has prose in a dtype field: `"Int32-or-str per Phase 1.2 choice"`. A generic dtype-mapping consumer must special-case all three styles.
**Fix:** Pick one vocabulary; move the game_id open decision out of `dtype` into a `note`, with `dtype: "tbd"` or similar sentinel.

### IN-03: §-number cross-references against unnumbered headings

**File:** `docs/data-contract.md:5, 32, 45, 62, 100, 146, 148`
**Issue:** References like "§8", "§4", "§7" resolve only by counting H2 headings (they do currently resolve correctly — verified). Inserting any section breaks every reference silently.
**Fix:** Number the H2 headings explicitly (`## 8. Charting-Protokoll …`) or reference by name.

### IN-04: `filename_pattern` is a prose template, not machine-checkable

**File:** `docs/data-contract.schema.json:20`
**Issue:** `"YYYY-MM-DD_{TEAM1}-vs-{TEAM2}_{COMP}.csv"` mixes two placeholder styles and cannot be applied by a validator without hand-translation — a drift point for the file that is supposed to be consumed directly.
**Fix:** Add `"filename_regex": "^\\d{4}-\\d{2}-\\d{2}_[A-Z]{3}-vs-[A-Z]{3}_[A-Z0-9-]+\\.csv$"` alongside the human-readable pattern.

### IN-05: Synthetic-time formula summary omits the first-play-zero rule from the cited source

**File:** `docs/data-contract.md:68`
**Issue:** The C-08 summary ("`play_time = 1200 / max(play_id_half)` … kumulativ abgezogen von 1200") omits that the actual code (`helper_add_hudl_mutations.py:399`, correctly cited) sets `play_time = 0` for the first play of each half, so the first play has exactly 1200 s remaining. A reimplementation from the summary alone would be off by one play-time slice for every play of a half.
**Fix:** Append "(erster Play jeder Halbzeit: `play_time = 0`, d. h. startet bei exakt 1200 s)" to line 68.
