## Summary

This phase produces documents, not code: a German markdown data-contract spec, an English machine-readable schema file, a proposed filename convention, a halftime-boundary record format, and recorded charting-protocol decisions. The single external dependency is one conversation with the Videoanalyst covering only three things: charting vocabulary consistency going forward, gaps in the defense columns, and the ODK-perspective question for exchanged film.

The most valuable research findings come from auditing the 47 legacy games (3,701 plays) in `data_raw.csv` against the parsing code in `Python/helper_add_hudl_mutations.py`. The reality deviates from the C-07 vocabulary in ways the contract must resolve: 846 plays (23%) have an **empty** `RESULT` (silently classified as `"pass"` by the current pipeline), `No Good` (97×) and `Fumble` (9×) occur but are not in C-07, combined results use a `", "` separator (`Complete, TD`, `Sack, Safety`, `Interception, Def TD`), and malformed variants exist (`Complete Penalty` without comma, `Penalty (declined)`). The `ODK` column is polluted in several legacy games (team names and formation strings instead of O/D/K), which matters because `drive_id` derivation depends on clean ODK flips. On the positive side: `play_id` is contiguous 1..N in all 47 games, and the `yardline_50` ← `YARD LN` rule (`-x if x < 0 else 50 - x`) reproduces the manual column for 3,656 of 3,658 parseable rows (99.95%).

**Primary recommendation:** Write the contract as two artifacts (`docs/data-contract.md` in German + `docs/data-contract.schema.json`), fix the RESULT grammar as *base token + optional modifier tokens joined by `", "`* with `No Good` and `Fumble` added to the canonical token list, mandate non-empty `RESULT` and clean `ODK ∈ {O, D, K}` forward-only, and gate the COVERAGE/DEF FRONT/BLITZ vocabulary section on sighting a real sample export (checkpoint task — that data is not in the repo).

## Common Pitfalls

### Pitfall 1: Empty RESULT is a silent feature-corruptor — and it is common
**What goes wrong:** 846 of 3,701 legacy plays (23%) have an empty `RESULT`. The current parser's `.otherwise(pl.lit("pass"))` classifies every one of them as a pass play. They occur on normal downs for both O and D plays (355 O, 330 D), not just PATs. `[VERIFIED: data_raw.csv audit + helper_add_hudl_mutations.py line 53]`
**Why it happens:** Charting effort varies by game; nothing enforces the field.
**How to avoid:** The contract must declare `RESULT` mandatory (non-empty) for every play going forward, and the charting-protocol part of the analyst conversation must cover it. Document the legacy 23% as a known grandfathered defect.
**Warning signs:** Pass-play share unexpectedly high in a newly ingested game.

### Pitfall 2: Legacy ODK is polluted — drive_id derivation depends on clean ODK
**What goes wrong:** Legacy `ODK` contains `O` (1,356) and `D` (1,276) but also team names (`Germany`, `Spain`, …), formation strings (`Slot Right`, `Pile Left`, `BUNCH LEFT`), 259 empties, and even a stray embedded header row (`OFF FORM`). The locked `drive_id` rule (ODK possession flips) breaks on such data. `[VERIFIED: data_raw.csv audit]`
**Why it happens:** Some legacy games were charted with shifted/repurposed columns.
**How to avoid:** Contract locks `ODK ∈ {O, D, K}` and required, forward-only. Note explicitly in the spec that legacy games take the grandfathered ingest path in 1.2 (which reads the manually maintained `drive_id` column instead of deriving).
**Warning signs:** A new export with formation names in ODK means the preset/charting drifted.

### Pitfall 3: The C-07 vocabulary is incomplete against reality
**What goes wrong:** Observed distinct RESULT values include `No Good` (97), `Fumble` (9), `Penalty (declined)` (1), `Complete Penalty` (1, missing comma), `No Good, Penalty`, `Complete, Penalty` — none expressible in the bare C-07 token list. `KNEEL` conversely occurs **zero** times in 3,701 legacy plays. `[VERIFIED: data_raw.csv audit]`
**Why it happens:** C-07 was distilled from the parser's `.str.contains()` patterns, which ignore tokens they don't look for; `No Good` matters only via the exact-match `== "Good"` PAT check (a `No Good` PAT correctly fails that check, by accident of design).
**How to avoid:** The contract's canonical vocabulary should be C-07 **plus** `No Good` and `Fumble`, with an explicit combination grammar (base token + modifiers, `", "` separator) and exact casing (parser is case-sensitive). Record this as an amendment/clarification of C-07 in the contract. Fumble semantics (possession change? dead ball?) is a genuine charting question for the analyst conversation.
**Warning signs:** Any new distinct RESULT value in an export that is not in the schema token list.

### Pitfall 4: German-Excel CSV dialect is part of the contract, not an afterthought
**What goes wrong:** `data_raw.csv` is semicolon-delimited with a UTF-8 BOM — the German-locale Excel "CSV" dialect. Hudl exports arrive as Excel files; the CSV step happens on the user's machine. If delimiter/encoding are not fixed in the contract, a future export saved with different locale settings parses garbage. `[VERIFIED: data_raw.csv starts with BOM, `;` delimiter]`
**Why it happens:** Excel's CSV output depends on OS locale settings.
**How to avoid:** The schema's `file_format` block fixes `delimiter`, `encoding`, and file `type`. Recommendation: `;` + `utf-8-sig` to match the established local workflow (alternative: have 1.2 ingest the .xlsx directly — note as an option for 1.2, don't decide here).
**Warning signs:** Single-column parse results, mangled umlauts in team names.

### Pitfall 5: Treating the analyst conversation as blocking all other work
**What goes wrong:** The phase stalls waiting for an external person (flagged as a blocker in STATE.md).
**How to avoid:** Only three items truly need the conversation: forward charting vocabulary consistency (incl. Fumble semantics and mandatory RESULT), defense-column gaps/consistency, and the ODK-perspective rule for exchanged film. Everything else (spec skeleton, schema file, filename proposal, half-boundary format, legacy audit section, vocabulary proposal) can be drafted first so the conversation only confirms/fills marked `PENDING` slots.
**Warning signs:** Plan structure that puts the conversation in wave 1.

### Pitfall 6: Defense-column values are not in the repo
**What goes wrong:** The locked "sight real values first" approach for COVERAGE cannot be executed from repo data — no file contains `COVERAGE`, `DEF FRONT`, or `BLITZ` columns. `[VERIFIED: headers of data_raw.csv, insights/df2.csv, games_plays.csv, games_plays_OLD.csv checked]`
**How to avoid:** Plan a human-input/checkpoint task: user exports at least one recent game (ideally several across the season) with the real preset and drops it in the repo (or pastes distinct values). The COVERAGE vocabulary section of the contract stays `PENDING` until then.

pl.when(pl.col('RESULT').str.contains("Rush")).then(pl.lit("run"))
 .when(pl.col('RESULT').str.contains("Penalty")).then(pl.lit("no_play"))
 .when(pl.col('RESULT').str.contains("KNEEL")).then(pl.lit("qb_kneel"))
 .when(pl.col('down') == 0).then(pl.lit("extra_point"))
 .otherwise(pl.lit("pass"))                      # <- empty RESULT lands here

# PAT:     RESULT == "Good"  &  down == 0  &  yardline_50 == 45 (1pt) / 40 (2pt)
