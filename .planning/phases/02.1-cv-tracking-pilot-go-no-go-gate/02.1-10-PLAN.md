  <action>
Implement `train_detector` with three modes selected by its keyword arguments.

**Dataset preparation (private helper).** `rfdetr` expects the Roboflow COCO layout: sibling `train/`
and `valid/` directories, each containing its images plus an `_annotations.coco.json`. Build that
layout from `data/labels/{session}/corrected/instances.json` plus the frame manifest's CLIP-level
split — read the split from the manifest, never re-derive it, so training and every later metric use
the same partition. Call `validate_coco` before preparing and refuse to train on an invalid dataset.
Write the prepared layout under the artifact output dir, not into `data/labels/`.

**Training mode** (`from_artifacts=None`): construct `RFDETRSmall(resolution=<resolved>)` and call its
`train(...)` with `dataset_dir`, `epochs`, `batch_size`, `grad_accum_steps` and `output_dir`, all
resolved as `argument or config.cv.<key>`. Read the installed `rfdetr` version's `train()` signature
before wiring it and record any deviation from these names in the module docstring. `resolution` must
be a multiple of 224 — raise a named exception listing the offending value otherwise. After training,
evaluate on the `valid` split and compute mAP50 and mAP50-95 overall AND per class (`player`,
`referee`); if the trainer does not expose per-class AP, compute it from the validation predictions
with `supervision`'s mean-average-precision metric. Write `metrics.json`, `params.json` (every
resolved setting plus the dataset `content_sha256`, the machine identifier and the torch/CUDA
versions) and the best checkpoint into the output dir.

**Registration** (`register=True`, the default): open `mlflow_store.ensure_experiment(
config.cv.detector_experiment, config)` and a `mlflow.start_run()`, log every entry of `params.json`
as a param and every entry of `metrics.json` as a metric, call
`registry.register_detector_model(checkpoint, registry.detector_model_name(config), config)` inside
the run, and return `DetectorTrainResult(run_id, checkpoint, metrics)`. Do NOT auto-promote — promotion
is a separate, reviewed step, exactly as `ffep promote` is for the EP/WP models.

**Remote-training mode** (`register=False`): run training and write the artifacts, skip every MLflow
call, and return a `DetectorTrainResult` with an empty `run_id`. This is what runs on the Dell box,
which has the GPU but not the primary machine's MLflow store (D-05).

**Registration-only mode** (`from_artifacts=<dir>`): skip training entirely, read `metrics.json` /
`params.json` / the checkpoint from that directory, and perform the registration step above. This is
what runs on the primary machine after the Dell's artifacts are copied over. Raise `WeightsNotFound`
naming the directory and the missing file when any of the three is absent.

tests/test_cv_detect_train.py, offline with a monkeypatched trainer (a fake `RFDETRSmall` whose
`train()` writes a dummy checkpoint and metrics) and a tmp_path MLflow store:
- the prepared dataset layout puts every manifest `train` clip's frames under `train/` and every
  `val` clip's frames under `valid/`, with no clip in both
- an invalid dataset (from `validate_coco`'s failure modes) aborts before any trainer call
- a resolution that is not a multiple of 224 raises the named exception listing the value
- `register=True` creates exactly one MLflow run whose params include the dataset `content_sha256`
  and whose metrics include per-class AP keys, and registers exactly one model version
- `register=True` does NOT set the champion alias
- `register=False` writes the artifacts and makes no MLflow call (assert the tmp store stays empty)
- `from_artifacts` registers without calling the trainer (assert the fake trainer's call count is 0)
- `from_artifacts` pointing at a directory missing the checkpoint raises `WeightsNotFound` naming it

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| remote training machine -> primary machine | a checkpoint file and metrics JSON cross machines and are then executed as a model |
| MLflow artifact store -> process | `mlflow.pyfunc.load_model` deserializes and runs stored model code |
| training dataset -> model provenance | an unrecorded dataset makes the detector untraceable |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-2.1-26 | Tampering | a checkpoint registered under a claimed dataset it was not trained on | mitigate | Task 1 writes the dataset `content_sha256` into `params.json` at training time and logs it as an MLflow param at registration; Task 2's checkpoint text has the operator verify the hash before copying artifacts back |
| T-2.1-15 | Spoofing | loading detector weights from an arbitrary path at inference time | mitigate | Registration is the only path weights enter the store; plan 02.1-11's loader consumes a run id resolved through the champion alias, never a filesystem path |
| T-2.1-03 | Tampering | run id / model name interpolation into MLflow URIs | mitigate | `cv/registry.py` (plan 02.1-06) reuses the Strand-1 validators; `detect.py` calls into it rather than building URIs itself |
| T-2.1-27 | Elevation of privilege | model code deserialized from an MLflow artifact | accept | The artifact store is local to the primary machine, written only by this project's own registration path; no third-party model artifacts are loaded. Same trust model the EP/WP pickles already operate under |
| T-2.1-18 | Tampering | train/val leakage inflating the recorded metrics | mitigate | Task 1 builds the layout from the manifest's clip-level split and a test asserts no clip appears in both directories |
</threat_model>
