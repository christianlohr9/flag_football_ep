# Phase 2.1: CV Tracking Pilot (Go/No-Go Gate) - Research

**Researched:** 2026-08-24
**Domain:** Sports computer vision pipeline (zero-shot pre-labeling -> model-in-the-loop annotation -> small-object detector fine-tune -> multi-object tracking -> unsupervised team clustering -> manual homography -> XY export), run on a solo-developer two-machine setup (Apple Silicon Mac + Windows/CUDA box)
**Confidence:** MEDIUM-HIGH (stack and licensing verified against live registries/GitHub; several macOS/CVAT interaction risks are MEDIUM confidence from GitHub issues, not official docs)

## Summary

This phase wires together five off-the-shelf, license-clean building blocks — Grounding DINO (zero-shot pre-labels), CVAT+SAM2 (correction UI), RF-DETR-Small (fine-tuned detector), OC-SORT via `trackers` (tracking), SigLIP+UMAP+KMeans (team split) — into a single pilot run on the one game of drone material that exists (61 Hudl-re-encoded per-play clips, 1920x1080/30fps CFR, ~10.5 min total, 243 MB on disk). All five building blocks are verified Apache-2.0/MIT on their canonical registries (PyPI + GitHub license API), so the project's no-AGPL policy (C-06) holds — with one critical exception found during this research: **`BoxMOT`, the tracking library named in the source plan docs and research notes, is now AGPL-3.0-licensed** (confirmed via its own `LICENSE` file and GitHub API, current as of 2026-08-24). This phase must use `roboflow/trackers` (PyPI package `trackers`, Apache-2.0) instead — it implements OC-SORT natively, integrates with `supervision.Detections`, and works with any detector including RF-DETR.

The second major finding is environmental, not licensing: CVAT's own Docker Hub images (`cvat/server:latest`, `:dev`) are **amd64-only** as of this research date — no arm64 manifest exists. D-06's "self-hosted via Docker Compose on the M5 Max" will run under Rosetta/QEMU emulation, and the CVAT+Nuclio SAM2 serverless deployment path has multiple open, unresolved GitHub issues specific to macOS (bash `globstar` incompatibility in `deploy_cpu.sh`, `nuctl` volume-format errors, native-extension build failures for OpenVINO-era functions). SAM2 itself also has incomplete MPS operator coverage. None of this blocks the phase, but the plan should budget a fallback: running SAM2's video predictor as a standalone CPU/MPS script that exports pre-annotations for CVAT import, bypassing the Nuclio-in-Docker-on-ARM path entirely if it proves too flaky.

Third, direct inspection of the actual pilot footage (not just its CSV metadata) materially changes two open unknowns from CONTEXT.md. All three sampled clips (001, 030, 061) show the identical static framing — same goalpost, same "PANAMA" endzone lettering position, same stands — strongly suggesting **one single hover position for the entire game**, not "hover position(s)" plural. And a full-clip inspection of clip 015 (t=0/3/6/9s) confirms real play action (a route developing toward the end zone with a catch attempt at t=9s), with jersey numbers legible on multiple players despite the small on-screen size — better than the capture protocol's blunt "Unbrauchbar at >40m/1080p" tier would suggest in isolation. This is anecdotal (3-4 clips out of 61) and does not replace the D-03 sighting pass, but it de-risks the pilot's premise going into planning.

**Primary recommendation:** Build the pilot as a `flag_football_ep.cv` subpackage with an optional `cv` uv dependency group (`rfdetr`, `trackers`, `sahi`, `autodistill` + `autodistill-grounding-dino`, `transformers`, `umap-learn`, `scikit-learn`, `opencv-python`, `supervision`) — never `boxmot`. Use `roboflow/sports`' published `TeamClassifier` (SigLIP+UMAP+KMeans) and `ViewTransformer` (`cv2.findHomography`/`warpPerspective`) as direct implementation templates — both MIT-licensed, both exactly the algorithms D-05/D-13 already lock in. Wrap the fine-tuned RF-DETR checkpoint in an `mlflow.pyfunc.PythonModel` to reuse the existing champion-alias registry pattern from `model/registry.py` unchanged.

### Pattern 1: MLflow pyfunc wrapper for a non-flavor model
**What:** Wrap the trained `RFDETRSmall` object in a small `mlflow.pyfunc.PythonModel` subclass (`load_context` loads the checkpoint path from `artifacts`, `predict` calls the underlying `.predict()`), then `mlflow.pyfunc.log_model(python_model=..., artifacts={"weights": checkpoint_path})`.
**When to use:** Any time a library's native checkpoint format doesn't match one of MLflow's built-in flavors (xgboost, pytorch, sklearn, ...) but the project still wants the standard log/register/promote/resolve flow already proven in `model/registry.py`.
**Example:**
```python
# Source: MLflow official docs pattern (mlflow.org/blog/custom-pyfunc), applied to RF-DETR
# by reasoning in this research session -- no RF-DETR-specific tutorial found, verify the
# predict() signature against the installed rfdetr version before relying on it.
import mlflow.pyfunc

class RFDETRWrapper(mlflow.pyfunc.PythonModel):
    def load_context(self, context):
        from rfdetr import RFDETRSmall
        self.model = RFDETRSmall(pretrain_weights=context.artifacts["weights"])

    def predict(self, context, model_input):
        return self.model.predict(model_input)

with mlflow.start_run():
    mlflow.pyfunc.log_model(
        name="model",
        python_model=RFDETRWrapper(),
        artifacts={"weights": str(checkpoint_path)},
        registered_model_name="cv_detector_model",
    )
# reuse model/registry.py's promote()/resolve_champion() unchanged with name="cv_detector_model"
```

### Pattern 2: Team classification via SigLIP + UMAP + KMeans
**What:** Extract SigLIP vision-embeddings per player crop, reduce to 3D via UMAP, cluster into 2 groups via KMeans -- no jersey-color labels needed.
**When to use:** Team assignment on any pilot/game where labeling jersey colors by hand is undesirable (this project's D-13/plan-2 default).
**Example:**
```python
# Source: github.com/roboflow/sports sports/common/team.py (MIT license), confirmed via
# WebFetch of the raw file in this research session
from transformers import SiglipVisionModel, AutoProcessor
import umap
from sklearn.cluster import KMeans

SIGLIP_MODEL_PATH = "google/siglip-base-patch16-224"

class TeamClassifier:
    def __init__(self, device="cpu"):
        self.model = SiglipVisionModel.from_pretrained(SIGLIP_MODEL_PATH).to(device)
        self.processor = AutoProcessor.from_pretrained(SIGLIP_MODEL_PATH)
        self.reducer = umap.UMAP(n_components=3)
        self.cluster_model = KMeans(n_clusters=2)

    def extract_features(self, crops):
        # PIL-convert crops, batch through processor + model, mean-pool hidden states
        ...

    def fit(self, crops):
        features = self.extract_features(crops)
        projections = self.reducer.fit_transform(features)
        self.cluster_model.fit(projections)

    def predict(self, crops):
        features = self.extract_features(crops)
        projections = self.reducer.transform(features)
        return self.cluster_model.predict(projections)
```

### Pattern 3: Manual homography calibration
**What:** `cv2.findHomography(source_px, target_field_pts)` fit once per hover position; `cv2.perspectiveTransform` for point-by-point conversion, `cv2.warpPerspective` for full-frame top-down rendering (radar reel).
**When to use:** Every static-camera/drone-hover setup (D-05 locked decision); never build a custom DLT solver.
**Example:**
```python
# Source: github.com/roboflow/sports sports/common/view.py (MIT license), confirmed via
# WebFetch of the raw file in this research session
import cv2
import numpy as np

class ViewTransformer:
    def __init__(self, source: np.ndarray, target: np.ndarray):
        source = source.astype(np.float32)
        target = target.astype(np.float32)
        self.m, _ = cv2.findHomography(source, target)
        if self.m is None:
            raise ValueError("homography could not be calculated")

    def transform_points(self, points: np.ndarray) -> np.ndarray:
        if points.size == 0:
            return points
        reshaped = points.reshape(-1, 1, 2).astype(np.float32)
        transformed = cv2.perspectiveTransform(reshaped, self.m)
        return transformed.reshape(-1, 2)

    def transform_image(self, image: np.ndarray, resolution_wh: tuple) -> np.ndarray:
        return cv2.warpPerspective(image, self.m, resolution_wh)
```
Field-coordinate targets (D-13: x in yards on the `yardline_50` axis, y across field width) are just the `target` array's units -- pick yards directly and every downstream consumer (2.3's EPA join) reads native coaching units with no unit-conversion step.

### Anti-Patterns to Avoid
- **Hand-rolling a 4-point DLT homography solver:** `cv2.findHomography` (optionally with `cv2.RANSAC` for >4 noisy points) is a one-line, battle-tested replacement -- there is no reason to derive the projective transform by hand.
- **Training RF-DETR at its architecture default resolution without checking the sighting pass first:** RF-DETR-Small defaults to 512x512 input; C-05 requires per-domain inference settings, and the drone regime (small, distant players) likely needs a higher `resolution` (must stay a multiple of 32 for detection models, e.g. 576/704) or SAHI tiling — decide from measured apparent object size, not from the library default.
- **Reaching for `boxmot` because it's what the source docs say:** see Pitfall 2. The docs are stale on this specific point.
- **Assuming one `uv.lock` resolution works identically on both machines:** the M5 Max needs the MPS-enabled `torch` wheel, the Dell box needs a CUDA-enabled `torch` wheel matching its installed CUDA toolkit version. Treat these as two separate environments even though they share one `pyproject.toml`.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|--------------|-----|
| Small-object detector for player/referee classes | A YOLO variant from scratch, or an anchor-based CNN | `rfdetr` fine-tune | Apache-2.0, DINOv2 backbone, purpose-built for fast fine-tuning on small custom datasets, avoids the C-06 AGPL trap entirely |
| Multi-object tracking with ID continuity across occlusion | A custom Kalman filter + Hungarian matcher | `trackers.OCSORTTracker` (roboflow, Apache-2.0) | OC-SORT's observation-centric re-update/momentum mechanisms are exactly what's needed for the ≥90%-no-ID-switch gate criterion (C-09); reinventing this is real engineering risk for zero pilot-scope benefit |
| Team assignment without labels | Hand-coded jersey-color HSV thresholds | SigLIP + UMAP + KMeans (`roboflow/sports` pattern) | Color thresholding breaks under the exposure variance the capture protocol already flags as a domain risk; embedding-based clustering is robust to lighting and is the proven pattern for this exact problem |
| Manual homography math | Custom perspective-transform derivation | `cv2.findHomography`/`warpPerspective`/`perspectiveTransform` | OpenCV's DLT+RANSAC implementation is the industry standard; zero reason to re-derive |
| Zero-shot pre-labeling | Training a tiny detector from nothing before any labels exist | Grounding DINO via `autodistill` | Purpose-built for exactly this bootstrap step; ~10x labeling-cost reduction is the documented industry pattern (`docs/research-notes.md` point 5) |
| Small-object tiled inference | Custom sliding-window + NMS-merge logic | `sahi` | Model-agnostic via `supervision` loaders, has a documented RF-DETR integration path, handles the tile-boundary NMS merge correctly (mostly -- see Pitfall 4 for a known edge case) |

**Key insight:** Every algorithmic building block this phase needs already has a maintained, permissively-licensed, and (per this research) individually verified-non-slop implementation. The actual engineering work in this phase is integration, calibration, and measurement — not model/algorithm development.

## Common Pitfalls

### Pitfall 1: CVAT + Nuclio self-hosted setup on Apple Silicon is genuinely rough
**What goes wrong:** `docker compose up` for CVAT pulls `cvat/server` images that are amd64-only (verified via Docker Hub API on both `latest` and `dev` tags, 2026-08-24) -- Docker Desktop on the M5 Max will run these under Rosetta/QEMU emulation. Deploying the SAM2 Nuclio serverless function on top adds a second layer of risk: multiple open, apparently-unresolved GitHub issues describe `deploy_cpu.sh` failing on macOS's default bash (`shopt: globstar: invalid shell option name` -- macOS ships bash 3.2, which lacks `globstar`), `nuctl` volume-mount format errors, and older OpenVINO-based serverless functions failing with "Tensorflow is not built for this platform" under emulation.
**Why it happens:** CVAT's serverless functions were built and tested primarily on Linux/x86_64 with an NVIDIA GPU in mind; Apple Silicon support is not an explicit target of the project as of this research date.
**How to avoid:** (1) Install a modern bash via Homebrew (`brew install bash`) and invoke deployment scripts with it explicitly, not the macOS system bash. (2) Budget real setup time -- this is not a 10-minute `docker compose up`. (3) Have a fallback ready: run SAM2's video predictor as a standalone Python script (CPU or MPS-with-fallback, see Pitfall 3) that writes mask-propagated pre-annotations directly to a COCO/CVAT-importable format, then use CVAT purely as a correction UI without ever deploying the Nuclio SAM2 function. This still satisfies D-06's "footage never leaves the user's machines" requirement.
**Warning signs:** `docker compose up` containers restart-looping; `nuctl deploy` errors mentioning volume format or `insufficient_scope`; SAM2 tracker "assisted annotation" button in the CVAT UI silently doing nothing.
**Confidence:** MEDIUM (GitHub issues, not official CVAT docs; the underlying amd64-only image claim is HIGH confidence, directly verified via Docker Hub API).

### Pitfall 2: BoxMOT license drift — source docs are stale
**What goes wrong:** `docs/plan-2-cv-tracking.md` and `docs/research-notes.md` both list BoxMOT (via the PyPI package `boxmot`) as an OC-SORT tracking option under an "MIT/Apache" license summary. As of this research session, `mikel-brostrom/boxmot`'s own `LICENSE` file is the full GNU Affero General Public License v3.0 text, and the GitHub API confirms `license.spdx_id: "AGPL-3.0"`.
**Why it happens:** Licenses on actively-developed OSS projects change over a project's lifetime; the source docs were evidently written when BoxMOT carried a different (or no explicit) license.
**How to avoid:** Use `roboflow/trackers` (PyPI package name `trackers`, Apache-2.0, confirmed) instead. It implements OC-SORT natively and is designed to slot into an RF-DETR + `supervision` pipeline with no glue code.
**Warning signs:** Any task description or code comment that imports `boxmot` — treat as a hard stop, this violates the project's own C-06 constraint.
**Confidence:** HIGH (directly verified `LICENSE` file content + GitHub API license field, cross-checked against the original OC-SORT reference implementation which is MIT-licensed and roboflow/trackers which is Apache-2.0).

### Pitfall 3: SAM2 and Grounding DINO have incomplete Apple Silicon acceleration
**What goes wrong:** SAM2 raises errors on some operations when forced onto `device="mps"` (not all ops are implemented for the MPS backend); Grounding DINO's `MultiScaleDeformableAttention` module is a custom CUDA operator that fails to compile on a machine without CUDA and silently falls back to a pure-Python/CPU implementation (a "Failed to load custom C++ ops" warning, not a hard error). Separately, Grounding DINO's Swin-Transformer backbone uses `torch.roll`, which MPS does not support unless `PYTORCH_ENABLE_MPS_FALLBACK=1` is set.
**Why it happens:** Both models were developed and primarily tested against CUDA hardware; MPS support is retrofitted and incomplete as of this research date.
**How to avoid:** For the pilot's one-time, few-hundred-frame pre-labeling pass, plain CPU execution is acceptable (slow, but this is not a hot loop) — do not spend setup time chasing MPS acceleration for Grounding DINO. If MPS is attempted anyway, set `PYTORCH_ENABLE_MPS_FALLBACK=1` before import. For SAM2, budget for CPU fallback in the standalone-script contingency described in Pitfall 1.
**Warning signs:** `RuntimeError` mentioning an MPS-unsupported operator; a console warning about failing to load custom C++/CUDA ops (this one is informational, not fatal — CPU fallback still runs correctly, just slower).
**Confidence:** MEDIUM (WebSearch cross-referenced against multiple GitHub issues on both `facebookresearch/sam2` and `IDEA-Research/GroundingDINO`; no single official doc confirms all details, but the pattern is consistent across sources).

### Pitfall 4: SAHI + RF-DETR tiling has a known tuning gap at high tile-resolution
**What goes wrong:** SAHI is documented as supporting RF-DETR via `supervision` data loaders (model-agnostic slicing), but at least one open GitHub issue (`roboflow/rf-detr#780`) reports RF-DETR-Seg + SAHI "still missing cells in dense tiles, and inference is too slow" at 1900-2200px slice sizes, asking for tuning/speedup advice with no confirmed resolution at the time of this research.
**Why it happens:** Tile-boundary object splitting and cross-tile NMS merging is an inherently fiddly parameter space (overlap ratio, tile size, confidence threshold), and DETR-style models (fixed query count per forward pass, no anchor-based NMS baked in the same way YOLO has) may need different tuning than SAHI's YOLO-era defaults.
**How to avoid:** Don't reach for SAHI by default — the plan should first measure apparent player size from the sighting pass (D-03) and only enable tiling if plain full-frame inference at a bumped `resolution` (e.g. 576 or 704, still under the "one game < 1h" inference budget) proves insufficient. If tiling is needed, start with SAHI's documented default slice/overlap parameters and treat further tuning as a measured, not assumed, step.
**Warning signs:** Missing detections specifically at tile-seam locations on the field; per-game inference time creeping toward or past the 1h/game C-09 gate threshold once tiling is enabled.
**Confidence:** MEDIUM (one specific GitHub issue found; SAHI+RF-DETR compatibility itself is documented in a HuggingFace Space demo and Roboflow's own blog post, so the integration path exists, but the tuning gap at high resolution is a real, currently-open report).

### Pitfall 5: MLflow's `file:` tracking store doesn't support the model registry (already-known project pitfall, applies again here)
**What goes wrong:** `model/registry.py` and `model/mlflow_store.py` already carry an explicit code comment about this: MLflow's model-registry API (`register_model`, alias calls) does not work against the deprecated local `file:` FileStore because the registry needs SQL query capabilities FileStore doesn't implement.
**Why it happens:** The registry is metadata-heavy (versions, aliases, stages) and MLflow's file-based store was never designed for it.
**How to avoid:** Route every CV MLflow call through the existing `mlflow_store.configure(config)` / `ensure_experiment(...)` functions exactly like `model/train.py` does — do not call `mlflow.set_tracking_uri()` with a raw `file:` path anywhere in the new `cv/` subpackage.
**Warning signs:** `register_model`/`set_registered_model_alias` calls raising confusing `MlflowException`s or silently no-op'ing.
**Confidence:** HIGH (this is the project's own documented prior finding, re-surfaced here because the new `cv/registry.py` module is the second place in the codebase that will call these APIs).

## Open Questions

1. **Does the RF-DETR-Small default 512x512 resolution suffice for this footage, or does the sighting pass demand a bump / SAHI tiling?**
   - What we know: sample frames show players at roughly 25-45px tall in the raw 1920x1080 frame at the apparent hover altitude; jersey numbers are legible on several players in the sampled frames.
   - What's unclear: whether this holds across all 61 clips and all field positions (players farther from the camera, e.g. deep in the far end zone, will be smaller); no formal per-clip measurement has been done.
   - Recommendation: D-03's sighting pass should include a rough apparent-object-size measurement (even eyeballed pixel height on a few representative frames per hover position) to make the resolution/SAHI decision (Claude's Discretion per CONTEXT.md) from evidence rather than the RF-DETR library default.

2. **Will `autodistill-grounding-dino` install cleanly on the M5 Max, or will its underlying CUDA-op dependency need the HF `transformers` GroundingDINO fallback?**
   - What we know: the original IDEA-Research GroundingDINO has a well-documented CPU-fallback path (informational warning, not a hard failure) when no CUDA is present, which is exactly the M5 Max's situation.
   - What's unclear: `autodistill-grounding-dino`'s exact pinned dependency chain was not installed/tested in this research session (no network install was attempted against the ecosystem's own resolver in this environment).
   - Recommendation: Treat the first `uv sync --extra cv` on the M5 Max as a smoke-test task; if `autodistill-grounding-dino` fails to import or is unusably slow, fall back to `transformers`' `GroundingDinoForObjectDetection` with the `IDEA-Research/grounding-dino-tiny` checkpoint (pure PyTorch, no custom op).

3. **How many hover positions does the full 61-clip set actually contain?**
   - What we know: 3 sampled clips (001, 030, 061) spanning the full clip-number range show identical framing.
   - What's unclear: the remaining 58 clips are unexamined; a genuinely different hover position (e.g. a mid-game repositioning for battery swap per the capture protocol's drive-based swap guidance) could exist between sampled clips.
   - Recommendation: D-03's sighting pass is the authoritative answer here; this research's finding should be treated as a favorable prior, not a substitute.
