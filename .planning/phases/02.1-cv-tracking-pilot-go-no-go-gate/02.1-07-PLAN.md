<objective>
Turn 10.5 minutes of drone footage into a labelling work package: a deterministic, clip-stratified
sample of roughly 400 frames with a leak-free clip-level train/val split, pre-annotated zero-shot so
the human corrects boxes instead of drawing them.

Purpose: this is the "~10x labelling saving" step from `docs/research-notes.md`, and the clip-level
split is what keeps the later detector metric honest (a val frame from a clip whose neighbouring
frames were trained on is not a validation frame). The frame sample must be reproducible — plan
02.1-09's dataset hash and plan 02.1-10's training run both key on it.
Output: `frames.sample_training_frames` + manifest I/O, `cv/prelabel.py`, tests.
</objective>

<interfaces>
Frame sample manifest (`data/labels/{session_id}/manifest.json`, gitignored):

{
  "session_id": str,
  "seed": int,
  "target": int,
  "split": {"<clip_number>": "train" | "val", ...},     // clip-level, never frame-level
  "frames": [
    {"clip_number": int, "clip_path": str, "frame_index": int,
     "timestamp_s": float, "image_path": str, "split": "train"|"val"}, ...
  ]
}

COCO pre-label output (`data/labels/{session_id}/prelabels/instances.json`, gitignored):
COCO 1.0 `instances` layout with `categories = [{"id": 1, "name": "player"}, {"id": 2, "name": "referee"}]`
(the `cv.dataset.CLASS_NAMES` vocabulary, in that order), `images[].file_name` relative to the
prelabels directory, `annotations[].bbox` in COCO `[x, y, w, h]` pixel form, and `annotations[].score`
carrying the zero-shot confidence so the annotator can sort by it.
</interfaces>

  <action>
Implement `sample_training_frames(config, session_id, *, target, seed, out_dir)`:

- Allocate the `target` frame budget (default `config.cv.label_frame_target` = 400) proportionally to
  clip duration across all clips of the session, with a floor of 3 and a ceiling of 12 frames per
  clip, so no single long clip dominates and no clip is unrepresented. When more than one
  hover_position_id exists in `data/reference/hover_positions.csv`, allocate the budget per hover
  position first (proportional to that position's total footage) and then within it — the detector
  must see every camera regime.
- Within a clip, place the frames on an evenly spaced grid over `[0.5 s, duration - 0.5 s]`, then jitter
  each timestamp by up to +/- 40% of the grid spacing using a `random.Random(seed)` seeded once per
  clip from `(seed, clip_number)`. Even spacing alone would systematically sample the same play phase
  in every clip; pure randomness would clump. Frame indices are `round(t * fps)` from the inventory
  row, matching `extract_frames`' naming so a manifest entry and a written file always agree.
- Split by CLIP, not by frame: shuffle the clip numbers with `random.Random(seed)` and assign 20% (at
  least 6 clips) to `val`, the rest to `train`. Every frame inherits its clip's split. Document in
  the docstring why frame-level splitting would leak (adjacent frames of a 30 fps clip are nearly
  identical images).
- Extract every sampled frame with `extract_frames` into `out_dir` (default
  `config.paths.labels / session_id / "frames"`), and return the `FrameSampleManifest`.

Implement `write_manifest(manifest, path)` (atomic tmp-sibling + `os.replace`, JSON with sorted keys
and 2-space indent so a re-run produces a byte-identical file) and `read_manifest(path)` (raises a
named exception naming the path when absent, and when the manifest's `seed`/`target` disagree with
what the caller expects).

Extend tests/test_cv_frames.py using a tmp_path inventory plus generated clips:
- the same `(target, seed)` produces a byte-identical manifest across two runs
- the total frame count is within +/-10% of `target` and every clip has between 3 and 12 frames
- no clip appears in both splits; `val` holds at least 6 clips
- with two hover positions in the sighting CSV, both receive frames proportional to their footage
- frame indices in the manifest match the filenames actually written by `extract_frames`
- a different `seed` produces a different sample (guards against an accidentally-constant seed)
  </action>

Implement `prelabel_frames(config, frames_dir, out_dir, *, force=False)`:

- Load the sample manifest that belongs to `frames_dir` so the COCO `images` list is exactly the
  sampled frames in manifest order (not a directory glob, which would silently include leftovers from
  an earlier run).
- Run the zero-shot backend recorded in `docs/cv-setup.md`. Primary path:
  `autodistill_grounding_dino.GroundingDINO` with
  `CaptionOntology({"person": "player", "referee": "referee"})`. Fallback path (used when the primary
  backend is unavailable, per RESEARCH Alternatives Considered): `transformers`
  `GroundingDinoForObjectDetection` with checkpoint `IDEA-Research/grounding-dino-tiny` and the text
  prompt `"person. referee."`. Select the backend explicitly through a module-level
  `_BACKENDS` mapping and a `backend` keyword defaulting to autodetection; raise
  `PrelabelBackendUnavailable` naming both the attempted backend, the underlying import error and the
  fallback command when neither is importable. Never return an empty COCO file as if it were a
  successful run.
- Run on CPU by default and set `PYTORCH_ENABLE_MPS_FALLBACK=1` before importing torch when
  `config.cv.device == "mps"` (RESEARCH Pitfall 3: Grounding DINO's Swin backbone uses `torch.roll`,
  which MPS does not implement). A few hundred frames on CPU is minutes, not a hot loop — do not spend
  effort on acceleration here.
- Emit `out_dir / "instances.json"` in the COCO layout defined in this plan's `<interfaces>` block,
  writing atomically. Copy (or hardlink) the sampled frames next to it so the directory is a
  self-contained CVAT import package.
- `force=False` and an existing `instances.json` -> skip the model run, return the existing result
  with a notice saying so (the `--force/--no-force` cache-bypass ergonomics of `ffep fetch-sportapp`).
- `PrelabelResult.notices` records the backend used, the device, the wall-clock seconds, the number
  of frames with zero detections (expected on drone footage — record it, do not hide it) and the
  confidence threshold applied.

- second call without `--force` skips the backend (assert the fake backend's call count stays put)

- an unavailable backend raises `PrelabelBackendUnavailable` whose message names the fallback

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| extracted frames -> git | sampled frames show identifiable players (DSGVO, `docs/capture-legal.md`) |
| HuggingFace hub -> process | Grounding DINO weights are fetched from a remote registry |
| manifest JSON -> later plans | the sample manifest determines what gets trained on and evaluated against |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-2.1-01 | Information disclosure | `data/labels/{session}/frames` and `prelabels` | mitigate | Everything is written under `config.paths.labels`, gitignored by plan 02.1-01; acceptance criteria assert `git check-ignore` on both the manifest and the COCO file |
| T-2.1-18 | Tampering | train/val leakage through frame-level splitting | mitigate | Task 1 splits by clip and tests assert no clip appears in both splits — a leak here would make plan 02.1-10's detector metric meaningless and could wrongly pass the gate |
| T-2.1-19 | Spoofing | a silently-empty zero-shot run passed off as a successful pre-label pass | mitigate | Task 2 raises `PrelabelBackendUnavailable` instead of writing an empty COCO file, and records the zero-detection frame count in `notices` |
| T-2.1-17 | Tampering | remote Grounding DINO checkpoint fetched at runtime | accept | Fixed, named checkpoints only (`IDEA-Research/grounding-dino-tiny` for the fallback), no user-controlled model id; the package itself passed the legitimacy audit in 02.1-RESEARCH.md |
| T-2.1-10 | Tampering | half-written manifest or COCO file | mitigate | Both are written atomically (tmp sibling + `os.replace`) |
</threat_model>
