# Phase 02.1: Code Review Report

**Reviewed:** 2026-08-30T07:03:23Z
**Depth:** standard
**Files Reviewed:** 26
**Status:** issues

## Summary

Full review of the Phase 2.1 CV tracking pilot production scope (23 Python modules plus `ffep.toml`, `pyproject.toml`, `.env.example`), with attention to CVAT credential handling, PII paths, and subprocess/ffmpeg usage as requested.

The security posture is largely sound: CVAT credentials are resolved only through `config.secret()` from the environment/`.env`, never interpolated into exception messages or echoed output; every `subprocess.run` call (ffmpeg/ffprobe in `cv/frames.py`) uses argument lists, never `shell=True`; the CVAT export unzip has a real zip-slip guard (`dataset._safe_extract_zip`); the hand-maintained inventory CSV's `local_path` is checked for absolute/`~`/`..` traversal (`frames.clip_paths`); and PII-bearing artifacts (extracted frames, prelabel packages, GT frames, overlay videos) default to the gitignored `data/labels/` tree — with one exception noted below (WR-06). No hardcoded secrets, no `eval`, no injection paths were found.

The correctness picture is weaker. The `ffep cv benchmark` command — the CLI surface for the C-09 "<1h/game inference" gate metric — is broken twice over: it reads a per-stage timing parquet that nothing in the codebase ever writes (`track_session` computes `stage_seconds` and then drops it), and even against its intended input shape its footage-seconds formula undercounts real footage duration by a factor of ~3-4 while hardcoding 30 fps, which would understate the extrapolated game runtime in exactly the direction that flatters the gate. The gate document evidently got its 47.83-min figure from calling the library function directly, so the shipped number is not necessarily wrong — but the shipped command is. A cluster of warnings concerns silent metric distortion (continuity denominator, unvalidated review verdicts, silent 30 fps fallback), hidden cwd dependence in library-level `load_config()` calls, and CLI results (`match_rate`, unmatched counts) computed but never surfaced.

## Critical Issues

### CR-01: `ffep cv benchmark` reads a stage-timing parquet that no code path ever produces

**File:** `src/flag_football_ep/cv/commands.py:570-598`
**Issue:** The command loads `--tracks` (help text: "Input tracking Parquet (carries per-stage timing metadata)") and builds `StageTiming(stage=row["stage"], seconds=row["seconds"], frames=row["frames"])` from its rows. The canonical tracking parquet is written exclusively by `schema.write_tracking_parquet` with `TRACKING_COLUMNS`, which contains no `stage`/`seconds`/`frames` columns. No writer of a stage-timing parquet exists anywhere in `src/` (verified by grep). `track.track_session` accumulates exactly this data in `TrackResult.stage_seconds` but never persists it, and the `ffep cv track` command does not even echo it. Running `ffep cv benchmark --tracks data/processed/tracking/<session>_tracks.parquet` crashes with `polars.exceptions.ColumnNotFoundError: stage` on any real artifact. The C-09 runtime gate metric is therefore unreachable through the documented CLI; the gate doc's number could only have been produced by hand-driving the library function.
**Fix:** Persist stage timings from `track_session` (e.g. a sibling `<session>_stage_timings.parquet` or JSON with columns `stage`, `seconds`, `frames`) and point the benchmark command at that artifact:
```python
# track.py, after the write stage:
timing_df = pl.DataFrame(
    {"stage": list(stage_seconds), "seconds": list(stage_seconds.values()),
     "frames": [frame_counts[s] for s in stage_seconds]}
)
timing_df.write_parquet(resolved_out_path.with_name(f"{session_id}_stage_timings.parquet"))
```
and change `benchmark`'s `--tracks` option to `--timings` with matching help text.

### CR-02: benchmark `footage_seconds` formula inflates the frame count ~3-4x and hardcodes 30 fps, understating the C-09 runtime extrapolation

**File:** `src/flag_football_ep/cv/commands.py:596`
**Issue:** `footage_seconds = sum(stage.frames for stage in stages) / 30.0`. Every stage (`decode`, `detect`, `track`, `write`) covers the *same* frames — `detect.DetectionRun` increments each stage's frame counter once per decoded frame — so summing `frames` across stages counts each real frame once per stage (~3-4x). An inflated `footage_seconds` deflates every per-stage real-time factor in `extrapolate_game_runtime` by the same factor, so the extrapolated minutes-per-game come out ~3-4x too low — an error in the favorable direction for the "<1h/game" gate criterion, which is precisely the kind of silently flattering number the module's own "Richtwert, kein Messprotokoll" framing forbids. Separately, `/ 30.0` hardcodes 30 fps even though both `frames._probe_fps` and `track._probe_fps` exist because "a declared fps can round differently."
**Fix:** Derive footage seconds from one stage's frame count and a real fps:
```python
decode = next(s for s in stages if s.stage == "decode")
footage_seconds = decode.frames / measured_fps  # persist fps alongside the timings (CR-01)
```

## Warnings

### WR-01: Continuity coverage denominator is the last tracked frame, not the clip's real frame count

**File:** `src/flag_football_ep/cv/continuity.py:120-130`
**Issue:** `_measure_clip` uses `clip_frame_count = max(frame_index) + 1` computed from the *tracked rows*. If detection/tracking dies partway through a clip (exactly the failure mode this metric exists to catch), the denominator shrinks to the last frame that produced a confirmed track, and `longest_track_frac` is overstated — e.g. a track covering frames 0-299 of a 900-frame clip where tracking stopped at frame 300 reports `longest_track_frac = 1.0`. This biases the C-09 auto-flag metric optimistically, against the module's own "whole game is the denominator" (D-09) rule. `video_inventory.csv` durations and a probed fps are already available in `track.py` for exactly this comparison.
**Fix:** Compute the denominator from `round(declared_duration * fps)` (reusing `track._read_declared_durations`/`_probe_fps`), falling back to `max(frame_index) + 1` only when the inventory has no duration — and emit a notice when the fallback is used.

### WR-02: `_VALID_VERDICTS` is dead code — human review verdicts are never validated

**File:** `src/flag_football_ep/cv/continuity.py:97, 230-264`
**Issue:** `_VALID_VERDICTS = frozenset({"pass", "fail", ""})` is defined and never referenced. `summarise_review` counts `verdicts == "pass"` and `verdicts == "fail"` but treats any other non-empty string (a typo like `Pass`, `ok`, `yes`) as *reviewed* (`reviewed_mask` true) while counting it as neither pass nor fail. A typo'd verdict therefore silently deflates `pass_rate` (denominator `n_clips`, numerator misses the row) with no error — the exact "quietly wrong headline number" failure mode this module's docstring says it exists to prevent. The unused constant shows the validation was intended and never wired.
**Fix:** In `summarise_review` (and `_load_existing_human_columns`), raise on any verdict outside `_VALID_VERDICTS`:
```python
bad = df.filter(~pl.col("verdict").fill_null("").is_in(sorted(_VALID_VERDICTS)))
if bad.height:
    raise ValueError(f"invalid verdict(s) in {review_csv}: {bad['clip_number'].to_list()}")
```

### WR-03: Small sessions silently get zero (or nearly zero) training clips from the val-split floor

**File:** `src/flag_football_ep/cv/frames.py:69-70, 398-403`
**Issue:** `n_val = min(len(clip_numbers), max(_MIN_VAL_CLIPS, round(_VAL_FRACTION * len(clip_numbers))))` with `_MIN_VAL_CLIPS = 6`. For a session with 6 or fewer clips, *every* clip is assigned `val` and the train split is empty; with 7-8 clips, 1-2 train clips remain. No error or notice is raised at sampling time — the failure only surfaces much later as `validate_coco`'s misleading "split 'train' has zero 'player' boxes" error, or as a nonsense fine-tune. Fine for the 61-clip pilot, wrong for any smaller session (e.g. a follow-up steeper-angle capture with few clips, which the gate decision explicitly anticipates).
**Fix:** Cap `n_val` so at least one train clip always survives and raise a named error when the session is too small for a meaningful split, e.g. `n_val = min(n_val, len(clip_numbers) - 1)` plus `if len(clip_numbers) < 2: raise ManifestError(...)`.

### WR-04: `extract_frames` silently overwrites on frame-index collisions; manifest carries duplicate entries

**File:** `src/flag_football_ep/cv/frames.py:246-274, 420-441`
**Issue:** Output filenames are keyed only by `round(timestamp * fps)`. Two jittered timestamps in adjacent grid cells — and especially the clamped `min(end, max(start, ...))` timestamps on short clips, where several cells clamp to the same boundary — can round to the same `frame_index`. The second ffmpeg call overwrites the first file, and the manifest then contains two `FrameSample` entries pointing at the same `image_path`/`frame_index`. Downstream, `prelabel` emits two COCO `images` entries with the same `file_name` (distinct ids), which corrupts the CVAT import and the `validate_coco` file-name set comparison (sets silently dedupe).
**Fix:** After computing `timestamps`, dedupe by rounded frame index before extraction (`sorted({round(t * fps): t for t in timestamps}.values())`), or raise when a collision would occur.

### WR-05: `track._probe_fps` silently falls back to 30.0, corrupting `timestamp_s` without a notice

**File:** `src/flag_football_ep/cv/track.py:179-192`
**Issue:** When `cv2.VideoCapture.get(CAP_PROP_FPS)` returns 0/NaN (common for slightly damaged containers), the function silently returns `30.0`. Every `timestamp_s` in the canonical tracking parquet, the tracker's `frame_rate` tuning, and the declared-duration frame-count sanity check then use a fabricated fps with no notice — for a 25 or 60 fps clip the timestamps are wrong by 17-100% and the "decoded N frames, expected ~M" check will fire with misleading numbers (or falsely pass). `frames._probe_fps` (ffprobe) raises `FrameExtractionError` in the same situation; the two modules disagree on error discipline for the same probe.
**Fix:** Either raise (mirroring `frames._probe_fps`) so per-clip containment in `track_session` records it as a notice, or append an explicit `notices` entry naming the clip and the assumed fps.

### WR-06: Showcase reel (rendered player footage, PII) defaults to `data/processed/`, contradicting the project's own PII placement rule

**File:** `src/flag_football_ep/cv/commands.py:561` (cf. commands.py:447-449, overlay.py:14-15)
**Issue:** `ffep cv radar` defaults `out_path` to `cfg.paths.processed / "showcase.mp4"`. The reel's left half is `overlay.draw_frame` over raw frames — rendered player footage. The `overlay` command's own comment three commands earlier states: "Overlays are rendered player footage (PII, T-2.1-01) — they belong under the gitignored label tree, never under `reports/` or `data/processed/`", and `overlay.py`'s docstring repeats it. `data/processed/*` happens to be gitignored today, but it is ignored as "regenerable pipeline output", not as PII — a future re-inclusion of processed artifacts (or a sync/backup rule keyed on that directory's non-PII framing) would exfiltrate footage. The 02.1-17 summary confirms the real reel was manually placed under `data/labels/.../showcase/`, i.e. operators already had to work around this default.
**Fix:** `out_path = out or (cfg.paths.labels / cfg.cv.pilot_session_id / "showcase" / "showcase.mp4")`.

### WR-07: cwd-dependent `load_config()` calls inside library functions can load the wrong config or crash

**File:** `src/flag_football_ep/cv/homography.py:237, 448`; `src/flag_football_ep/cv/accuracy.py:213-215`
**Issue:** `load_calibration`, `pick_points`, and `load_gt_positions` internally call `load_config()` with the default `Path("ffep.toml")`, which resolves against the process working directory. `config.py`'s own docstring promises "behavior is the same regardless of where `ffep` is invoked from", and every CLI command threads `--config` through — but these three re-load a *different* config behind the CLI's back. Run from any directory other than the repo root the commands crash (`FileNotFoundError: config file not found: ffep.toml`); run from a directory containing a different valid `ffep.toml` (e.g. a second checkout or a scratch copy with different field dimensions), calibration/GT validation silently runs against the wrong field geometry. The fixed `load_calibration(path)`-only signature is a test contract, but the config can still be resolved relative to a known anchor.
**Fix:** Resolve the default config path relative to the calibration/GT file being loaded or accept the already-loaded `Config` via an optional keyword with a contract-compatible default (`def load_calibration(path, *, config: Config | None = None)`), falling back to `load_config()` only as a last resort with a warning.

### WR-08: CVAT error handling erases all diagnostic information (`from None` + generic message)

**File:** `src/flag_football_ep/cv/dataset.py:364-371, 397-405`
**Issue:** `create_cvat_task`/`export_cvat_task` wrap the entire network interaction in `except Exception as exc: raise DatasetError(f"... (HTTP {getattr(exc, 'status', 'unknown')})") from None`. Credential hygiene justifies not echoing the raw exception (an auth failure body could quote the username), but this implementation throws away *everything*: a DNS failure, a connection refused (CVAT container down — the most common case for a localhost Docker instance), a timeout, a 401, and an SDK bug all surface identically as "CVAT task creation failed against http://localhost:8080 (HTTP unknown)". The operator cannot distinguish "start Docker" from "wrong password" from "malformed COCO". The exception *type* name carries no credentials and is safe to include.
**Fix:** Include `type(exc).__name__` and the sanitized status/reason in the message, and chain with `from exc` (traceback text does not reach `typer.echo` output; if chaining is deemed too risky, at minimum name the exception class):
```python
raise DatasetError(
    f"CVAT task creation failed against {config.cv.cvat_host} "
    f"({type(exc).__name__}, HTTP {status})"
) from None
```

### WR-09: `teams.assign_teams`/`extract_track_crops` have no CLI wiring — `team_id` is unreachable through the documented command surface

**File:** `src/flag_football_ep/cv/commands.py` (whole file), `src/flag_football_ep/cv/teams.py`
**Issue:** The `cv_app` surface covers sight/sample/prelabel/cvat/dataset/train/promote/track/calibrate/coords/export/overlay/continuity/accuracy/radar/benchmark — but no `teams` command exists. `track_session` writes rows with `team_id` null; nothing an operator can invoke fills it. Downstream consumers degrade silently: `overlay`/`radar` draw every player gray ("no team"), and `accuracy._select_gt_frames`'s `has_both_teams` ranking criterion is permanently false, silently weakening the stratified GT-frame selection. Given the module's fixed three-parameter contract and the palette's team-anchoring machinery, this looks like missing wiring rather than a deliberate omission.
**Fix:** Add a `ffep cv teams` command that reads the tracking parquet, calls `extract_track_crops` + `assign_teams`, and rewrites the parquet via `write_tracking_parquet`, echoing `TeamAssignmentResult.notices`.

### WR-10: `validate_coco` crashes with a bare `TypeError` on a COCO image entry missing `width`/`height`

**File:** `src/flag_football_ep/cv/dataset.py:165-171`
**Issue:** `img_w, img_h = image.get("width"), image.get("height")` tolerates absence by yielding `None`, but the very next line computes `x + w > img_w + eps`, which raises `TypeError: unsupported operand type(s)` instead of the documented `DatasetError` naming the offending item. A hand-edited or foreign-tool COCO export (untrusted input per T-2.1-02) missing these keys produces an unexplained traceback rather than the module's promised named validation failure.
**Fix:** Validate presence first: `if not isinstance(img_w, (int, float)) or not isinstance(img_h, (int, float)): raise DatasetError(f"image {image.get('file_name')!r} is missing width/height")`.

### WR-11: `render_showcase_reel` fixes frame size/fps from the first clip; mixed-resolution clips crash or get silently dropped by `VideoWriter`

**File:** `src/flag_football_ep/cv/radar.py:387-390, 426-428`
**Issue:** `half_size`, `canvas_wh`, and the writer's fps are locked from the first clip. The inventory schema records `resolution` *per clip*, and the sighting module's tier logic explicitly anticipates mixed resolutions within a session. For a later clip with a different height, `np.hstack([left, right])` raises `ValueError` mid-reel; with the same height but different width, the composed canvas no longer matches the writer's declared size and OpenCV's `VideoWriter.write` *silently discards* every frame of that clip — the reel plays through with whole plays missing and no error. Mixed fps likewise silently retimes later clips.
**Fix:** Per clip, compare `(src_width, src_height)` (and fps) against the locked values and either letterbox/resize the frame to `half_size` or raise a named `CvError` identifying the mismatching clip.

### WR-12: `_resolve_backend` catches only `ImportError`; weights-download failures propagate as bare library exceptions

**File:** `src/flag_football_ep/cv/prelabel.py:207-229`
**Issue:** The class docstring for `PrelabelBackendUnavailable` promises it covers "the Grounding DINO weights cannot be fetched", but `_resolve_backend` catches only `ImportError`. `_load_transformers_backend` calls `from_pretrained(...)` inside the loader, so an offline machine or a HuggingFace outage raises `OSError`/`requests.ConnectionError` straight through to the CLI — exactly the bare-library-exception leak the `cv/__init__.py` no-silent-failure convention says must never reach `cli.py`.
**Fix:** Catch `(ImportError, OSError)` in the loader loop (HF download failures subclass `OSError`), recording each in `errors` and raising `PrelabelBackendUnavailable` as designed.

## Info

### IN-01: `_apparent_player_heights` docstring states p50-then-p10 order but returns `(p10, p50, n)`

**File:** `src/flag_football_ep/cv/sighting.py:259-345`
**Issue:** Docstring opens "Median (p50) and 10th-percentile (p10) ... pixel height"; the return is `(p10, p50, frames_analyzed)`. The one caller unpacks correctly, but the doc/order mismatch is a swapped-metrics trap for the next caller.
**Fix:** Reword the docstring to state the actual return order, or return a small named tuple.

### IN-02: `PrelabelBackendUnavailable` misused for a missing frame file

**File:** `src/flag_football_ep/cv/prelabel.py:282-286`
**Issue:** A sampled frame missing on disk raises `PrelabelBackendUnavailable` — a backend-availability exception for a filesystem problem. Misleading class name in logs/tests.
**Fix:** Raise a dedicated `PrelabelInputError(CvError)` (or reuse `frames.ManifestError`).

### IN-03: `_find_coco_annotations` fallback picks the first arbitrary `*.json`

**File:** `src/flag_football_ep/cv/dataset.py:301-321`
**Issue:** When neither `instances.json` nor `instances_default.json` exists, `sorted(extract_dir.rglob("*.json"))[0]` silently promotes whatever JSON sorts first (which could be a CVAT manifest/metadata file) to `instances.json`.
**Fix:** Restrict the fallback to `annotations/*.json` or validate the chosen file has `images`/`annotations` keys before promoting it.

### IN-04: `export_cvat_task` leaves `task_{id}_export.zip` inside the COCO package directory

**File:** `src/flag_football_ep/cv/dataset.py:384, 415`
**Issue:** The downloaded archive stays in `out_dir` after extraction. `dataset_hash` ignores it (non-image suffix), but it doubles the on-disk footprint of PII imagery and clutters the package that `create_cvat_task`-style consumers iterate.
**Fix:** `archive_path.unlink(missing_ok=True)` after successful extraction.

### IN-05: `overlay.draw_frame`'s `config` parameter is unused

**File:** `src/flag_football_ep/cv/overlay.py:73-135`
**Issue:** `config` is accepted and never read — dead parameter that forces every caller (including `radar.render_showcase_reel`) to thread a value through for nothing.
**Fix:** Drop it, or document it as reserved if the signature is contract-locked.

### IN-06: Manifest stores absolute `image_path` but repo-relative `clip_path`

**File:** `src/flag_football_ep/cv/frames.py:429-441`
**Issue:** `FrameSample.image_path = str(out_path)` is machine-absolute while `clip_path` is deliberately repo-relative; a manifest copied between machines (Dell/Colab remote-training flow, C-10) has half-portable paths, and `prelabel`/`_filter_manifest_to_dataset` compare by basename to compensate.
**Fix:** Store `image_path` repo-relative like `clip_path` and resolve against `config.paths.data_root.parent` on read.

### IN-07: `_prepare_dataset_layout` can mix stale images into a reused `--out` directory

**File:** `src/flag_football_ep/cv/detect.py:280-291`
**Issue:** `split_dir.mkdir(parents=True, exist_ok=True)` plus copy-in never clears a pre-existing `dataset/train|valid` layout; re-running with an explicit `--out` after the manifest/dataset shrank leaves orphaned images beside the fresh `_annotations.coco.json`. RF-DETR trains from the annotation file so this is latent, but the directory no longer matches the recorded `content_sha256`.
**Fix:** `shutil.rmtree(dataset_dir, ignore_errors=True)` before rebuilding the layout.

### IN-08: `ffep cv coords` default overwrites the input tracking parquet in place

**File:** `src/flag_football_ep/cv/commands.py:401`
**Issue:** `out_path = out or tracks` rewrites the canonical artifact by default. The atomic write plus conform-before-write makes this safe against corruption, but a bad calibration (in-tolerance but wrong) irreversibly replaces the pixel-only original with mis-projected coordinates and no backup.
**Fix:** Acceptable if intentional (D-14 single-artifact rule); consider echoing an explicit "overwriting in place" notice.

### IN-09: GT picker HTML interpolates user-typed text into `innerHTML`/attribute values

**File:** `src/flag_football_ep/cv/accuracy.py:479-669` (`render()` template literals)
**Issue:** `pt.team`/`pt.scalePairId` values typed by the operator are re-rendered via `row.innerHTML = \`... value="${pt.team}" ...\`` without escaping — a `"` or `<` in the team hint breaks the panel markup (self-inflicted, local-file-only; no remote exposure). Same for CSV assembly, which only strips commas.
**Fix:** Set input values via `element.value = pt.team` instead of attribute interpolation.

### IN-10: `frames._probe_fps` divides by an unvalidated ffprobe denominator

**File:** `src/flag_football_ep/cv/frames.py:227-230`
**Issue:** `r_frame_rate` of `"30/0"` (seen on damaged containers) raises a bare `ZeroDivisionError` instead of `FrameExtractionError`.
**Fix:** Guard `float(den) == 0` and raise `FrameExtractionError` naming the clip and the raw ffprobe value.
