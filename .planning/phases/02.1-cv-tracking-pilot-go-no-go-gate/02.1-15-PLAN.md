<objective>
Measure C-09's position-error criterion honestly: a hand-labelled ground-truth set of player foot
positions across many plays, the measured error distribution in yards and metres, and an explicit
decomposition of where the error comes from.

Purpose: D-10 explicitly buys a full labelling week for this, because "~<= 1 m position error" is
otherwise unfalsifiable. The GT set is also a Phase 2.3 asset — every separation, spacing and speed
metric later computed on the XY data can be validated against it.
Output: `cv/accuracy.py`, a filled `data/reference/gt_positions.csv`, and `docs/pilot-accuracy.md`.
</objective>

no images. One row per hand-marked player-foot position:

Define `GT_COLUMNS`/`GT_SCHEMA` exactly as this plan's `<interfaces>` block, create the header-only
`data/reference/gt_positions.csv`, and implement `load_gt_positions(path)` on the
`reference._read_reference_csv` pattern with validate-on-load: `field_zone` restricted to the listed
vocabulary, `class_name` restricted to `player`/`referee`, pixel coordinates inside the declared frame
size, `hover_position_id` present in `hover_positions.csv`, `gt_id` unique, and a `scale_pair_id`
appearing on exactly two rows with a matching non-null `scale_true_yards`. Each violation raises a
named exception naming the offending `gt_id`.

Implement `prepare_gt_frames(config, tracks, *, n_frames, out_dir)`: choose the frames to label with
deliberate spread rather than at random — stratify across clips, across the five `field_zone` values
(using the tracked `x_yards` distribution to find frames with players in each zone), and across both
`team_id` values, then pick frames at moments with the most simultaneously tracked players so one
labelled frame yields many GT points. Export each chosen frame as a grid-annotated JPEG under
`out_dir` (gitignored label tree) and seed `data/reference/gt_positions.csv` with the
`clip_number`/`frame_index`/`hover_position_id`/`field_zone` columns filled and the coordinate columns
empty for the annotator to fill. Never overwrite rows that already carry coordinates.

Implement `measure_position_error(gt, tracks, config)`:
- transform each GT pixel foot point to yards with `transformer_for(hover_position_id)` — the SAME
  calibration the pipeline uses, so this isolates pipeline foot-point error from homography error
- match each GT point to the nearest pipeline track foot point in the same `(clip_number, frame_index)`
  within a maximum radius of 3 yards; unmatched GT points are counted as misses and reported as a
  match rate, never silently dropped (dropping them would report the error of only the easy cases)
- report `n_points`, `median_yards`, `p90_yards`, `max_yards`, the match rate, and a `per_zone` frame
  with the same statistics per `field_zone` — an error that is fine at midfield and bad in the far end
  zone is the finding, and an aggregate would hide it
- compute the known-distance check from the `scale_pair_id` rows: for each pair, the measured yard
  distance between the two transformed GT points versus `scale_true_yards`, reported as a signed error
  so a systematic scale bias is visible
- raise a named exception when fewer than 50 GT points carry coordinates — a position-error
  distribution from a handful of points is not a measurement

tests/test_cv_accuracy.py, math-only with `synthetic_tracks` and synthetic calibrations:
- each `load_gt_positions` validation rule raises the named exception naming the `gt_id`
- with GT points placed exactly on synthetic track foot points, `median_yards` is 0 and the match rate
  is 1.0
- a GT point offset by a known pixel distance yields the expected yard error under a known homography
- an unmatched GT point (beyond the radius) lowers the match rate and does not enter the distribution
- `per_zone` reports separate statistics and a zone with a deliberately larger offset shows a larger
  median
- the known-distance check returns the expected signed error for a synthetic pair
- fewer than 50 coordinate-carrying rows raises the named exception

  <how-to-verify>
This is the labelling budget D-10 explicitly bought. It measures how far off the pipeline's positions
are — the second C-09 criterion.

1. For each exported frame, mark the ground-contact point (the feet, where the player touches the
   turf) of every clearly visible player and official. Enter `foot_x_px`/`foot_y_px` from the labelled
   grid into the seeded rows, adding rows with new `gt_id` values (`c{clip}f{frame}p{n}`) as needed.
2. Mark the feet, not the body centre. The homography maps the ground plane; a body-centre mark
   introduces an error proportional to player height, which is the same order as the 1 m threshold
   being measured.
3. Set `class_name` and, where you can tell, `team_hint`.
4. Add at least 5 scale pairs: two marks whose true separation you can read off the field markings
   (for example both feet points on the same yard line, 10 yards apart, or a goal-line corner and the
   sideline mark 5 yards away). Give both rows the same `scale_pair_id` and the true separation in
   `scale_true_yards`. This is the independent "against known field dimensions" check from C-09.
5. Aim for at least 200 GT points spread across all five zones; the measurement refuses to run below
   50. More points in the far zones is more valuable than more points at midfield — the far end zone
   is where the error is expected to be worst.
6. Do NOT add training labels while you are in here. This is evaluation labelling, which D-10 allows;
   growing the training set is what D-06 forbids as an answer to a gate problem.
  </how-to-verify>
