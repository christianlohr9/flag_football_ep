# Phase 02.2 Plan 14: OTC OBS Delivery (Staged, Upload Deferred) Summary

**`deliver_bundle` implemented against an S3-compatible endpoint via `s3fs`, credential-safe and unit-tested without a live bucket; since OTC OBS credentials are not available in this environment, delivery is instead fully staged locally (hardlinked archives + SHA-256 manifest + German participant README) with a complete runbook (`docs/hackathon-otc-upload.md`) for the day credentials arrive.**

## Performance

- **Duration:** single session
- **Tasks:** 3/3 complete, with Task 2 executed as a user-directed deviation (see below) instead of the plan's original checkpoint:human-action
- **Files modified:** 5 (2 source, 1 test, 2 docs, 1 new doc)

## Accomplishments

- Implemented `deliver_bundle(config, archive, remote) -> str` in `cv/bundle.py`: resolves credentials by env-var name only (`config.secret`), builds the S3-compatible client with the configured `endpoint_url` (never the AWS default), uploads via `s3fs`, and verifies the remote object's size against the local file before returning the URI -- raises `BundleError` on any credential, upload, or size-mismatch failure, never leaking a credential value in any message
- Added `_build_s3_client` as the single monkeypatchable network seam (mirrors `cv.dataset._build_client`'s CVAT pattern), enabling 7 new delivery tests with zero network access: successful upload + size verification, endpoint/credential kwargs assertion, missing-env-var failure naming the variable, size-mismatch failure, missing-archive failure, upload-failure with no secret leakage and the two documented addressing/listobjects remedies, and object-key derivation from the archive's own `{kind}-set_...` filename prefix
- Implemented `stage_bundles_for_delivery(config, bundles_dir, out_dir, kinds=...)`: hardlinks each already-built archive into a dated staging directory, writes a `manifest.json` (per-archive size, full SHA-256, the bundle's own `content_sha256`, `detector_run_id`, planned object key) and a German `README.md`; re-checks the "test" kind's file listing against the four label/GT/homography filenames as staging-time defense-in-depth on top of `build_bundle`'s own leak guards
- Added `ffep cv stage-delivery` and ran it for real against the actual `data/bundles/` output: staged all three bundles (dev 2,252,756,132 bytes, test 2,665,778,520 bytes, transfer 553,798,247 bytes) into `data/processed/hackathon-delivery/2026-09-07/`, confirmed via `stat` that the staged files share the source archives' inode (zero duplicated disk for ~5.1 GB of content) and that the recorded `archive_sha256` values match an independent re-hash
- Wrote `docs/hackathon-otc-upload.md`: German runbook covering both upload paths (the project's own `ffep cv deliver` with the two env vars; the AWS-CLI/obsutil fallback against the configured OTC endpoint with path-style-addressing and `listobjects` remedies), post-upload verification (object listing against the staging manifest, `head-object` size/ETag check with the multipart-ETag caveat explained, an optional download-and-rehash spot check), and what to send participants afterward
- Extended `docs/hackathon-bundles.md` with an `## Auslieferung` section recording the staged-but-not-uploaded state, the concrete object-key scheme for all three bundles, and a pointer to the runbook

## Decisions Made

- **Deviation from the plan's Task 2 (checkpoint:human-action):** the plan called for pausing and handing the user OTC bucket/credential provisioning steps, then running one real upload. A mid-session user instruction stated the OTC credentials will not exist for a while and directed a fully-staged, non-blocking alternative instead: build the local staging directory, write the runbook for both upload paths, and prove staging is complete via a dry-run test -- all without requiring credentials now. This plan proceeds on that instruction; the original checkpoint's acceptance criteria (private-bucket confirmation, real upload URI) are deferred to whenever the user runs `docs/hackathon-otc-upload.md`'s commands, not abandoned.
- `deliver_bundle` re-raises `config.secret()`'s `ConfigError` as `BundleError` (`from None`) so every failure mode from this module surfaces as one error type, matching the plan's acceptance criterion ("A missing `OTC_OBS_ACCESS_KEY_ID` produces `BundleError` naming that variable").
- The staging manifest's `archive_sha256` (whole-ZIP-byte hash) is deliberately distinct from the pre-existing `content_sha256` (tree-content hash) already published per bundle -- both READMEs (staging and `hackathon-bundles.md`) state explicitly which one to use and why, to avoid a participant checking the wrong hash after download.
