## Summary

This phase does not start from zero — Phase 2.1 already built the entire CV pipeline (`sighting.py`, `frames.py`, `prelabel.py`, `dataset.py`, `detect.py`, `registry.py`, `track.py`, `teams.py`, `homography.py`, `overlay.py`, `radar.py`, `continuity.py`, `accuracy.py`, `benchmark.py`), a working CVAT-self-hosted correction UI, an MLflow store with champion-alias detector versioning, and a 304-frame single-domain COCO dataset with full content-hash traceability. Phase 2.2's job is almost entirely **orchestration and one new capability (DVC) layered on top**, not new infrastructure: sight the two never-piloted domains, propose and lock a mix, run two AL iterations reusing `prelabel.py`/`dataset.py`/`detect.py`, add DVC versioning around the existing `data/labels/` COCO layout, freeze a detector/detection snapshot for the hackathon bundles, and package everything for delivery via Open Telekom Cloud's S3-compatible OBS.

The two most consequential findings from this research are (1) **RF-DETR's newest large variants (XLarge, 2XLarge) ship under PML 1.0, not Apache-2.0** — this is a hard exclusion under the project's Apache-2.0-only policy (C-06/D-02), so any variant comparison must stay within Nano/Small/Medium/Large; and (2) **DVC changed ownership in November 2025** (lakeFS/Treeverse acquired it from Iterative.ai) — the PyPI package is unaffected (still `dvc`, still Apache-2.0, still installs via `pip`/`uv add`), but the canonical source repo is now `github.com/treeverse/dvc`, not `github.com/iterative/dvc`; anyone consulting older bookmarked docs/issues should expect this move.

**Primary recommendation:** Treat this phase as five sequential capability additions to the existing `cv/` subpackage — (1) sighting extension to sideline+broadcast, (2) a thin `cv/active_learning.py` module built from existing `detect.py` outputs (uncertainty + diversity scoring, no new detection infrastructure), (3) a `data/labels/` → DVC migration with an OTC-OBS-shaped remote config, (4) a frozen-snapshot/freeze-tag mechanism on top of the existing MLflow champion-alias pattern, and (5) a bundle-packaging CLI verb that reuses `export.py`/`overlay.py`/`radar.py` outputs. No component requires abandoning what 2.1 built.

### Pattern 1: Uncertainty + Diversity Frame Selection (build, don't import)

**What:** RF-DETR ships no active-learning tooling — confirmed via WebSearch/GitHub README review; its uncertainty output is limited to per-keypoint covariance for keypoint models, not a general detection-confidence-based selection API [CITED: github.com/roboflow/rf-detr, WebSearch 2026-08-31]. The AL loop must be assembled from primitives already in the codebase.

**When to use:** Both AL iterations (D-15/D-16).

**Practical construction** (informed by the academic literature on uncertainty+diversity hybrids — entropy/margin-based uncertainty, core-set/clustering-based diversity [CITED: arxiv.org/pdf/2503.16125 "Uncertainty Meets Diversity", arxiv.org/pdf/2605.10349 "Portable Active Learning for Object Detection" — MEDIUM confidence, general CV literature not RF-DETR-specific]):

```python
# Source: constructed from existing cv/detect.py DetectionBatch + supervision.Detections
# (no equivalent exists upstream; this is new code, not a verified library pattern)

def frame_uncertainty_score(detections: sv.Detections) -> float:
    """Low max-confidence detections and confidence values clustered near the
    threshold both signal model uncertainty. A frame with zero detections in
    a domain known to have players present is itself a strong uncertainty
    signal (possible domain-shift miss)."""
    if len(detections) == 0:
        return 1.0  # maximal uncertainty: model found nothing where it should
    conf = detections.confidence
    # margin-style: how close to the confidence threshold are the detections
    return float(np.mean(np.abs(conf - CONFIDENCE_THRESHOLD)))

def diversity_key(clip: ClipMeta) -> tuple:
    """Stratify AL selection across clip, hover_position/camera, and coarse
    field-zone bucket (from homography if available) so the pool doesn't
    collapse onto one easy scenario."""
    return (clip.domain, clip.session_id, clip.hover_position_id, clip.field_zone_bucket)
```

**Anti-pattern:** selecting purely by lowest confidence without a diversity constraint — this collapses onto one hard scenario (e.g., all frames from one clip's worst 3 seconds) and starves iteration 2 of new coverage. D-15 explicitly requires both signals.

### Pattern 2: DVC on top of the existing content-hash discipline

**What:** `dataset.py::dataset_hash()` already computes a `content_sha256` over `data/labels/.../corrected/` that MLflow training runs log as a parameter — this is functionally a manual, ad-hoc version pointer. DVC formalizes exactly this pattern: `dvc add <dir>` creates a `.dvc` file (containing an MD5-based hash + size) that git tracks, while the actual data lives in `.dvc/cache` and is pushed to a remote.

**When to use:** After each AL iteration's CVAT export lands in `data/labels/`, before training.

```bash
# Source: doc.dvc.org (official docs) — pip install / add and basic add+push flow
dvc remote add otc-obs s3://<bucket>/flag-football-datasets
dvc remote modify otc-obs endpointurl https://obs.eu-de.otc.t-systems.com
dvc remote modify otc-obs region eu-de
# credentials via env vars (AWS_ACCESS_KEY_ID/AWS_SECRET_ACCESS_KEY-equivalent OTC AK/SK),
# never committed — same secret() pattern as CVAT credentials in flag_football_ep.config

dvc add data/labels/2026-05-16_FRIENDLY-GER-vs-PANAMA-ROJO-DRONE/corrected
git add data/labels/2026-05-16_FRIENDLY-GER-vs-PANAMA-ROJO-DRONE/corrected.dvc
git commit -m "..."
dvc push
```

**Interaction with existing `content_sha256`:** DVC's own hash (MD5-based, in the `.dvc` file) and `dataset.py::dataset_hash()`'s SHA-256 serve different purposes and should both be kept — DVC's hash is for data movement/dedup, the project's own hash is what MLflow already logs and what training-run traceability (D-15/2.1) depends on. Do not replace one with the other; log both if convenient, but do not break the existing MLflow-parameter contract.

**Open question for the planner:** whether each AL iteration is its own DVC-tracked directory (`data/labels/al-iteration-1/`, `al-iteration-2/`) or a single growing directory with `dvc.yaml` pipeline stages tracking each addition as a new commit. CONTEXT.md explicitly delegates "exact DVC layout" to the planner. A single growing directory with one `.dvc` file re-added per iteration is simpler and matches the "one dataset, one detector across domains" framing (D-04) better than per-iteration silos — recommended, not mandated.

```python
# for train/val. Eval-clip freezing is the same idea one level up: freeze
# clip IDs into a manifest BEFORE the AL pool is drawn from the remainder.
FROZEN_EVAL_CLIPS = {
    "drone": [...],       # subset of the 61 pilot clips (or fresh drone game, see D-07)
    "sideline": [...],
    "broadcast": [...] if not deferred to transfer-only,
}
```

Per-domain inference settings (SAHI on/off, tiling resolution) must be decided from the sighting pass's apparent-player-px measurement — `sighting.py::recommend_inference_settings()` already exists and produced the drone-domain settings in 2.1; the same function should run against sideline/broadcast sighting output rather than a new bespoke decision path.

### Anti-Patterns to Avoid

- **Reporting pooled mAP across domains** — explicitly forbidden by C-05/D-04; every eval report must show per-domain numbers.
- **Treating RF-DETR-XLarge/2XLarge as a drop-in variant swap** — PML 1.0 license breaks C-06; if a variant comparison happens, it must stop at Large.
- **Re-running zero-shot Grounding-DINO prelabeling for AL iterations 2+** — 2.1 already trained a fine-tuned detector; AL iteration prelabeling should use that detector (`detect.py::load_detector`), which will be far more accurate on this domain than the zero-shot backend prelabel.py currently defaults to for cold-start. `prelabel.py` may need a new code path (or the AL loop calls `detect.py` directly and only reuses `prelabel.py`'s CVAT-import shaping, not its zero-shot backend selection).
- **Silently overwriting the frozen hackathon baseline** — D-05 requires the freeze to be an explicit, deliberate deliverable; AL retraining after the freeze point must write to a new MLflow run/alias, never mutate the frozen one.

## Common Pitfalls

### Pitfall 1: AL prelabeling with the wrong backend

**What goes wrong:** `prelabel.py` currently defaults to a zero-shot Grounding-DINO backend (`_load_transformers_backend`), which was the correct choice for the *cold-start* pilot (no fine-tuned detector existed yet). If AL-iteration prelabeling reuses this same code path unchanged, it throws away the fine-tuned detector's much higher accuracy on this exact domain, producing worse prelabels and more correction burden — defeating the purpose of "prelabel → mostly confirmation work" (D-17).
**Why it happens:** `prelabel.py` and `detect.py` are separate modules with separate purposes (2.1's cold-start vs. 2.1's post-training inference); nothing forces AL code to pick the right one.
**How to avoid:** AL iteration prelabeling must call `detect.py::load_detector()` + inference, not `prelabel.py`'s zero-shot backend. If `prelabel.py`'s CVAT-import shaping is reused, only its output-formatting logic should be reused, not its backend selection.
**Warning signs:** AL-iteration correction sessions take as long as the cold-start correction did, or per-domain mAP does not improve between iterations despite added labels.

### Pitfall 2: RF-DETR license trap on larger variants

**What goes wrong:** A size-comparison experiment (CONTEXT.md discretion, "size comparison is allowed if VRAM/inference budget permit") could tempt trying RF-DETR-XLarge or -2XLarge for a stronger baseline, especially since an AWS GPU instance might remove the 8 GB VRAM constraint.
**Why it happens:** The `rfdetr` package's newest variants ship under different license terms (PML 1.0) than the Small/Medium/Large/Nano tier (Apache 2.0) — this is a recent change from when RF-DETR only had Small; training data / muscle memory from "RF-DETR is Apache-2.0" is no longer categorically true for the whole model family.
**How to avoid:** Any variant comparison must stay within `{Nano, Small, Medium, Large}`. Treat this as a hard gate check before any `rfdetr_plus`/XL import, mirroring the existing `test_cv_dependencies.py::test_boxmot_absent_from_pyproject`-style automated guard from 2.1.
**Warning signs:** an import of `rfdetr_plus`, `RFDETRXLarge`, or `RFDETR2XLarge` anywhere in the codebase or a plan.

### Pitfall 3: DVC remote auth against OTC OBS untested in this environment

**What goes wrong:** `dvc-s3`'s `endpointurl` mechanism is documented as working with S3-compatible services generically (MinIO, DigitalOcean Spaces are the officially documented examples), and OTC's own `obs-s3` compatibility layer is real and documented by Open Telekom Cloud itself — but this specific combination (dvc-s3 client library ↔ OTC OBS server) has not been verified working end-to-end anywhere in this research (no test bucket, no credentials available in this session).
**Why it happens:** S3-compatibility layers vary in fidelity (path-style vs. virtual-hosted-style addressing, `ListObjectsV2` support, multipart upload quirks) — the DVC docs themselves warn "any other S3 parameter can also be set... though effectiveness depends on the specific platform."
**How to avoid:** Treat the first `dvc push` to the OTC OBS remote as a checkpoint-worthy validation step, not an assumed-working config. If it fails, `listobjects` (forcing the older `list_objects()` API) is the first thing to try per DVC's own Ceph/emulator guidance.
**Warning signs:** `dvc push` hangs, times out, or returns signature-mismatch errors (classic path-style vs. virtual-hosted-style addressing symptom).

### Pitfall 4: Assuming the pilot's 304 frames are clean enough to seed v0 without inspection

**What goes wrong:** CONTEXT.md flags this explicitly as a discretion item — the pilot dataset has a known, documented limitation: single annotator, no inter-annotator-agreement measurement, and a labeling-convention shift partway through (frames up to ~103 were polygon-annotated then converted to boxes, later frames direct rectangles), which already introduced a small, documented sub-pixel bounds artifact. Treating it as an unquestioned v0 seed risks propagating a labeling-convention inconsistency into the multi-domain dataset.
**Why it happens:** It is tempting to fold in "free" existing labels without a quality pass, especially under a metric-driven ("more labels only if mAP improves") mindset that discourages relabeling.
**How to avoid:** Spot-check a sample of the 304 frames against the labeling convention documented in `docs/cv-setup.md` (`## Datensatz` → "Labeling-Konvention") before folding them in as v0; the GT position set (`gt_positions.csv`) stays eval-only regardless (already locked, unrelated question).
**Warning signs:** per-domain mAP for the drone domain does not track with added AL-iteration labels the way sideline/broadcast domains do, suggesting a training-signal inconsistency traceable to the seed set.

### Pitfall 5: Hackathon "frozen baseline" silently drifting

**What goes wrong:** D-05 requires the hackathon bundles to pin an explicitly frozen detector/detection state; because AL retraining happens in the same phase (and the hackathon strand is sequenced first but not necessarily *finished* before AL work starts, per D-04's "conditional tasks must not block the phase"), there is a real risk that a later AL-trained detector's outputs get regenerated into the bundle directories without anyone deciding to do that.
**Why it happens:** `detect.py`'s existing CLI verbs (`train`, `promote`) don't inherently distinguish "this run is the hackathon-frozen one" from "this run is the next AL iteration" — that's a new semantic this phase must add.
**How to avoid:** Build the freeze as an explicit artifact (a tagged MLflow run alias like `hackathon-frozen`, distinct from the rolling `champion` alias `registry.py` already manages, plus a pinned `run_id` recorded in a versioned file that the bundle-builder reads) rather than "whatever `champion` currently resolves to."
**Warning signs:** bundle contents change between two runs of the bundle-builder without an explicit re-freeze step being invoked.
