**Gathered:** 2026-08-31
**Status:** Ready for planning

<domain>
## Phase Boundary

A versioned multi-domain detection dataset robust enough for regular use (REQ-S2-03): 1,500+ verified frames (metric-driven above the 1,500 floor, up to 3,000), drone + second domain (mix at researcher's discretion, ~60/40 is orientation only), built model-in-the-loop with 2 active-learning iterations on the fine-tuned RF-DETR from Phase 2.1, one detector trained across all domains with per-domain eval splits and per-domain inference settings (D-04), versioned with DVC, publication path prepared.

**Explicitly integrated into this phase (user decision):** the full BWI hackathon challenge preparation (23–27 Nov 2026, `docs/hackathon-challenge-reid.md`) — test-set preparation, benchmark labelling (~4 h plan), data bundles for the teams, submission prerequisites. The hackathon strand is **sequenced first** (deadline-driven); dataset buildout/AL iterations run behind it.

**Gate reconciliation (recorded decision):** Phase 2.2 starts now despite the TEILWEISE gate verdict (`docs/pilot-gate-decision.md`). Rationale: the dataset buildout addresses detection robustness (gate criterion 2, PASSED), not the track-continuity miss — D-06 ("clear miss → capture setup, never more training labels") is not violated because these labels are not a response to the continuity failure. The continuity remediation paths (steeper drone angle via capture-Wunschzettel update; appearance-based ReID via the hackathon) run in parallel through the gate's re-trigger clause.

Not this phase: ReID implementation (the hackathon IS the ReID attempt), the gate re-run (full 61-clip continuity review — own small step after the hackathon), snap detection and coaching metrics (2.3), player identity (2.4), broadcast tracking/field-keypoint models (2.5), any Strand-1 changes.

<decisions>
## Implementation Decisions

### Gate reconciliation & documentation
- **D-01 Start now, document the rationale.** The start-despite-TEILWEISE decision is recorded in three places, kept consistent in one commit: a short dated addendum to `docs/pilot-gate-decision.md` (consequences section: 2.2 released for detection robustness, continuity path untouched), plus adjusting the "only after passed pilot" wording in `.planning/ROADMAP.md` (Phase 2.2) and `.planning/REQUIREMENTS.md` (REQ-S2-03).
- **D-02 Gate re-run is NOT part of 2.2.** When a trigger fires (new steeper-angle session or working ReID from the hackathon), the re-run (re-track + full 61-clip continuity review) happens as its own small step after the hackathon. 2.2 ends with dataset + detector + hackathon assets.
- **D-03 Capture-Wunschzettel update, drone points only.** `docs/capture-protocol.md` gets an update carrying the three gate findings as wishes: steeper/more overhead hover angle, east endzone coverage (never reached in the pilot session), no in-clip camera cuts. No side-camera request for future events (user decision).

### Hackathon strand (integrated, sequenced first)
- **D-04 Hackathon prep is a plan strand of this phase** with full GSD rigor: test-set preparation, the challenge doc's labelling plan, data bundles, submission finalization. Conditional tasks (anything needing a second drone game) must not block the phase.
- **D-05 Frozen baseline for bundles.** The bundles ship detections + baseline tracks pinned to an explicitly frozen, versioned detector/detection state — AL retraining in this phase must not silently shift the benchmark. Freezing is a deliverable, not an accident.
- **D-06 Federation approval already granted** (user statement 2026-08-31: "die Anfrage ist positiv, wir haben alle Befugnisse") — covering hackathon use, distribution of the TV broadcast material, and publication. No request needs drafting; 2.2 documents the approval state (addendum in `docs/capture-legal.md` and the challenge doc's Datenschutz section). Record as a user assurance with date.
- **D-07 Private test set fallback:** if no second drone game arrives by November, ~15–20 of the 61 pilot clips (stratified over both hover positions) are withheld with their labels as the private test set and removed from the dev set. Coordinate with the frozen eval split (D-13) — the same clips can serve as private test + frozen eval.
- **D-08 Bundle delivery via Open Telekom Cloud.** Teams work on OTC; delivery expected via its S3-compatible object storage (OBS). Bundles are versioned, self-explanatory archives (data + eval scripts + README). The DVC remote may later point at the same OTC bucket.
- **D-09 Bundle documentation in German** (README, eval-script docs, metric descriptions) — consistent with the challenge doc and BWI context; code, identifiers, columns stay English as in the repo.

### Material & mix
- **D-10 Researcher sights first, then proposes the mix.** The sideline GoPro (60 clips, WM GER–MEX) and broadcast (51 TV clips, WM USA–AUS) material has never been through the pipeline. A sighting pass (2.1 style, against `docs/capture-protocol.md` tiers) precedes the mix decision. The researcher/planner sets the domain mix freely by metric benefit — 60/40 (D-03 project) is orientation, not a constraint (user explicitly granted full latitude).
- **D-11 Checkpoint on bad sideline material.** If sighting rates the sideline material (nearly) unusable for detection training, the phase STOPS with a checkpoint and the sighting findings; the user decides then (broadcast as replacement second domain vs. single-domain dataset).
- **D-12 Frame target is metric-driven.** 1,500 verified frames is the mandatory floor; beyond it, labelling continues only while per-domain mAP still clearly improves between AL iterations. No labelling for stockpile.

### Eval design
- **D-13 Frozen held-out eval clips per domain,** fixed up front, stable across all AL iterations and dataset versions; AL selects only from the remaining pool. Split discipline is clip-level (one game per domain makes game-level splits impossible; leakage rules per clip).
- **D-14 No hard metric gate for the phase.** Success = measurable per-domain mAP improvement over the pilot detector across the AL iterations, reported transparently (n, splits, both domains — statistical honesty conventions carry over). The real test remains the post-hackathon gate re-run.

### Labeling & active learning
- **D-15 AL selection = uncertainty + diversity.** Low-confidence/unstable detections mixed with diversity sampling across clips, field zones, game phases.
- **D-16 Labeling budget: ~1 weekend per AL iteration** — two concentrated blocks giving the planner clear wave boundaries.
- **D-17 100% human verification.** Every dataset frame is sighted and corrected/confirmed by the user in the annotation tool — the honest reading of "verified frames". Prelabels from the fine-tuned RF-DETR make this mostly confirmation work.

### Versioning, publication, compute
- **D-18 DVC for dataset versioning** — local-first like the rest of the repo (MLflow, uv, gitignored data). COCO exports for hackathon bundles and later publication fall out of it.
- **D-19 Publish after the hackathon.** 2.2 assesses and prepares (license choice, structure, docs); actual publication of the "first public flag-football detection dataset" happens after the hackathon — stronger package (dataset + benchmark), no conflict with the private test set.
- **D-20 Publish full frames** (no blurring/crops-only) — maximum research value including ReID, covered by the federation approval. License choice (e.g. CC BY-NC) at Claude's discretion within the publication assessment.
- **D-21 Compute: local 2.1 setup is the guaranteed base** (Dell 8 GB CUDA for training, M5 Max 128 GB for everything else). A possible AWS GPU instance is an optional accelerator — keep the training setup machine-portable; no plan may depend on AWS materializing.

### Claude's Discretion
- Hard-case handling: mining strategy from existing material (congestion, occlusion, shadows, blitz plays) and whether weather/light augmentation joins the training recipe — researcher/planner decide after sighting; missing conditions are documented as dataset gaps.
- Whether the ~500 pilot labels seed the dataset as v0 — researcher checks label quality/consistency first; the GT positions set stays strictly eval-only either way.
- Labeling tool: CVAT+SAM2 (proven in 2.1) is the default; planner confirms in light of the DVC choice — switch only for a clear speed/integration win.
- RF-DETR variant: Small stays default; a size comparison is allowed if VRAM (8 GB Dell / AWS) and the C-09 inference budget (< 1 h/game on M5 Max) permit.
- Registry & recipe details fully delegated: one detector across domains (D-04) → one champion alias; MLflow logging + dataset-hash linkage as in 2.1; nothing silently overwritten. AL-iteration MLflow structure, hyperparameters, exact DVC layout, bundle archive format, eval-script packaging.

</decisions>
