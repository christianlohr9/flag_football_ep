# Phase 02.2 Plan 11: Iteration-1 Active-Learning Selection, Prelabel & CVAT Hand-off Summary

## Decisions Made

- `select_al_frames` invoked once per domain/session with that domain's own iteration-1 target, not a single multi-domain call with `target=750` -- the plan's own `<interfaces>` block requires this ("once per in-scope session with the per-domain target"), and the code confirms why: `select_al_frames`'s proportional diversity allocation has no notion of `docs/dataset-plan.md`'s fixed domain-mix percentages, only per-session calls can pin a domain's exact share.
- `selection_to_frame_manifest` fixes every AL frame's `split` field to `"train"` -- active-learning iterations only ever add new labelling material; the held-out validation role belongs exclusively to the already-frozen eval split.
- `cvat-push --max-images`'s task-naming always appends `-<index>` once the flag is given, even when a domain's target fits under the cap in a single chunk (sideline, broadcast) -- keeps task-naming uniform across every domain and every future iteration regardless of how the per-domain target happens to compare to the 300-frame cap.
- The AL-selection seed (`20260516`) reuses the frozen eval-split's seed for traceability, not because `select_al_frames` requires seed consistency across contracts -- any integer seed is valid and independent.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] `active_learning.py`'s selection manifest had no bridge to the `FrameSampleManifest` format `prelabel_frames`/`validate_coco` require**
- **Found during:** Task 1, before the first `ffep cv prelabel` invocation could even be attempted
- **Issue:** `select_al_frames` (frozen contract, plan 02.2-05/09) persists `ALSelection` to `selection_manifest.json` (`session_ids: list[str]`, no `split`/`clip_path` fields). `prelabel_frames` (frozen contract, plan 02.2-05) reads `frames_dir / "manifest.json"` in `frames.FrameSampleManifest`'s shape (`session_id: str`, `split: dict[int, str]`, `clip_path` per frame). The two plans that separately froze these two contracts never accounted for each other's shape -- without an adapter, an AL selection's extracted frames were structurally unreachable by the existing prelabel/dataset pipeline, blocking Task 2 entirely.
- **Fix:** Added `active_learning.py::selection_to_frame_manifest(config, selection)` (new function, not a frozen-contract signature) and wired it into `commands.py`'s `active-learn` CLI command to write `<out_dir>/manifest.json` automatically right after `select_al_frames` returns, using `frames.write_manifest`.
- **Files modified:** `src/flag_football_ep/cv/active_learning.py`, `src/flag_football_ep/cv/commands.py`, `tests/test_cv_active_learning.py`
- **Verification:** 2 new tests (`test_selection_to_frame_manifest_bridges_to_frame_sample_manifest`, `test_selection_to_frame_manifest_rejects_multi_session_selection`); real end-to-end check against all three domains' actual `manifest.json` output (`session_id`/`seed`/`target`/frame count/`split` all correct)
- **Committed in:** `6f2d785` (Task 1 commit)

**2. [Rule 3 - Blocking] `ffep cv prelabel`'s CLI never exposed the `backend` parameter `prelabel_frames` already accepted**
- **Found during:** Task 2, attempting `ffep cv prelabel --backend finetuned` per the plan's `<interfaces>` block
- **Issue:** Plan 02.2-09's `prelabel_frames(config, frames_dir, out_dir, *, force=False, backend=None)` already supported forcing the `finetuned` backend, but `cv/commands.py`'s `prelabel` typer command (last touched by plan 02.1-07, before the `backend` parameter existed) never grew a `--backend` option -- the CLI usage the plan's `<interfaces>` block states as "existing after plans 02.2-05/09" did not actually exist.
- **Fix:** Added a `--backend` typer option (default `None`, preserving prior zero-shot-fallback-chain behavior exactly), passed straight through to `prelabel_frames(..., backend=backend)`.
- **Files modified:** `src/flag_football_ep/cv/commands.py`
- **Verification:** `uv run ffep cv prelabel --help` shows the option; real invocation confirms `backend=finetuned` in the run log for all three domains, never a `transformers`/Grounding-DINO backend line
- **Committed in:** `ecdee8a` (Task 2 commit)

**3. [Rule 3 - Blocking] `ffep cv cvat-push` had no way to cap task size, but the plan requires ≤300 frames per task**
- **Found during:** Task 2, before pushing the 450-frame drone prelabel package
- **Issue:** `create_cvat_task` (frozen contract) always pushes exactly the directory it's given as a single CVAT task, with no chunking. The plan's own acceptance criterion ("Every CVAT task created holds at most 300 frames") and Phase-2.1 precedent (a single 404-frame task exceeded one sitting) both require splitting, but no splitting utility existed anywhere in the codebase.
- **Fix:** Added `dataset.py::split_coco_for_task_upload(coco_dir, out_root, *, max_images)` (new function, not a frozen-contract signature) -- slices the COCO package's `images`/`annotations` into contiguous `<= max_images`-sized chunks, each a self-contained hardlinked directory. Wired a `--max-images` option into `cvat-push` that, when given, splits first and pushes each chunk as `<name>-<index>`.
- **Files modified:** `src/flag_football_ep/cv/dataset.py`, `src/flag_football_ep/cv/commands.py`, `tests/test_cv_dataset.py`
- **Verification:** 3 new tests (`test_split_coco_for_task_upload_caps_every_chunk_at_max_images`, `_single_chunk_when_already_under_max`, `_preserves_categories`); real invocation split drone's 450 frames into 300+150, confirmed via `GET /api/tasks` on the live CVAT instance
- **Committed in:** `ecdee8a` (Task 2 commit)
