# Phase 02.2 Ad-hoc Diagnosis: Iteration-1 Drone Regression Root Cause Summary (Revised)

**Three ablation runs on the verified held-out eval ground truth show the originally reported drone gap between the champion and iteration-1 was mostly (67-78%, depending on metric) a measurement artifact: the champion's own pilot training set overlapped 88+25 frames with the same 18 clips the eval ground truth was later sampled from. A clean-champion ablation (D, leaked clips fully removed) scores 0.9030/0.7847 instead of the original 0.9550/0.9423 -- but a smaller, genuinely held-out residual gap (~0.015 mAP_50, ~0.077 mAP_50_95) still remains against iteration-1, best explained by AL-1's per-clip frame density rather than the val split or multi-domain mix (both already ruled out).**

## Accomplishments

### Round 1: cheap hypotheses + ablations A/B

- **Cheap hypotheses checked and ruled out/confirmed without GPU:**
  - Manifest/frames actually trained on by `be854a1a…` confirmed correct: `dataset_content_sha256` param matches dataset v1.2's own hash exactly, and the run started after the `_resolve_manifest_path` fix (commit `53ba641`) — the stale-pilot-manifest bug does not explain the gap.
  - No labelling-convention drift between the pilot's corrected dataset and the AL-1 corrections: box statistics (boxes/image, referee share, box area/w/h) are nearly identical.
  - Frame-density-per-clip comparison surfaced a real structural difference: champion trained on 322 frames across 46 clips (median 7/clip); v1.2 drone draws 450 frames from only 43 pool clips (median 12/clip, at `_MAX_CANDIDATES_PER_CLIP`'s cap of 12).
- **Minimal code addition:** `train_detector` gained an `init_weights: Path | None` parameter (`RFDETRSmall(pretrain_weights=...)`), a CLI `--init-weights` flag, and a regression test — committed `94f0572`.
- **Ablation A** (drone-only 450-frame subset of v1.2, seeded clip-level 10% val split): run `702ab0b5baaf422fa0c21e3988daa4a4`. Held-out drone: `mAP_50 0.8884`, `mAP_50_95 0.7076` — within noise of iteration-1's `0.8881`/`0.7073`, falsifying candidates 1 (no val split) and 2 (multi-domain mix).
- **Ablation B** (v1.2 full, initialized from the champion's `checkpoint_best_total.pth` via `init_weights`): run `689d5f1dc2c2450785be0f1a1bac9491`. Held-out drone: `mAP_50 0.8926`, `mAP_50_95 0.7283` — a small, real improvement, far short of closing the gap.
- Initial conclusion (before coordinator review): frame density/diversity per clip was the dominant explanation. **This was incomplete** — see round 2.

### Round 2: coordinator review + ablation D (the corrected, honest conclusion)

- **Coordinator's critique (correct):** the champion's own frozen-eval comparison number was never a clean held-out measurement either. Its pilot training set drew 88 train + 25 val frames from the exact 18 clips the drone eval ground truth was later sampled from (different frame indices of the same clips — near-duplicates of what the champion trained on). v1.2/ablation A/ablation B contain none of those 18 clips. Combined with the already-documented prelabel bias (95% of the champion's own verified drone GT boxes are unchanged copies of its own prelabels), this could explain the entire drone gap without any frame-density effect at all.
- **Ablation D — "clean champion":** the champion's exact pilot recipe (corrected pilot dataset, 30 epochs, 896px, batch 4, grad-accum 4, MPS, the champion's own clip-level split assignments preserved unchanged for surviving clips), with every frame from the 18 frozen drone eval clips removed from train and val. Actual removal: 76 of 304 corrected images (not the ~291/43-clip estimate from manifest-sample-level counting before correction-filtering) — leaving **228 images, 33 clips**, split 181 train / 47 val (20.6%), verified 0 overlap with the frozen eval clips via `assert_no_frozen_eval_clips`.
  - 228 images falls below `dataset.validate_coco`'s default `_MIN_IMAGES=250` floor — resolved by monkeypatching `dataset._MIN_IMAGES = 200` for this one diagnostic training invocation (the mechanism `dataset.py`'s own docstring documents this constant being resolved for), not a `train_detector` signature change.
  - First training attempt crashed with a `RuntimeError` from PyTorch's DataLoader workers — a real bug in the disposable launcher script (missing `if __name__ == "__main__":` guard, causing macOS "spawn" multiprocessing to recursively re-invoke the top-level training call in each worker). Fixed and re-run cleanly.
  - MLflow run `a6d53662e6fa4df88d10debd1551de6b`, `checkpoint_source = best_total` (real val split, real best-checkpoint selection — same as the champion). Registered as `cv_detector_model` version 5.
- **Held-out result:** drone `mAP_50 0.9030`, `mAP_50_95 0.7847` — a substantial drop from the original leaky champion's `0.9550`/`0.9423`, but still above iteration-1 (`0.8881`/`0.7073`) and ablation A (`0.8884`/`0.7076`).
- **Frame-density comparison, D vs. v1.2-drone:** D (228 images, 33 clips, median 7/clip, min 3, max 12) preserves the full pilot's original density profile almost unchanged (the full 304-image pilot: median 7/clip) — only the 18 eval clips are missing. v1.2-drone (450 images, 43 clips, median 12/clip, near the cap) remains far denser per clip. The density contrast persists independent of the leakage question.
- **The honest accounting:** of the original drone gap (`Δ 0.0669 mAP_50` / `0.2350 mAP_50_95`), ablation D closes **77.7% of the `mAP_50` gap and 67.1% of the `mAP_50_95` gap** — leakage plus prelabel bias is the majority explanation, not a minor caveat. A real residual gap remains: D (`0.9030`/`0.7847`) still exceeds iteration-1 and ablation A by `~0.0149 mAP_50` / `~0.0774 mAP_50_95` (`22.3%`/`32.9%` of the original gap). Since ablation A already ruled out the missing val split and the multi-domain mix as explanations for a gap of this shape, and D uses the same real val-split mechanism as the champion without closing this smaller residual, frame density/diversity per clip remains the most plausible explanation for what is left — just a substantially smaller effect than the pre-coordinator-review conclusion implied.
- **Sideline data point (not resolved further):** D's zero-shot GoPro/Hinterfeld transfer (`mAP_50 0.6255`, `mAP_50_95 0.5264`) is weaker even than the original leaky champion's zero-shot transfer (`0.7971`/`0.7813`) — plausibly just the smaller training set (228 vs. 304 images) but not investigated further within this diagnosis's scope.

## Decisions Made

- Ran 3 ablation runs total: 2 of the objective's originally-allowed 3 (A, B), plus a 4th (D) added specifically in response to the coordinator's leakage critique — a distinct question from the original 4 candidates, not a retry of the same budget.
- Ablation A's val-split seed (`20260905`) is deliberately new, not the project's `20260516` sampling/eval-freeze seed.
- Ablation D preserves the champion's own clip-level split assignments for surviving clips unchanged (read directly from the pilot manifest), rather than re-deriving a new split for the reduced 33-clip pool — this is what "same split logic" means: reusing the champion's actual computed split, not re-running the split algorithm on a different clip count.
- `dataset._MIN_IMAGES` was monkeypatched (250 → 200) for ablation D's single training invocation via a standalone script, not by widening `train_detector`'s public signature — `dataset.py`'s docstring documents this constant being resolved from the module attribute at call time specifically to support this pattern; 228 images falling below the champion's original 304-image floor is an unavoidable, honestly-reported consequence of a leakage-free ablation on this small a pilot set, not something to paper over with a lower permanent floor.
- Implemented `init_weights` as a minimal, tested addition to `train_detector`/`ffep cv train` rather than overloading `--resume` (round 1 decision, unchanged by the round-2 revision).
- Did not run a sideline-only ablation for D — its weaker-than-champion zero-shot GoPro/Hinterfeld transfer is flagged as an open, unexplained data point rather than chased further within this diagnosis's scope.

## Deviations from Plan

**1. [Rule 1 - Bug] Ablation D's training launcher script crashed on first attempt from a missing multiprocessing guard**
- **Found during:** first `python data/reports/tmp_run_ablation_d.py` invocation (a disposable diagnostic script, not committed to the repository)
- **Issue:** the script called `train_detector(...)` directly at module top level with no `if __name__ == "__main__":` guard. PyTorch's DataLoader workers use macOS's "spawn" multiprocessing start method, which re-imports the launcher file as `__main__` in each worker process — without the guard, each worker re-executed the top-level `train_detector(...)` call itself, cascading into a `RuntimeError: Please call iter(combined_loader) first.` deep inside PyTorch Lightning's fit-loop teardown.
- **Fix:** wrapped the training call in `if __name__ == "__main__":` and re-ran cleanly.
- **Files modified:** none in the repository (the launcher script was disposable diagnostic scaffolding, deleted after use, never committed)
- **Verification:** re-run completed successfully end-to-end (30 epochs, real per-epoch val metrics table, registered MLflow run `a6d53662e6fa4df88d10debd1551de6b`)
- **Committed in:** n/a (the fixed script was never committed; only its output — the training run and eval report — is)
