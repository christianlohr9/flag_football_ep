  <behavior>
    - `freeze(name, run_id, config)` sets `FROZEN_ALIAS` on the model version produced by `run_id` and returns that version
    - `freeze` on an unknown run id raises `RegistryError` naming the run id; a bare `MlflowException` never escapes
    - `resolve_frozen(name, config)` returns the pinned run id and is unaffected by a subsequent `promote()` of a different run
    - `write_freeze_pin` writes `{run_id, dataset_hash, model_version, frozen_at}` atomically; `read_freeze_pin` round-trips it and raises a named error on a missing key
    - Freezing twice with a different run id raises unless an explicit `force` path is used — a re-freeze is a decision, not a retry
  </behavior>
  <action>
    Implement `cv/freeze.py` against the frozen contract, mirroring `registry.py::promote`
    structurally: validate the model name and run id with the existing validators, call
    `mlflow_store.configure(config)` before constructing `MlflowClient()`, search model versions by
    `run_id`, filter to the requested model name, call `set_registered_model_alias(name,
    FROZEN_ALIAS, version)`, and wrap every `MlflowException` in `FreezeError` with a message naming
    the model, alias and run id. `resolve_frozen` mirrors `resolve_champion` against `FROZEN_ALIAS`.

    `write_freeze_pin`/`read_freeze_pin` use the `frames.py::write_manifest` idiom verbatim in
    spirit: `json.dumps(..., indent=2, sort_keys=True)` to a `.tmp` sibling, `os.replace`, and an
    explicit required-key check on read. Add a `force: bool = False` keyword to the freeze CLI path
    only (the module-level `freeze` signature stays as contracted); the refusal to silently re-pin
    lives in `write_freeze_pin`, which raises `FreezeError` when the target file exists with a
    different `run_id`.

    Write tests/test_cv_freeze.py using the `_make_config` fixture pattern: register two dummy
    model versions in a tmp SQLite MLflow store, freeze the first, promote the second, and assert
