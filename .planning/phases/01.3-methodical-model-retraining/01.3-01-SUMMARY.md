# Phase 1.3 Plan 01: MLflow SQLite Store Migration Summary

**Migrated the MLflow tracking store from the deprecated `file:` FileStore to a SQLite-backed store behind one shared `mlflow_store` module, and rewrote all 16 FileStore-layout-dependent tests to use it.**

## Performance

- **Duration:** 45 min
- **Started:** 2026-08-19T05:35:00Z (approx)
- **Completed:** 2026-08-19T06:20:51Z
- **Tasks:** 3
- **Files modified:** 6 (1 created, 5 modified)

## Accomplishments

- `src/flag_football_ep/model/mlflow_store.py`: single source of truth for the tracking URI (`sqlite:///{mlruns}/mlflow.db`), artifact root (`file://{mlruns}/artifacts`), store configuration, and idempotent experiment creation/reuse.
- `train.py`/`score.py` no longer set `MLFLOW_ALLOW_FILE_STORE` or construct a `file:` tracking URI directly; both route through `mlflow_store`.
- `tests/test_model_train.py` and `tests/test_model_score.py` fully migrated off the FileStore's on-disk run-directory layout; `_run_dirs` deleted; a new test asserts the sqlite file exists and no `params/` directory remains anywhere under `mlruns`.
- `docs/pipeline.md` section 7 rewritten to describe the SQLite store, the artifact root, and the `mlflow ui --backend-store-uri sqlite:///...` command.
- Fixed a latent `config.py` bug where `Config.paths` entries stayed relative to the invoking shell's cwd whenever `--config` was passed as a relative path, contradicting the module's own docstring guarantee.

## Decisions Made

- Kept `mlflow_store`'s four functions as the plan specified (`tracking_uri`, `artifact_location`, `configure`, `ensure_experiment`) with no additional public surface, so future registry-touching modules (01.3-03 onward) have exactly one obvious entry point.
- `_log_run`'s exception handling: `mlflow.create_experiment` failures are re-raised as `MlflowStoreError` naming both the experiment name and the tracking URI, following the codebase's named-exception convention (RESEARCH/PATTERNS "Named-exception, no-silent-failure error handling").

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Fixed `config.py`'s relative-path resolution of `Config.paths`**
- **Found during:** Task 1 (verifying the acceptance criterion that `mlflow_store.tracking_uri(load_config())` prints a string starting with `sqlite:////` and ending with `/mlruns/mlflow.db`)
- **Issue:** `load_config`'s docstring promises "Path attributes are resolved relative to `path`'s parent directory (not the process working directory), so behavior is the same regardless of where `ffep` is invoked from." In practice, `base_dir = path.parent` on the default relative `Path("ffep.toml")` produced `Path(".")`, so every `Config.paths` entry (including `mlruns`) stayed relative to the shell's cwd -- directly contradicting the docstring and this plan's `<interfaces>` note that `Config.paths.mlruns` is "resolved absolute". This is out of Task 1's `<files>` list but directly blocked its acceptance criteria.
- **Fix:** Changed `base_dir = path.parent` to `base_dir = path.resolve().parent` in `load_config`.
- **Files modified:** `src/flag_football_ep/config.py`
- **Verification:** `.venv/bin/python -c "..."` now prints `sqlite:////Users/.../mlruns/mlflow.db`; full `tests/test_config.py` (11 tests) still passes; full `pytest -q` suite passes.
- **Committed in:** `1ebdc0a` (part of Task 1 commit)
