## User Constraints (from CONTEXT.md)

### Locked Decisions

**Grouped-CV protocol**
- Evaluation scheme: Leave-one-game-out (LOGO) over `game_id` — every game is held out once; all reported metrics come from these held-out predictions. This is the maximal form of REQ-S1-07/D-07 (user chose it over GroupKFold K=5 knowing the ~50+ fits cost).
- Tuning: Hyperopt scores each trial on a cheap grouped inner CV (e.g. GroupKFold K=5 over games); the winning params are then evaluated once with the full LOGO loop. No play-level leakage anywhere in tuning; no fully-nested LOGO×trials explosion.
- Shipped model: LOGO is measurement only. The production model is refit once on all games with the tuned params — one artifact.
- Out-of-fold EPA: The LOGO held-out predictions are persisted; `ffep score` uses each historical play's out-of-fold EP/WP (nflfastR precedent) so own-team EPA in 1.4 is not flattered by in-sample predictions. New/unseen games are scored with the refit model.

**Calibration & training report**
- Naive baseline: Class-frequency baseline — predict the marginal outcome distribution (training-data class rates) for every play; report model log-loss against it.
- Report form: MLflow run artifacts — reliability-curve PNGs per class + metrics table logged to the training run, browsable in the MLflow UI. No separate standalone report file required.
- Miscalibration policy: Report only. No isotonic/Platt layer in this phase; if curves look bad, calibration correction becomes an explicit follow-up decision.
- Per-source breakdown: LOGO metrics and reliability curves are reported per source/competition (legacy Hudl, new Hudl, sportapp, IFAF WM-2026) alongside pooled numbers — this is how the folded IFAF-benchmarking todo is realized. IFAF games train like any other source (no external holdout).

**Feature re-tests & training-data mix**
- Training pool: Pool everything — all four sources train the production models. The per-source breakdown guards against a source hurting; competition level enters as a tested covariate.
- Real `half_seconds_remaining`: IFAF-only sub-experiment — one documented WP experiment on IFAF games comparing real `game_clock_ms`-derived time vs the synthetic construction on the same games. Quantifies what synthetic time costs; the production feature set stays synthetic until Hudl delivers real time (REQ-S1-02 outcome).
- Adoption criterion: A feature candidate is adopted when mean pooled LOGO log-loss improves over the current feature set. Every candidate experiment is logged in MLflow with its verdict (satisfies REQ-S1-09 "documented outcomes").
- Recency weighting: Exponential decay by game date (half-life tuned as part of the experiment); on EP it multiplies with the existing `Total_W_Scaled` weight.
- Competition covariate: Categorical competition tier from a small maintained tier vocabulary in reference data (e.g. womens-international / womens-national / mixed-other), one-hot encoded. Not source-as-proxy.
- Existing EP weighting: `Total_W_Scaled` (drive-score-distance × score-differential, nflfastR-style) stays as an untouched given — not re-tested.

**PAT baselines & model versioning**
- PAT estimation: Pooled overall success rate per PAT type (1-pt, 2-pt) over the whole dataset, replacing `PAT_BASELINE_ONE_POINT = 0.5` / 46% constants in `features/mutations.py`; attempt counts and confidence intervals reported alongside.
- Versioning (REQ-S1-11): MLflow model registry is primary — registered model per EP/WP, the source of truth consumers resolve against. The dated + training-data-hash `.pkl` export from 1.2 is kept (satisfies the requirement's literal filename wording; offline use).
- Promotion: Registry champion alias per model with an explicit `ffep promote` step, used after reviewing the training report. `ffep score` resolves the champion alias — it never silently follows the latest run (changes today's latest-FINISHED-run behavior in `model/score.py`).

## Summary

Phase 1.3 is a methodology change to two already-working training pipelines (`train_ep`, `train_wp` in `src/flag_football_ep/model/train.py`), not a new system. Everything needed is already an installed dependency (`scikit-learn` 1.5.1, `xgboost` 2.1.1, `mlflow` 3.15.1, `hyperopt` 0.2.7, `scipy` 1.14.1 transitively via scikit-learn) — **no new third-party packages are required**. The two pieces of real technical risk are (1) replacing the single `train_test_split` with a Leave-One-Group-Out (LOGO) loop over `game_id` cheaply enough to run ~50+ XGBoost fits per model per training invocation, and (2) making the MLflow **model registry** actually work, which the current codebase cannot do today because it points `mlflow.set_tracking_uri` at a `file:` store — **the MLflow model registry requires a database-backed tracking store; it does not work against a plain `file:` store** [VERIFIED: mlflow.org docs, cross-checked against installed mlflow 3.15.1 by running register/alias/load end-to-end locally]. This is fixable with zero new dependencies: point the tracking URI at a local SQLite file (`sqlite:///...`) instead of `file:...`; this was verified in this session to support `register_model`, `set_registered_model_alias`, `get_model_version_by_alias`, and `models:/name@alias` loading — all in-process, with no `mlflow server` process required.

`sklearn.model_selection.LeaveOneGroupOut` and `GroupKFold` are both stdlib-equivalent (already-installed scikit-learn) primitives that do exactly what D-07/CONTEXT ask for: no game's plays ever appear in both a fold's train and test partitions. `sklearn.calibration.calibration_curve` (binary signature, already installed) is the correct primitive for the per-class reliability curves — for the 5-class EP model this means computing one one-vs-rest curve per class, exactly as CONTEXT's "reliability curves per class" describes; no multiclass calibration library is needed because CONTEXT explicitly defers any calibration *correction* to a future phase (report only).

The single biggest pitfall this research surfaces beyond what's in CONTEXT: **switching the tracking store from `file:` to `sqlite:` changes MLflow's on-disk layout**, and the existing test suite (`tests/test_model_train.py::_run_dirs`) walks the FileStore's `mlruns/<exp>/<run>/params/*` directory structure directly — that directory layout will not exist once runs are logged against a SQLite backend (run metadata moves into the `.db` file; only artifacts stay on disk). Any plan for this phase must budget a test-suite update alongside the registry migration, not just new tests for new behavior.

**Primary recommendation:** Do the registry migration first (tracking URI → `sqlite:///{config.paths.mlruns}/mlflow.db`, artifact root kept under `config.paths.mlruns` via an explicit `artifact_location` on `create_experiment`), because every other task (LOGO evaluation logging, per-source breakdown, PAT chart) hangs artifacts and metrics off the same `_log_run` contract that migration touches.

### Pattern 1: Leave-One-Group-Out evaluation loop
**What:** For each unique `game_id`, fit on all other games, predict on the held-out game, accumulate out-of-fold predictions; aggregate metrics only after the loop completes.
**When to use:** Any time metrics must reflect "how well does this generalize to a game the model has never seen," which is the entire point of REQ-S1-07/D-07.
**Example:**
```python
# Source: scikit-learn docs (sklearn.model_selection.LeaveOneGroupOut), verified against
# installed scikit-learn==1.5.1 in this session.
from sklearn.model_selection import LeaveOneGroupOut
import numpy as np

logo = LeaveOneGroupOut()
groups = model_data["game_id"].to_numpy()
X = model_data.select(features).to_numpy()
y = model_data.select("label").to_numpy().ravel()

oof_pred = np.full((len(y), num_class), np.nan)
for train_idx, test_idx in logo.split(X, y, groups=groups):
    model = xgb.XGBRegressor(**fit_params)
    model.fit(X[train_idx], y[train_idx], sample_weight=weight[train_idx] if weight is not None else None)
    oof_pred[test_idx] = model.predict(X[test_idx])
```
Note: `logo.get_n_splits(groups=groups)` returns the exact fit count (== number of unique games) before running the loop — use it to log an expected-runtime estimate/progress bar, since CONTEXT explicitly leaves runtime engineering (parallelization, caching) to the planner's discretion.

### Pattern 3: Naive class-frequency baseline log-loss
**What:** Predict the training-data marginal class distribution for every row; compute `log_loss` against it as the floor the model must beat.
**When to use:** REQ-S1-08's "log-loss against a naive baseline."
**Example:**
```python
# Source: sklearn.metrics.log_loss signature verified against installed
# scikit-learn==1.5.1: (y_true, y_pred, *, normalize=True, sample_weight=None, labels=None).
import numpy as np
from sklearn.metrics import log_loss

class_freqs = np.bincount(train_y, minlength=num_class) / len(train_y)
naive_pred = np.tile(class_freqs, (len(test_y), 1))
naive_log_loss = log_loss(test_y, naive_pred, labels=list(range(num_class)))
```
For WP (binary), the naive baseline is simply the marginal win rate (e.g. ~0.5 if home/away is balanced, but compute it — do not assume 0.5).

### Pattern 4: MLflow registry against a local SQLite tracking URI (no server)
**What:** Point the tracking URI at a SQLite file instead of `file:`, which unlocks `register_model`/alias APIs in-process.
**When to use:** REQ-S1-11's "MLflow model registry is primary" decision.
**Example (empirically verified end-to-end in this session, exit code 0, all assertions passed):**
```python
import mlflow
from mlflow import MlflowClient

mlflow.set_tracking_uri("sqlite:///" + str(config.paths.mlruns / "mlflow.db"))
mlflow.set_experiment(experiment)  # or create_experiment(..., artifact_location=...) once, then set_experiment

with mlflow.start_run() as run:
    mlflow.log_params(params)
    mlflow.log_metric(metric_name, metric_value)
    mlflow.xgboost.log_model(model, name="model", registered_model_name="ep_model")

client = MlflowClient()
versions = client.search_model_versions("name='ep_model'")
latest_version = versions[0].version
client.set_registered_model_alias("ep_model", "champion", latest_version)

# Later, from ffep score:
mv = client.get_model_version_by_alias("ep_model", "champion")
model = mlflow.xgboost.load_model(f"models:/ep_model@champion")
```
**Confirmed in this session:** this pattern works with zero `mlflow server` process — `register_model`, `search_model_versions`, `set_registered_model_alias`, `get_model_version_by_alias`, and `models:/name@alias` loading all succeeded against a bare `sqlite:///...` tracking URI in a throwaway `/tmp` sandbox.
**Also confirmed:** `mlflow.create_experiment(name, artifact_location="file:///abs/path")` lets you keep artifacts under the existing `config.paths.mlruns` directory even though run *metadata* now lives in the `.db` file — so the "local mlruns/ foundation" decision from Phase 1.2 is preserved for artifacts, only the metadata backend changes.

### Anti-Patterns to Avoid
- **Nested LOGO-inside-hyperopt-trials:** CONTEXT already forbids this (fit-count explosion: 50+ games × up to 100 trials). Tuning must score against a cheap GroupKFold(K≈5) inner loop; LOGO runs exactly once, after tuning, to produce the reported/measurement metrics.
- **`file:` tracking URI + expecting registry calls to work:** `mlflow.register_model(...)` / `MlflowClient().create_registered_model(...)` will raise against a `file:` store — this is a hard MLflow limitation, not a bug to work around with retries or different call patterns.
- **Computing `Drive_Score_Dist_W`/`ScoreDiff_W`-style weights inside a LOGO fold:** `make_ep_model_mutations` already guards this with `DegenerateWeightRange` (module docstring, "must be computed on the full training corpus, never per game or on any subset with no variation"). The LOGO loop must **fit models on pre-computed weight columns**, not recompute `make_ep_model_mutations` per fold — recomputing per-fold on an 11-game training subset risks a near-degenerate range on the excluded fold and silently distorts weights fold-to-fold, defeating the point of a stable, comparable weighting scheme.
- **Using `CalibrationDisplay.from_estimator` for the 5-class EP model:** it is designed around a single fitted binary/OvR-wrapped estimator; for LOGO's out-of-fold arrays (no single fitted estimator object, just accumulated prediction arrays) call `calibration_curve` directly per class instead.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Group-aware train/test splitting | Custom `game_id not in test_ids` filtering logic | `sklearn.model_selection.LeaveOneGroupOut` / `GroupKFold` | Already handles group-index bookkeeping correctly (no accidental leakage on edge cases like a group with 1 row); it's the exact tool nflfastR-style methodology maps onto |
| Reliability-curve binning | Custom `np.histogram`-based binning of predicted probabilities | `sklearn.calibration.calibration_curve` | Handles `strategy="uniform"` vs `"quantile"` binning edge cases (empty bins, degenerate ranges) that a hand-rolled version would need to reinvent |
| Binomial confidence intervals for PAT success rates | Manual normal-approximation CI (`p ± 1.96*sqrt(p(1-p)/n)`), which is a poor approximation for small-n or extreme-p samples (PAT success rates are often >90%) | `scipy.stats.binomtest(...).proportion_ci()` (Wilson/Clopper-Pearson) | PAT attempt counts in a single-season flag-football dataset are likely in the tens-to-low-hundreds range per type — exactly where the normal approximation breaks down |
| Model registry / "latest model" resolution | A custom `resolve_run`-style directory-scan-and-sort-by-mtime "latest model" convention | MLflow's registered-model + alias API (already the CONTEXT-locked decision) | This is precisely what MLflow's registry exists to replace; hand-rolling it duplicates a library capability CONTEXT already chose |

**Key insight:** Every capability this phase needs is a documented, already-installed library primitive. The engineering work is entirely in *composition* (looping LOGO over the existing `_train` pipeline shape, switching one tracking-URI string) — not in building new evaluation or storage machinery from scratch.

## Common Pitfalls

### Pitfall 1: MLflow registry silently failing against the `file:` store
**What goes wrong:** Calling `mlflow.xgboost.log_model(..., registered_model_name=...)` (or `mlflow.register_model`) against a `file:`-scheme tracking URI either raises `MlflowException` or (depending on MLflow version/path) partially succeeds in confusing ways.
**Why it happens:** Model Registry is a metadata feature that requires SQL query capabilities (foreign keys between registered models, versions, aliases, and runs) that MLflow's FileStore does not implement.
**How to avoid:** Migrate the tracking URI to `sqlite:///{config.paths.mlruns}/mlflow.db` (verified working, see Pattern 4) before writing any registry-touching code.
**Warning signs:** Any `MlflowException` mentioning "registry" or "not supported" immediately after switching `--tune`/training code to call `registered_model_name=`.

### Pitfall 2: Existing tests assume the FileStore's on-disk run-directory layout
**What goes wrong:** `tests/test_model_train.py::_run_dirs` walks `mlruns_path.iterdir()` expecting `<experiment_id>/<run_id>/params/*` files on disk. Once the tracking URI is `sqlite:///...`, run metadata (params, metrics, tags) lives inside the SQLite database, not as flat files — `_run_dirs` will find zero matching directories (or only artifact directories with no `params/` subfolder), silently breaking assumptions baked into several existing assertions.
**Why it happens:** FileStore and SqlAlchemyStore have genuinely different on-disk representations; MLflow's client API abstracts this for reads (`client.get_run(...)` works identically either way) but any test or code that pokes at the filesystem directly does not get that abstraction for free.
**How to avoid:** Audit every test/helper that walks `config.paths.mlruns` directly (not just through the MLflow client API) before flipping the tracking URI; `_run_dirs` specifically needs rewriting to either query via `MlflowClient` or to only check for the artifact subdirectory (which does still exist on disk).
**Warning signs:** Any test asserting on `Path.iterdir()` / `Path.rglob()` results under `config.paths.mlruns` rather than through `mlflow.tracking.MlflowClient`.

### Pitfall 3: LOGO runtime blowing up without early guardrails
**What goes wrong:** ~50+ full XGBoost fits per model (EP + WP = 100+ fits per full training invocation) can take much longer than the single-fit path today, especially if `--tune`'s inner CV is layered on top without care.
**Why it happens:** XGBoost fit cost scales with `n_estimators` × dataset size; a naive loop with no early stopping or parallelism repeats full-cost fits sequentially.
**How to avoid:** CONTEXT explicitly leaves this to the planner's discretion — options include `n_jobs`/`nthread` parallelism inside each fit, running folds concurrently (careful: concurrent MLflow child-run logging against a single SQLite file can hit `database is locked` errors under naive multiprocessing — batch results and log once, or use one writer process), or capping `n_estimators` for the LOGO measurement pass separately from the shipped model's tuned value. Measure actual wall-clock on the real dataset size before committing to a specific runtime strategy in the plan.
**Warning signs:** `sqlite3.OperationalError: database is locked` if fold-level logging is parallelized naively against the same `.db` file.

### Pitfall 4: `game_date` sparsity breaking recency weighting
**What goes wrong:** The canonical schema's `game_date` column (`src/flag_football_ep/canonical.py`) is a nullable `Utf8` extra — it may be null or inconsistently formatted for some sources (e.g., `legacy`), which would silently zero out or `NaN` the exponential-decay recency weight for those rows.
**Why it happens:** `game_date` was added as a nullable extra column, not a `CORE_COLUMNS` requirement enforced at ingest for every source.
**How to avoid:** Before implementing the recency-weighting experiment, check `game_date` null-rate per source on the real `plays.parquet`; if any pooled source has a meaningful null rate, decide (and document as a Task) whether those rows get a neutral/median weight or whether recency weighting is scoped to only the sources with reliable dates.
**Warning signs:** `Total_W_Scaled` producing `null`/`NaN` after multiplying in a recency factor for any source.

### Pitfall 5: Competition-tier join key ambiguity
**What goes wrong:** The canonical `competition` column is free text and format varies wildly by source (Hudl-parsed strings from filenames, sportapp's `competition_name`/`competition_league`, IFAF's tournament `name`/`id`, legacy's literal `"legacy"` placeholder). A naive `competition -> tier` mapping keyed only on the raw string will miss many values or collide unintentionally (e.g., two different competitions coincidentally sharing a substring).
**Why it happens:** `competition` was populated per-source, independently, with no cross-source normalization step (unlike `team_mapping.csv`, which explicitly exists to normalize `source_team -> canonical_team` per source).
**How to avoid:** Follow the `team_mapping.csv` precedent: key the new `competition_tier` reference CSV on `(source, competition)` pairs (or `game_id`, if that's more reliable per source), not on `competition` alone — mirroring the existing `source,source_team,canonical_team` shape in `data/reference/team_mapping.csv`.
**Warning signs:** A one-hot competition-tier column that is `null`/`unmapped` for a large fraction of rows after the join — check coverage before trusting any grouped-CV result that includes this covariate.

### Champion-alias resolution replacing `resolve_run`'s "latest FINISHED" default
```python
# Source: verified against installed mlflow==3.15.1 in this session.
from mlflow import MlflowClient
from mlflow.exceptions import MlflowException

def resolve_champion(registered_model_name: str, config: Config) -> str:
    mlflow.set_tracking_uri("sqlite:///" + str(config.paths.mlruns / "mlflow.db"))
    client = MlflowClient()
    try:
        mv = client.get_model_version_by_alias(registered_model_name, "champion")
    except MlflowException as exc:
        raise RunNotFound(
            f"no 'champion' alias set for registered model {registered_model_name!r} -- "
            "run `ffep promote` after reviewing a training run"
        ) from exc
    return mv.run_id  # existing _validate_run_id / load_model(run_id, config) path still applies
```
This preserves T-1.2-08's no-arbitrary-path property: the alias resolves to a `run_id` from the registry's own bookkeeping, never a caller-supplied path fragment.

## Open Questions

   - What we know: CONTEXT marks storage format/location as Claude's discretion; Phase 1.4's own-team EPA reporting is a stated downstream consumer.

2. **Does the real dataset's game count make LOGO's runtime acceptable without parallelization?**
   - What we know: CONTEXT accepted "the ~50+ fits cost" as a locked tradeoff; exact wall-clock was not measured in this research session (no real `plays.parquet` available in this worktree).
   - What's unclear: Whether 50+ sequential XGBoost fits per model complete in seconds, minutes, or longer on the actual dataset size — this materially affects whether the plan needs a parallelization task in Wave 1 or can defer it.
   - Recommendation: The plan's first LOGO task should include a quick wall-clock measurement (e.g., time the loop on the real ingested data) before deciding whether to invest in parallelization; do not pre-build parallel infrastructure speculatively.
