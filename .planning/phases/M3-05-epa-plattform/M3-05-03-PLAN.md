<objective>
This plan merges what were originally two separate plans -- a corpus freeze manifest, and
training-run lineage/calibration/tier/no-play metrics -- into one. CONTEXT groups both under the
same "hygiene" bucket, ordered after the quick wins (M3-05-02) and before the gate; keeping them
in one plan also removes an earlier design's awkward cross-plan dependency (a separate plan
"wiring the freeze citation into training" after both existed independently). This plan produces
the freeze manifest AND cites it from the training run that trained against it, in the same
place.

No training run today can say, on its own, which exact corpus it was trained against beyond a
per-model, post-filter hash (`training_data_sha256`), and `ffep train` (the only production
training entry point) logs zero git lineage -- verified live against this project's own MLflow
store: the current champion run's tags have no `mlflow.source.git.commit` key, because MLflow's
automatic git-detection never fires for a venv console-script entry point (`.venv/bin/ffep`).
Only `scripts/hc_corpus_ablation.py`'s ad-hoc runs get any of this today -- both the corpus
fingerprint/git-commit hashing scheme AND per-tier/no-play computations already exist there,
proven, just scoped to the wrong entry point.

CONTEXT requires the promotion gate (M3-05-06) to read metrics MLflow already has, not
re-derive them from CSVs whose naming convention already changed mid-phase (M3-02's
`data/reference/epa_refinement/2026-09-08/` subfolder, sibling to the undated original). This
plan is the prerequisite: generalize what the ablation script already proved out into `_train`'s
shared path, so every `ffep train` run -- champion candidate or not -- carries the numbers a
gate needs, plus a fresh corpus-freeze manifest and command, plus the one genuinely missing
number (a scalar calibration metric; today only a reliability-curve PNG exists).

`TIER_FEATURE_COLUMNS` (`tier_womens_international`, `tier_womens_national`, `tier_mixed_other`)
are already one-hot columns in both `EP_FEATURES` and `WP_FEATURES` -- present in `model_data`
by the time `run_logo` runs. Per-tier metrics do not need the ablation script's separate
label-frame reconstruction and CSV re-join; they can be derived directly from these existing
columns, which is simpler than what `hc_corpus_ablation.py::build_tier_metrics` does.

Per RESEARCH Pitfall 3: no source in this project (`fetch/ifaf.py`, `ingest/hc_workbook.py`)
writes an in-band "fetched at" timestamp today. This plan's per-source snapshot date is a
best-effort file-mtime approximation, explicitly labelled as such in the manifest -- not
treated as ground truth. A `_fetched_at.json` sidecar in the fetch layer is a real, separate
follow-up, out of this plan's scope.

Purpose: give every future retrain a citable, reproducible statement of which corpus it saw, and
make lineage plus gate-relevant metrics a property of every production training run.
Output: `model/freeze.py`, `ffep freeze-corpus`, `ffep train --freeze`, extended `_train`/
`_log_run`, and one new `evaluate.calibration_max_deviation` function.
</objective>

```python
def compute_corpus_fingerprint(plays: pl.DataFrame) -> str:
    keys = plays.select("game_id", "play_id", "source").sort(["game_id", "play_id", "source"])
    return hashlib.sha256(keys.write_csv().encode("utf-8")).hexdigest()

def git_commit_sha() -> str:
    try:
        result = subprocess.run(
            ["git", "rev-parse", "HEAD"], cwd=REPO_ROOT,
            capture_output=True, text=True, check=True,
        )
        return result.stdout.strip()
    except (OSError, subprocess.CalledProcessError):
        return "unknown"
```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| corpus state -> committed manifest | the manifest is a claim about what `plays.parquet` contained on a given date; a wrong claim misleads every run that cites it |
| filesystem mtime -> "snapshot date" | mtime can be touched by `git checkout`/backup/`rsync` without content changing (RESEARCH Pitfall 3) |
| training run -> MLflow store | lineage and gate-relevant metrics are only as trustworthy as the code that computes them at fit time |
| metric key sanitization -> MLflow API | tier/class names interpolated into metric keys could collide or contain unsafe characters |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-M3-05-03 | Tampering | `data/reference/corpus_freeze/*.json` | mitigate | Manifests are committed to git like every other reference dataset -- git history is this project's existing tamper-evidence mechanism |
| T-M3-05-04 | Information Disclosure (misleading provenance) | best-effort mtime snapshot date | accept | Explicitly labelled `"approximate": true`; a real fetch-layer sidecar is a documented follow-up |
| T-M3-05-05 | Tampering (identifier injection) | manifest filename parsing / `--freeze <path>` | mitigate | Filenames are generated by this module only; `--freeze <path>` is only ever used as a filesystem read path, never interpolated into a shell command or SQL |
| T-M3-05-06 | Repudiation | `git_commit`/`corpus_fingerprint` params | mitigate | Captured inside `_train` at fit time, with the proven `"unknown"` fallback so a missing `git` binary never fails a training run |
| T-M3-05-07 | Tampering (metric key collision) | `per_tier_logloss_<tier>`/`calibration_max_deviation_<class>` key sanitization | mitigate | Reuses the existing `_METRIC_KEY_UNSAFE.sub("_", ...)` sanitizer already proven for `logo_logloss_by_source_<source>` |
| T-M3-05-08 | Denial of Service (silent crash on narrow frames) | tier/no-play metrics on frames lacking `tier_*`/`result_raw` columns | mitigate | Both additions are guarded no-ops when the columns are absent, matching the existing `half`-sentinel guard discipline in `mutations.py` |
| T-M3-05-SC | Tampering | package installs | accept | This plan installs nothing new |
</threat_model>
