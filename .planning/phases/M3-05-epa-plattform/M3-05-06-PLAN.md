<objective>
Two related pieces of "operator surface" CONTEXT requires, both depending on this phase's
earlier work landing first: (1) a training run should be able to name which corpus freeze
(M3-05-02) it trained against; (2) `ffep promote` should refuse a candidate that fails a
mechanical check (M3-05-03's new metrics) unless a human explicitly overrides it with a written
reason.

The gate replaces "judgement by hand reading the MLflow UI" as the DEFAULT path
(`docs/model-training.md` section 3's current description) -- it does not remove judgement, it
gives judgement an escape hatch that is itself logged. Four criteria, all readable from the
candidate run's own MLflow metrics after M3-05-03 landed: beats the naive baseline
(`logloss_improvement > 0`, already logged); beats the current champion
(`candidate_metric <= champion_metric + epsilon`, resolved via the EXISTING, unmodified
`registry.resolve_champion` -- if no champion exists yet, this check passes automatically, there
is nothing to beat); calibration within tolerance (every `calibration_max_deviation_<class>`
metric under a threshold); no-play share under the 2% threshold M3-02 already established
informally (`docs/epa-refinement-2026-10.md`: "über der intern verabredeten
2-%-Eskalationsschwelle" -- reused, not reinvented).

Threshold defaults are Claude's discretion per CONTEXT, with one caveat: the current champion
(whichever M3-05-01 resolved it to) predates M3-05-03's new metrics and will not have
`calibration_max_deviation_*`/`no_play_share` logged on it -- there is no historical value to
calibrate a tolerance against yet. Ship the RESEARCH-proposed starting defaults
(`max_calibration_deviation=0.15`, `max_no_play_share=0.02`, `champion_epsilon=0.0`), documented
in `ffep.toml` as explicitly provisional, and get their first real empirical exercise in
M3-05-07's gated extra-point-fix re-promotion.

Purpose: promotion becomes gated by default, with an auditable override, not judged by hand.
Output: `model/gate.py`, `[promotion_gate]` in `ffep.toml`, `ffep train --freeze`,
`ffep promote --force --reason`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| gate check -> champion alias | the gate is the mechanical guard between a candidate run and production; a bug here either blocks a good model or ships a bad one |
| `--reason` free text -> MLflow tag | user-supplied text reaching a tag value |
| freeze manifest path (CLI arg) -> filesystem read | an operator-supplied path |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-M3-05-14 | Tampering (wrong metric key) | `evaluate_gate`'s per-model metric resolution | mitigate | Metric key resolved by `model_prefix` explicitly (Pitfall 2) -- a dedicated test asserts the gate reads `logo_mlogloss` for `ep` and `logo_logloss` for `wp`, never the other model's key |
| T-M3-05-15 | Elevation of Privilege | `ffep promote --force` | mitigate | `--force` requires a non-empty `--reason`, refused otherwise (`typer.BadParameter`); the reason and the operator are logged as MLflow tags on the promoted run, not just printed to a terminal that can be lost (Pitfall 4) |
| T-M3-05-16 | Repudiation | gate pass/fail/skip result | mitigate | `GateResult` distinguishes a real pass from a skipped check (metric absent on an old run) and the CLI prints every check's outcome, so a promotion is never silently justified by a check that did not actually run |
| T-M3-05-17 | Tampering (identifier injection) | `--reason` / `--freeze <path>` CLI inputs | mitigate | `--reason` is passed as a normal `set_tag` argument (parameter-bound MLflow API call, never string-interpolated into a URI/query -- RESEARCH Security Domain); `--freeze <path>` is only ever used as a filesystem read path via `Path`/`open`, never interpolated into a shell command or SQL |
| T-M3-05-SC | Tampering | package installs | accept | This plan installs nothing new |
</threat_model>
