# Phase 1.2: Repo to Pipeline - Research

**Researched:** 2026-08-17
**Domain:** Python data pipeline packaging (Typer CLI, polars ETL, XGBoost training, MLflow tracking) for a flag-football play-by-play analytics repo
**Confidence:** MEDIUM-HIGH — stack choices are well-documented and low-risk; the domain-specific merge/validation logic is HIGH confidence (verified directly against this repo's own code and data), the IFAF/cpx.studio API integration is LOW confidence (no official docs, single-session discovery)

## Summary

This phase turns a notebook-and-`Python/`-helpers prototype into an installed package (`flag_football_ep`) driven by a Typer CLI (`ffep`). The core technical shape is uncontroversial: Typer for subcommands (locked decision), polars for all dataframe work (already the project's dialect), MLflow's local file-based tracking (`mlruns/`) as a logging sidecar around the existing XGBoost training code, and a small validation module that layers per-game business-rule checks (monotonic drive IDs, gapless play sequences, score reconstruction) on top of the `docs/data-contract.schema.json` core-plus-optional column contract already produced in Phase 1.1.

The real complexity is domain-specific, not framework-specific, and was only visible by reading the actual code being ported: (1) the Hudl mutation chain (`Python/helper_add_hudl_mutations.py`) derives `posteam`/`home_team` by assuming "the team with the first drive is home" — a documented fragile precedent that the Phase 1.1 contract's TEAM1/ODK rule is supposed to supersede for new-format ingest, but the legacy path still needs the old inference; (2) the existing sportapp.fi pipeline (`Python/fetch_sportappfi_api.py`) does NOT reuse `make_hudl_mutations` — it derives `play_type`/`touchdown`/`scoring_play`/etc. from a completely separate text-parsing path (`action_title`, `down_desc.str.contains("PAT")`) because sportapp.fi's JSON has no RESULT-string equivalent; the two mutation chains only converge at the final canonical-column level, they are not shared code; (3) `data/wc24_pbp.csv` (14,546 rows, checked into the repo) is **already the fully-mutated output** of the old sportapp.fi pipeline for WC24 2024 — not raw data — and Phase 1.1's ep_model.ipynb currently concatenates it post-mutation with Hudl data; the new snapshot-first `ffep fetch-sportapp` design (raw JSON to disk, ingest reads from disk) means this file's provenance and reuse status needs an explicit planning decision.

**Primary recommendation:** Typer + polars + MLflow (full package, not `mlflow-skinny`, for local `mlflow ui` access) as the stack; port the two existing mutation chains (Hudl RESULT-parsing, sportapp.fi text-parsing) largely as-is into `ingest/hudl.py` and `ingest/sportapp.py` rather than trying to unify them into one function; build validation as a dedicated module that consumes `data-contract.schema.json` for column-level checks and hand-written polars checks for the four sequence/score business rules — this is not a case for a generic schema-validation library, because the checks are per-game sequence invariants, not per-row constraints.

### Locked Decisions

**CLI shape & entry points**
- One installed CLI with subcommands — `ffep ingest`, `ffep fetch-sportapp`, `ffep fetch-ifaf`, `ffep train`, `ffep score`. Everything discoverable from one entry point.

**Validation report & failure policy**
- Failure mode: Quarantine — games failing validation are excluded from the canonical Parquet and listed prominently in the report; the run continues with valid games.
- Final-score reference: A small maintained CSV under `data/reference/` (same workflow as `data/half_boundaries.csv`) maps each game to its true final score; the score-reconstruction check validates against it.
- Report form: Console summary during the run + a per-run Markdown report written next to the Parquet — one section per game, pass/fail per check.
- Legacy path: The grandfathered `data_raw.csv` games (47) run through the same checks but warn-only — never quarantined.

- API strategy: Snapshot first — `ffep fetch-*` downloads raw JSON into `data/raw/<source>/` once; ingest always reads from disk.
- Merge model: One canonical plays table with nullable extras — core columns (down, distance, yardline, result, score, teams, half) required for every source; rich Hudl charting fields and IFAF real game-clock nullable.

- Parquet shape: Single `plays.parquet`, rebuilt atomically per ingest, with source/competition/season as ordinary filter columns; games metadata as a second small Parquet.

### Pattern 1: Contract-driven column validation before mutation
**What:** Load `docs/data-contract.schema.json` at ingest start; check header against `core_columns` (fail hard if any missing) and `optional` columns (materialize as null if absent); ignore unknown columns with a log notice per the contract's `unknown_rule`.
**When to use:** First step of `ingest/hudl.py`, before any mutation logic runs — mutation code should never have to defend against a missing core column.
**Example:**
```python
# Source: docs/data-contract.schema.json (read directly, 2026-08-17)
import json
import polars as pl

def load_contract(path: str) -> dict:
    with open(path) as f:
        return json.load(f)

def validate_header(df: pl.DataFrame, contract: dict) -> pl.DataFrame:
    core = [c["name"] for c in contract["columns"] if c["presence"] == "core"]
    optional = [c["name"] for c in contract["columns"] if c["presence"] == "optional"]
    missing_core = [c for c in core if c not in df.columns]
    if missing_core:
        raise ValueError(f"missing core columns: {missing_core}")
    for col in optional:
        if col not in df.columns:
            df = df.with_columns(pl.lit(None).alias(col))
    return df
```

### Pattern 2: Quarantine at the game level, not the row level
**What:** Run all five validation checks per `game_id`; if any check fails for that game, exclude the entire game's plays from the Parquet write and record the failure(s) in the Markdown report. Valid games proceed.
**When to use:** Between the ingest/mutation stage and the final `plays.parquet` write — this is a `filter`, not a raise, for new-format games; legacy games (`data/raw/legacy/`) go through the same checks but only ever warn, never filter.
**Example:**
```python
# Pattern derived from CONTEXT.md quarantine decision + existing helper_add_hudl_mutations.py drive/play conventions
import polars as pl

def monotonic_drive_ids(df: pl.DataFrame) -> pl.DataFrame:
    # per game_id: drive_id must be non-decreasing across ascending play_id
    return (
        df.sort(["game_id", "play_id"])
          .group_by("game_id", maintain_order=True)
          .agg((pl.col("drive_id").diff().fill_null(0) >= 0).all().alias("drive_ids_monotonic"))
    )

def gapless_play_sequence(df: pl.DataFrame) -> pl.DataFrame:
    # per game_id: play_id must be exactly 1..N with no gaps
    return (
        df.group_by("game_id")
          .agg(
              pl.col("play_id").max().alias("max_play_id"),
              pl.col("play_id").n_unique().alias("n_unique_play_ids"),
          )
          .with_columns((pl.col("max_play_id") == pl.col("n_unique_play_ids")).alias("plays_gapless"))
    )
```

### Pattern 3: Two independent mutation chains, one canonical output
**What:** Hudl ingest derives `play_type`/`touchdown`/`scoring_play`/etc. from `RESULT` string tokens (`str.contains`/exact-token split per the contract grammar). sportapp.fi ingest derives the same *named* output columns from a completely different input shape (`action_title`, `down_desc` containing `"PAT"`, `play_result` text extracted via regex from `summary`). These are NOT the same function with different inputs — porting `Python/fetch_sportappfi_api.py`'s `add_event_columns`/`add_team_points`/`correct_posteam` helpers as their own module is correct; do not attempt to force sportapp.fi data through `make_hudl_mutations`.
**When to use:** Any time the plan is tempted to "unify the mutation logic" — the CONTEXT merge model already anticipates this by making the *canonical schema* (not the mutation code) the unification point ("one canonical plays table with nullable extras").
**Example:**
```python
# Source: Python/fetch_sportappfi_api.py (existing, read 2026-08-17) — sportapp.fi's own down=0/PAT derivation,
# structurally parallel to but independent from Hudl's RESULT-token parsing
down = pl.when(pl.col("down_desc").str.contains("PAT")).then(pl.lit(0)).otherwise(pl.col("down"))
```

### Anti-Patterns to Avoid
- **Forcing one mutation function across sources:** Hudl's `RESULT` grammar and sportapp.fi's `action_title`/`summary` text have no shared vocabulary; a "generic" mutation function would need so many source-specific branches it becomes two functions wearing one name. Keep them separate modules that converge only at the canonical-column contract.
- **Reusing `get_games()`'s "first-drive-team = home" heuristic for new-format Hudl ingest:** The Phase 1.1 contract's TEAM1/ODK-derived `posteam` rule exists specifically because this heuristic is fragile (CONTEXT explicitly calls it out as "known-fragile precedent" and "superseded ... for new-format ingest"). It should be kept only for the legacy path where TEAM1/filename-based derivation isn't available.
- **Row-level schema validation as a substitute for the four sequence checks:** A dtype/range validator (hand-rolled or pandera) catches "DN is 7" but not "drive_id went 3,4,4,3,5" or "play_id skipped 14"; these need `group_by("game_id")` aggregation logic, not per-row constraints.
- **Re-running the full hyperopt search inside `ffep train` on every invocation:** the notebook's actual saved models (`ep_model.pkl`, `wp_model.pkl`) were produced by fitting `XGBRegressor` once with hyperparameters already found by a prior 100-trial hyperopt search — CONTEXT's "port ... with obvious fixes only" does not require re-running that search on every future train. See Open Questions.

## Common Pitfalls

### Pitfall 1: A live API key is already committed to the repo
**What goes wrong:** `config/config.py` contains `API_KEY = 'wRX0tTke3DZ8RLKAMntjZ81LwgNQuSN9'` in plaintext, imported (or copy-pasted) by API-exploration notebooks (`api_call.ipynb`, `api_fuzzing.ipynb`) and structurally parallel to how `Python/fetch_sportappfi_api.py` expects an `api_key` parameter.
**Why it happens:** Early-stage prototype code, no `.env` convention existed yet.
**How to avoid:** Phase 1.2's config decision ("secrets ... come only from environment / .env, never committed") directly fixes the pattern going forward. The planner should include a task to (a) delete `config/config.py` from the working tree, (b) add `.env` (git-ignored) with `SPORTAPP_API_KEY`, (c) update `.gitignore` to cover `.env`. Rotating the already-exposed key is outside a research agent's scope to decide but should be flagged to the user — the key is in git history regardless of the code fix.
**Warning signs:** Any new fetch/ingest code that imports from `config.config` instead of `os.environ`/`pydantic-settings`/the new config module.

### Pitfall 2: The `RESULT` string grammar match is fragile if ported carelessly
**What goes wrong:** The current Hudl mutation code (`Python/helper_add_hudl_mutations.py`) uses `pl.col('RESULT').str.contains("Complete")` — this is documented in `docs/data-contract.md` as "fragile substring semantics" that "only works by accident" (`Incomplete` doesn't match `contains("Complete")` only because polars string comparison is case-sensitive and the substrings differ; `TD` ⊂ `Def TD` is caught only by an explicit `.str.contains("Def").not_()` guard).
**Why it happens:** The old code predates the Phase 1.1 contract's formal RESULT grammar (13-token vocabulary, exact-token match after split on `", "`, case-sensitive).
**How to avoid:** The contract (§"RESULT-Vokabular & Grammatik") already specifies the fix: split `RESULT` on `", "` and do exact token membership tests, not substring `.str.contains`. New-format ingest (`ingest/hudl.py`) should implement this properly; the legacy path (`ingest/legacy.py`) can keep the old `.str.contains` behavior since `data_raw.csv` is grandfathered and its malformed RESULT variants (`"Penalty (declined)"`, `"Complete Penalty"` without comma) are documented as "forward ungültig" (invalid going forward) but still present in the 47 legacy games.
**Warning signs:** A validation-check false-negative where `Incomplete` plays get classified as complete passes, or `Def TD` plays get double-counted as both offensive and defensive touchdowns.

### Pitfall 3: `python.requires-python` floor doesn't match the actual dev environment
**What goes wrong:** `pyproject.toml` declares `requires-python = ">=3.10"`, but the project's `.venv` is Python 3.13.3 and — per code-context notes carried over from Phase 1.1 planning — the intended project constraint is Python 3.12. `tomllib` (stdlib) requires Python ≥3.11, so if the config-file decision lands on TOML and the floor stays at 3.10, an extra `tomli` dependency becomes necessary for correctness on 3.10.
**Why it happens:** `requires-python` was never revisited since project bootstrap.
**How to avoid:** Planner should align `requires-python` to the actual target (verify with the user whether it's exactly "3.12" or "≥3.12") as part of this phase's pyproject.toml edits, alongside adding `typer`/`mlflow`/`[project.scripts]`.
**Warning signs:** CI or a fresh `uv sync` picking a different interpreter than what's actually been tested.

### Pitfall 4: `Total_W`/`Total_W_Scaled` weighting logic divides by a range that can be zero for a single game
**What goes wrong:** `make_ep_model_mutations` in `Python/helper_add_model_mutations.py` computes `(pl.max("Drive_Score_Dist") - pl.col("Drive_Score_Dist")) / (pl.max("Drive_Score_Dist") - pl.min("Drive_Score_Dist"))` — a division that is undefined (`0/0`) if `Drive_Score_Dist` has zero range within the frame it's applied to. Currently this is always called on the full multi-game dataset, so this hasn't manifested, but if `ffep train` is architected to (optionally) train/score a single game for testing, this becomes a live NaN/inf risk.
**Why it happens:** The weighting formula assumes a globally-diverse training set; it was written and only ever exercised against the full corpus.
**How to avoid:** Preserve the "always compute on the full training corpus, never per-game" invariant when porting; add a unit test asserting no NaN/inf appears in `Total_W_Scaled` for the ported training path.
**Warning signs:** `Total_W_Scaled` containing null/NaN/inf values after porting; `xgb.XGBRegressor.fit(sample_weight=...)` silently degrading model quality if this slips through.

### Pitfall 5: `pl.melt`/`.pivot(aggregate_function=...)` API surface in `get_games()` may need updating for the pinned polars floor
**What goes wrong:** `Python/helper_add_hudl_mutations.py`'s `get_games()` calls `df.melt(...)` and `.pivot(values=..., index=..., columns=..., aggregate_function=pl.element())` — polars has moved `.melt` toward `.unpivot` and reworked `.pivot`'s `aggregate_function` signature across versions since `polars>=1.5.0` was pinned. This is a real risk when porting, not a hypothetical.
**Why it happens:** polars is a fast-moving library; the pinned floor (`>=1.5.0`) does not guarantee the exact API surface the original code was written against.
**How to avoid:** When porting `get_games()` into `features/mutations.py`, run it against a fixture and check for `DeprecationWarning`/`AttributeError` before assuming a straight copy-paste works; consult the installed polars version's changelog for `.melt`/`.pivot` signature changes. [ASSUMED — not verified against a specific polars changelog entry in this research session; flag for planner validation during Wave 0.]
**Warning signs:** `AttributeError: 'DataFrame' object has no attribute 'melt'` or a `pivot()` call raising `TypeError` on `aggregate_function`.

## Open Questions (RESOLVED)

> All four questions were settled during planning. Resolution pointers:
> 1. Hyperopt search — RESOLVED by plan 13: `ffep train` defaults to the notebook's fixed hyperparameters; the 100-trial search is ported behind an opt-in `--tune` flag (research's recommended default, adopted without dropping the search).
> 2. `data/wc24_pbp.csv` disposition — RESOLVED procedurally by plan 11 task 1: a blocking `checkpoint:decision` presents the three disposition options with supporting numbers; the user decides at execution time.
> 3. pandera vs. hand-written loader — RESOLVED by plan 05: no pandera dependency; a hand-written loader over `data-contract.schema.json` provides the version tolerance needed.
> 4. IFAF/cpx.studio auth/rate limits — RESOLVED procedurally by plan 07 task 3: the first live call is an explicit verification checkpoint, and plan 12 derives its field mapping from that evidence with per-field `observed`/`documented`/`absent` tags.

1. **Does `ffep train` reproduce the full hyperopt hyperparameter search, or port only the tuned/fixed hyperparameters?**
   - What we know: The notebooks contain both an initial fixed-hyperparameter fit and a 100-trial `hyperopt` search (`fmin(..., max_evals=100)`) whose output (`best_hyperparams`) is then used for a second, "production" fit. The actual saved `.pkl` model files most likely come from the tuned fit.
   - What's unclear: Whether "port training/scoring behavior with obvious fixes only, NOT a methodological redo" (CONTEXT) means the hyperopt search itself is part of "today's behavior" that must be preserved verbatim inside `ffep train`, or whether it's acceptable/expected to hardcode the already-found tuned hyperparameters as defaults and treat re-tuning as out of scope until Phase 1.3's GroupKFold methodology work.
   - Recommendation: Default to hardcoding the tuned hyperparameters (faster, deterministic, avoids re-implementing a 100-trial search inside a "foundation" phase) but flag this explicitly for user confirmation during planning/discuss-phase — this materially affects `ffep train`'s runtime and whether `hyperopt` needs to be a runtime dependency of the package or just a one-time tuning script.

2. **What is the disposition of `data/wc24_pbp.csv`?**
   - What we know: It is the already-mutated output of the old sportapp.fi pipeline (14,546 rows, WC24 2024), currently concatenated post-mutation into training data in `ep_model.ipynb`.
   - What's unclear: Whether Phase 1.2's snapshot-first `ffep fetch-sportapp` is expected to re-fetch and re-process this tournament's raw JSON through the new canonical ingest path (making this file obsolete/regenerable), or whether it should be relocated as a second grandfathered/warn-only legacy input alongside `data_raw.csv`.
   - Recommendation: Surface this explicitly in planning — it directly affects REQ-S1-06 ("source-merge... consolidated into `data/`") and whether the training corpus size changes.

3. **Does `pandera[polars]` get added as a dependency for column-level validation, or does the ingest validator use a hand-written loader over `data-contract.schema.json`?**
   - What we know: Both are technically sound; pandera is legitimate (slopcheck OK, well-established) and maps cleanly onto the core-plus-optional model. A hand-written loader adds no new dependency and the schema file's shape (JSON, not JSON Schema draft) means no *generic* validator applies without a translation layer regardless.
   - What's unclear: Whether the marginal boilerplate reduction from pandera is worth a new dependency for a validator that's maybe 100-150 lines either way.
   - Recommendation: Planner's call — not blocking, listed as an Alternative rather than a Core Standard Stack entry for this reason.

4. **IFAF/cpx.studio API usage terms, rate limits, and authentication requirements are unverified.**
   - What we know: Four endpoint shapes were user-supplied and verified structurally in the folded todo (`unified-plays` returns 90 play objects with the fields listed in CONTEXT.md). No official API documentation exists (this appears to be an internal/undocumented tournament-ops API, not a public developer platform).
   - What's unclear: Whether requests require an API key/auth header (the user-supplied endpoints in the todo show no `apikey` param unlike sportapp.fi's URLs, but this may mean it's currently open or that auth details weren't captured), rate limits, and whether the WM-2026 tournament ID (`ffwc26-women`) is stable or will be reused/retired.
   - Recommendation: `ffep fetch-ifaf`'s first real run against the live API is itself the verification step; the planner should treat the first live call as a discovery/validation task (does it need headers? what's the actual response shape for `/events`?) rather than assuming the todo's single-session sighting is complete. | Hardcoded/committed API key (already present: `config/config.py`) | Information Disclosure | Move to `.env` (git-ignored) + `os.environ` read in the new `config.py` module; flag to the user that the already-committed key should be considered compromised and rotated with the sportapp.fi provider, since deleting it from the working tree does not remove it from git history |
| Malformed/malicious CSV/JSON input from Hudl exports or the IFAF API causing unhandled exceptions or silent bad data | Tampering / Denial of Service (of the pipeline, not a live service) | The REQ-S1-05 validation-and-quarantine design already mitigates this for structural issues (malformed data → quarantined, not silently ingested); ensure fetch code (`requests.get`) uses timeouts and checks `response.status_code`/handles non-JSON responses gracefully (the existing `fetch_sportappfi_api.py` already does basic status-code checking — port that pattern to `ifaf.py` too, since the cpx.studio endpoints are unverified/undocumented) |

This is a low-external-attack-surface internal analytics tool (no network-facing service, single operator, data is sports statistics not sensitive PII beyond player names already flagged and `.gitignore`'d in Phase 1.1). The one concrete, verified security finding from this research is the committed API key — everything else in this section is standard hygiene rather than an active threat.
