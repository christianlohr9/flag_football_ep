## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Score cross-check compared the wrong row (pre-play vs. post-play score)**
- **Found during:** Task 2, real-corpus validation (not required by the plan's automated verify, done as an extra sanity check)
- **Issue:** `context.score` is the score *entering* a play (pre-play), but `add_score_columns` credits a scoring row with its own points immediately, so the current row's reconstructed score already includes points `context.score` on that same row does not yet reflect. Comparing them directly produced a spurious one-play-lag mismatch on every play following any score — roughly 53% of the live corpus flagged as "mismatched" when almost none of it actually was.
- **Fix:** Compare `context.score` against the *previous* row's reconstructed score (`.shift(1).over("game_id")`, filled with 0 for each game's first play) instead of the current row's.
- **Files modified:** `src/flag_football_ep/ingest/ifaf.py`
- **Verification:** Live-corpus score-mismatch rate dropped from ~53% to ~39% after this fix alone (see deviation 2 for the rest); a hand-traced example game (GER-USA) confirmed the alignment is now correct row-by-row.
- **Committed in:** `f25ed16` (folded into the GREEN commit, module not yet reviewed/merged)

**2. [Rule 1 - Bug] `outcome.type` treated as authoritative for TOUCHDOWN/TD/TRY/XP1/XP2 scoring, but the live data shows it is not**
- **Found during:** Task 2, real-corpus validation, tracing the residual score mismatches after deviation 1's fix
- **Issue:** Some `outcome.type == "TOUCHDOWN"` rows are actually 1- or 2-point conversions (`outcome.pointsScored == 1` or `2`, confirmed by `description.kind == "TRY"` on those exact rows) rather than 6-point touchdowns. Separately, ~11% of `TOUCHDOWN`/`TD`-typed rows carry no `pointsScored` key at all, and `context.score` never changes across those specific rows — consistent with an overturned/nullified play that the source still tags with the scoring outcome type. The original design (`OUTCOME_MAP` keyed purely by type string, `TOUCHDOWN`/`TD` unconditionally setting `touchdown=1`) credited 6 points for all of these, corrupting the reconstructed score.
- **Fix:** Redesigned the five scoring-shaped types (`TOUCHDOWN`, `TD`, `TRY`, `XP1`, `XP2`) to route through a shared `_SCORING_OUTCOME_TYPES`/`_POINTS_TO_FLAG` branch keyed on `outcome.pointsScored` alone (6→touchdown/def_touchdown, 2→two_point_conv_success, 1→one_point_conv_success, anything else→no flag), rather than a fixed type→flag mapping.
- **Files modified:** `src/flag_football_ep/ingest/ifaf.py`, `docs/ifaf-field-mapping.md` (outcome-vocabulary table rewritten with the full per-combination breakdown and a new "scoring-shaped types" note), `tests/test_ingest_ifaf.py` (two new regression tests, one existing test's fixture payloads updated to include explicit `pointsScored`)
- **Verification:** Live-corpus score-mismatch rate dropped from ~39% to ~1.5% (62/4,057 plays) after this fix; the residual is concentrated almost entirely in one game (`ffwc26-wb1`, 58/77 of that game's mismatches) whose `context.score.away` field appears to never update in the source data regardless of which team scores — a genuine source-side data quirk, not a parser defect, and exactly the kind of signal `IngestNotices.score_mismatches` is designed to surface for later review, not something this plan is scoped to resolve further.
- **Committed in:** `f25ed16` (folded into the GREEN commit)
