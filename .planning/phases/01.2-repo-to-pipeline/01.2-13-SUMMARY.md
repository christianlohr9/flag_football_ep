## Accomplishments

- `train_ep`/`train_wp` fit the notebooks' exact features, split (`train_test_split(test_size=0.2, random_state=42)`), and fixed hyperparameters by default, logging every run's params (including `training_data_sha256`, `n_plays`, excluded game ids), metric (`test_mlogloss`/`test_logloss`), and model artifact to a local MLflow store — no run ever overwrites another's artifact.
- Optional `--tune` hyperopt search (ported `model_objective`, 9-key search space) is preserved behind an explicit flag, off by default, so a 100-trial search never runs on a plain `ffep train`.

- All EP/WP hyperparameters, feature lists and the hyperopt search space live in one place (`model/hyperparams.py`) with source-cell comments, so `train.py` never inlines a tuned value.

## Decisions Made

- MLflow's local file store is now opt-in (`MLFLOW_ALLOW_FILE_STORE=true`) under mlflow 3.15 — kept the file-based `mlruns/` approach the CONTEXT decision and this plan's behavior requirements depend on, rather than migrating to sqlite/server tracking mid-plan.
- Tuned refit always uses the full training frame (not the 80/20 train split), matching the notebooks' own tuned-refit cells exactly — this asymmetry with the `tune=False` path (which fits only on the split) is inherited from the original notebooks, not introduced here.
- The tuning objective's `reg_alpha`/`colsample_bytree` are NOT int-cast, unlike the notebooks' objective cells — that cast only applies to `hp.uniform`-sampled values (not `hp.quniform`), zeroes out `colsample_bytree`, and is never applied in the notebooks' own refit cells, so porting it would be porting a bug, not the intended behavior.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Opted back into MLflow's local file-based tracking store**
- **Found during:** Task 1 (first `train_ep` MLflow logging attempt)
- **Issue:** `mlflow==3.15.1` (already pinned in `pyproject.toml`) raises `MlflowException` on any `file:` tracking URI unless `MLFLOW_ALLOW_FILE_STORE=true` is set — the store is in "maintenance mode" by default in this version. This would have silently broken CONTEXT.md's locked "local mlruns/" decision and the plan's explicit behavior requirement (a run directory with params/metrics/artifact files under `config.paths.mlruns`).
- **Fix:** `os.environ.setdefault("MLFLOW_ALLOW_FILE_STORE", "true")` at module import time in `train.py`, documented in the module docstring.
- **Files modified:** `src/flag_football_ep/model/train.py`
- **Verification:** `test_train_ep_returns_non_empty_run_id` and the full suite pass with a real local `mlruns/` directory under `tmp_path`.
- **Committed in:** `ad74d99` (Task 1 commit)

**2. [Rule 1 - Bug] Explicit `labels` argument for every `log_loss` call**
- **Found during:** Task 1 (first held-out-split evaluation)
- **Issue:** `sklearn.metrics.log_loss(y_true, y_pred)` raises `ValueError` when the held-out split's `y_true` doesn't contain every class the model's `y_pred` has columns for — a real risk for any small or class-imbalanced split, not just synthetic test data.
- **Fix:** Pass `labels=list(range(num_class))` (EP) or omit for binary (WP) on every `log_loss` call, both in the main evaluation and the tuning objective.
- **Files modified:** `src/flag_football_ep/model/train.py`
- **Verification:** Full test suite passes, including the multi-class EP path on a synthetic corpus.
- **Committed in:** `ad74d99`, `6eab50e`, `9f3ad87`

**3. [Rule 1 - Bug] MLflow 3.x "Logged Model" artifact layout in test assertions**
- **Found during:** Task 1 (artifact-directory assertion)
- **Issue:** My own test assumed the pre-3.x layout (`<run_id>/artifacts/model/`); mlflow 3.x logs models as first-class "Logged Model" entities under `<experiment_id>/models/m-<id>/artifacts/`, linked to the run via `run.outputs.model_outputs`.
- **Fix:** Resolve the artifact directory through `client.get_logged_model(model_id).artifact_location` instead of assuming a fixed subpath.
- **Files modified:** `tests/test_model_train.py`
- **Verification:** `test_train_ep_run_directory_has_params_metric_and_model_artifact` passes.
- **Committed in:** `ad74d99`

**4. [Rule 1 - Bug] Relaxed a brittle stepped-metric-count assertion**
- **Found during:** Task 3 (stepped `tune_logloss` trial metric test)
- **Issue:** MLflow 3.x's Logged Model API re-appends a duplicate metric entry for the most recently logged step at `mlflow.xgboost.log_model()` time (visible directly in the run's raw metric file on disk), so raw `get_metric_history` length is not a stable count of `mlflow.log_metric` calls.
- **Fix:** Assert on the *set* of distinct steps logged (`{0, 1}`) rather than the raw history length, which is what the behavior actually requires (one entry per hyperopt trial).
- **Files modified:** `tests/test_model_train.py`
- **Verification:** `test_train_ep_tune_true_logs_stepped_trial_losses` passes deterministically across repeated runs.
- **Committed in:** `9f3ad87`

## Issues Encountered

- The initial tuning-test corpus (6 games x 12 plays, touchdown-only injection) never produced the Safety/Opp_Safety EP classes, so an 80/20 split could strand a class on only one side, and `XGBClassifier.fit(..., eval_set=[...])` requires every eval_set split to see the same label set as the training split. Resolved by injecting both touchdown and safety events across a larger corpus (20 games x 16 plays), verified empirically to produce all five EP classes in both sides of a `random_state=42` split.
