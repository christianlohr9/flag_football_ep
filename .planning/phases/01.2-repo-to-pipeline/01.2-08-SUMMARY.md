## Decisions Made
- Replaced the notebook's `index.is_in(df.select(...).unique(keep="last").to_dicts())` half_end trick with `index == index.max().over(["game_id","half"])` -- identical selection (index is monotonic with row order) without depending on struct/dict membership semantics.
- Scoped every fill/cum_sum operation in `prepare_ep_data`/`prepare_wp_data` by `game_id` (Task 1's explicit instruction) to eliminate cross-game leakage that the un-scoped notebook chain was vulnerable to in a multi-game training corpus.
- Fixed `receive_2h_ko`: the notebook's `prepare_wp_data` never forward-filled `start_posteam`, so the column was only correct on each half's `play_id==1` row and defaulted to 1 everywhere else. Forward-filled it across the whole game (`.over("game_id")`) to match the interface spec's stated behavior.
- Fixed `make_wp_model_mutations`'s `Winner` column: the notebook compared `posteam` against the literal strings `"home_team"`/`"away_team"` rather than the actual team names via `pl.col(...)`, which meant `label` was structurally always 0. Replaced with `pl.col("home_team")`/`pl.col("away_team")` and scoped the `backward_fill` by `game_id`.
- Kept Task 2's scope deliberately narrow per the plan's explicit "no formula changes" instruction: `add_ep_variables`'s `ep`/`tmp_posteam` backward_fill and the `home_ep_after` shift(-1) remain un-scoped exactly as in the notebook (they are effectively no-ops / edge cases given the model's `.predict()` output populates every row), matching the plan's two-additions-only restriction (guard + PAT constants).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `receive_2h_ko` computed against an un-filled `start_posteam`**
- **Found during:** Task 1 (prepare_wp_data)
- **Issue:** The notebook set `start_posteam` only on `play_id==1` and never forward-filled it in `prepare_wp_data` (unlike `prepare_ep_data`, which does), so `receive_2h_ko` was only correct on that one row per half and defaulted to 1 on every other row -- contradicting the interface spec ("0 when the play's posteam equals the game's first-play posteam").
- **Fix:** Added `.forward_fill().over("game_id")` to `start_posteam` in `prepare_wp_data`, matching `prepare_ep_data`'s pattern and the game_id-scoping the plan already mandated.
- **Files modified:** `src/flag_football_ep/features/mutations.py`
- **Verification:** `test_receive_2h_ko_zero_for_first_play_posteam` in `tests/test_features_mutations.py`
- **Committed in:** `93c5032`

**2. [Rule 1 - Bug] `make_wp_model_mutations`'s `Winner` compared against literal strings, not team names**
- **Found during:** Task 3 (make_wp_model_mutations)
- **Issue:** `Python/helper_add_model_mutations.py` set `Winner` via `.then("home_team")`/`.then("away_team")` -- Python string literals, not `pl.col(...)` expressions -- so `Winner` never held an actual team code and `label = (posteam == Winner)` could never be 1. This directly contradicted the plan's explicit `<behavior>` requirement ("labels 1 when posteam equals Winner").
- **Fix:** Replaced the literals with `pl.col("home_team")`/`pl.col("away_team")`, and scoped `Winner`'s `backward_fill()` with `.over("game_id")` so a multi-game frame's winners don't leak into each other.
- **Files modified:** `src/flag_football_ep/features/mutations.py`
- **Verification:** `test_winner_matches_actual_team_not_literal_string`, `test_label_is_one_when_posteam_equals_winner`, `test_two_game_winner_does_not_leak_across_games`
- **Committed in:** `eaabb0d`
