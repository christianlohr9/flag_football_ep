## Warnings

### WR-01: One malformed IFAF play entry aborts every IFAF game in the run

**File:** `src/flag_football_ep/ingest/ifaf.py:205-207` (`_play_sort_key`), `:236`
(`flatten_unified_plays`), `:469-481` (`ingest_snapshots`)
**Issue:** `ingest_snapshots` only wraps `load_snapshot` (catching `UnparseablePayload`).
The rest of the per-game chain — `flatten_unified_plays`, `map_teams`,
`derive_outcome_columns`, the score cross-check, `conform_to_canonical` — runs unguarded.
`_play_sort_key` returns `(play.get("playNumber", index), index)`; a play with
`"playNumber": null` (key present, value null), a *string* playNumber, or a non-dict play
entry raises `TypeError`/`AttributeError` out of `sorted(...)`. Reproduced against the
installed environment:

```
# unified-plays_a-bad.json: [{"playNumber": 1, ...}, {"playNumber": null, ...}]
# unified-plays_b-good.json: valid
ingest_snapshots(raw, team_mapping)
# -> TypeError: '<' not supported between instances of 'NoneType' and 'int'
#    (ALL games lost, including b-good)
```

In `pipeline._ingest_ifaf` this is caught around the *whole* `ingest_snapshots` call, so
the entire IFAF source (currently 32 real WM-2026 games) is silently reduced to one notice
line. This violates the documented invariant (`docs/pipeline.md` section 4: "One bad
export never removes the rest of its source" / module docstring: an unparseable snapshot
"never aborts the remaining games") — and this feed has already demonstrated surprising
shapes (null downs, missing `pointsScored`), so a live-feed quirk here is plausible, not
theoretical.
**Fix:** Make the sort key null/type-safe and wrap the per-game chain, mirroring
sportapp's containment:

```python
def _play_sort_key(index: int, play: Any) -> tuple:
    number = play.get("playNumber") if isinstance(play, dict) else None
    return (0, number, index) if isinstance(number, int) else (1, 0, index)
```

and in `ingest_snapshots`, wrap everything from `flatten_unified_plays` through
`conform_to_canonical` in a per-game `try/except (TypeError, AttributeError, ValueError,
pl.exceptions.PolarsError)` that records a skip notice and continues (keep
`UnmappedTeamError` propagating, per T-1.2-15). Add a regression test with a
`playNumber: null` play alongside a good game.

### WR-02: `gapless_play_ids` materializes `set(range(1, max_id + 1))` — unbounded memory from one corrupt cell

**File:** `src/flag_football_ep/validation/checks.py:218`
**Issue:** `expected = set(range(1, max_id + 1))` is bounded only by the data. `play_id`
comes from a non-strict cast of the charted `PLAY #` column (Hudl) — a single typo'd cell
like `"99999999"` (or a corrupt sportapp/legacy `play_id`) makes this build a set of ~1e8
Python ints (several GB) and effectively hangs `ffep ingest`. That defeats the plan-20
containment goal from the other direction: the bad cell no longer raises, but it can still
take down the whole run via memory exhaustion instead of degrading to a per-game FAIL.
`missing = sorted(expected - actual)` then also materializes a near-equal-size list.
**Fix:** Never materialize the expected range. Compute gaps arithmetically, e.g.:

```python
n_non_null = len(non_null_ids)
n_missing = (max_id - min_id_floor + 1) - len(actual) if max_id is not None else 0
```

and cap the *examples* (the report already bounds display via `_bounded`) by iterating
`range(1, max_id + 1)` lazily with an early stop after `_MAX_EXAMPLES` finds, plus a
sanity guard (e.g., `max_id > plays-in-game * K` fails immediately with an
"implausible play_id" detail instead of enumerating).

### WR-03: Hudl `play_type` is inconsistent for penalty-modified plays — "Rush, Penalty" is `run` but "Complete, Penalty"/"Sack, Penalty" are `no_play`

**File:** `src/flag_football_ep/ingest/hudl.py:308-316` (`derive_outcome_columns`)
**Issue:** The `play_type` when-chain checks `tok_rush` before `tok_penalty`:

```python
pl.when(pl.col("tok_rush")).then(pl.lit("run"))
.when(pl.col("tok_penalty")).then(pl.lit("no_play"))
...
```

So a `RESULT` of `"Rush, Penalty"` yields `play_type == "run"`, while `"Complete,
Penalty"`, `"Sack, Penalty"` or `"Incomplete, Penalty"` all yield `"no_play"`. Whichever
semantics the contract intends (penalty always nullifies, or penalty never nullifies),
it cannot be both depending on the base token. Note the test table in
`tests/test_ingest_hudl.py:212` conspicuously asserts no `play_type` for
`"Complete, Penalty"` — the ambiguity is currently untested rather than resolved. Any
downstream `play_type == "run"` vs `"no_play"` filter miscounts penalty plays
asymmetrically by base token.
**Fix:** Decide the precedence once (contract question — likely `tok_penalty` first, since
a flagged play is a no-play in this grammar; or exclude penalty from the play_type
derivation entirely and rely on the `penalty` flag) and reorder the chain accordingly,
then add explicit `play_type` assertions for `"Rush, Penalty"` and `"Complete, Penalty"`
to the grammar table test.

### WR-04: Every IFAF row has null `play_type`, contradicting the cross-source `play_type` promise

**File:** `src/flag_football_ep/ingest/ifaf.py:283` (`flatten_unified_plays`),
`:303-374` (`derive_outcome_columns`); `docs/pipeline.md:160-164`
**Issue:** `flatten_unified_plays` hardcodes `"play_type": None` and
`derive_outcome_columns` never sets it, so 100% of IFAF rows carry a null `play_type` —
including plays with fully parsed outcome types like `RUN`, `COMPLETE_PASS`,
`INCOMPLETE_PASS`, `SACK`, `INTERCEPTION`, `XP1`/`XP2`/`TRY`. `docs/pipeline.md` states
"Every source converges on one canonical `play_type` vocabulary … or null for an
*unparsed* play — so a downstream filter can rely on the column without knowing which
source a row came from." These IFAF plays are parsed, not unparsed; a downstream
`play_type == "run"` / `== "pass"` filter silently excludes the entire IFAF corpus — the
exact WR-11 failure mode this vocabulary was created to prevent. The cross-source
vocabulary test (`tests/test_cross_source_vocabulary.py`) only covers hudl and sportapp,
so this gap is invisible to the suite.
**Fix:** Map the obvious outcome types onto the vocabulary in `derive_outcome_columns`
(`RUN` -> `run`; `COMPLETE_PASS`/`INCOMPLETE_PASS`/`SACK`/`INTERCEPTION` -> `pass`;
`XP1`/`XP2`/`TRY` -> `extra_point`; leave genuinely ambiguous types null), or — if
deferral is deliberate — document the all-null IFAF `play_type` explicitly in
`docs/pipeline.md` section 4 and `ingest/ifaf.py`'s module docstring (as was done for
`yards_to_go`), and extend `test_cross_source_vocabulary.py` to cover IFAF.

### WR-05: IFAF `drive_id` starts at 0 when a game's first play lacks `possessionTeamId`

**File:** `src/flag_football_ep/ingest/ifaf.py:239-251` (`flatten_unified_plays`)
**Issue:** `drive_id` starts at 0 and increments when `posteam_raw != prev_posteam_raw`.
`prev_posteam_raw` is initialized to `None`; if the first play's `context` has no
`possessionTeamId` (a case the module explicitly anticipates — it tracks
`_missing_possession`), `None != None` is False and `drive_id` stays **0** for that play
and every following possession-less play. The game then fails `monotonic_drive_ids` with
the misleading detail "first drive_id is 0, expected 1" and is quarantined wholesale for
what is a missing-metadata condition the parser was supposed to degrade gracefully on
(compare: missing `down`/`ballOn` become nulls, not out-of-contract values).
**Fix:** Emit an in-contract value or a null instead of 0 — e.g. seed
`drive_id = 1` before the loop and only increment on a change between two *non-null*
possession ids:

```python
if posteam_raw is not None and prev_posteam_raw is not None and posteam_raw != prev_posteam_raw:
    drive_id += 1
```

(first play: `drive_id` starts at 1 unconditionally). Add a test with a
possession-less first play.

### WR-06: `correct_posteam` repeats the notebook's `&`/`==` precedence trap

**File:** `src/flag_football_ep/ingest/sportapp.py:425-427`
**Issue:**

```python
posteam_helper_max=pl.when(
    ((pl.col("play_id")) == (pl.col("posteam_helper_2"))) & pl.col("def_touchdown") == 1
)
```

Python binds `&` tighter than `==`, so this parses as
`((play_id == helper_2) & def_touchdown) == 1` — not the intended
`(play_id == helper_2) & (def_touchdown == 1)`. Verified against the installed polars
1.5.0: for the current strictly-0/1 `def_touchdown` the two parses happen to coincide
(`True & 1 == 1` etc.), so behavior is correct **today** — but this is byte-for-byte the
operator-precedence bug class that silently corrupted `scoring_play` in the notebook
(documented at length in `canonical.add_scoring_play_team`'s docstring) and it flips
semantics the moment `def_touchdown` becomes nullable or non-binary. The defensive-TD
branch of `correct_posteam` is also not covered by any fixture (TEST001 has no
interception TD), so a regression here would ship unnoticed.
**Fix:** Parenthesize explicitly:

```python
(pl.col("play_id") == pl.col("posteam_helper_2")) & (pl.col("def_touchdown") == 1)
```

and add a sportapp fixture (or unit test on `correct_posteam`) containing a defensive
touchdown drive so the reassignment path is actually exercised.

### IN-03: `run_id` has second resolution — two ingests in the same second collide

**File:** `src/flag_football_ep/pipeline.py:363`
**Issue:** `datetime.now().strftime("%Y%m%d-%H%M%S")` — a second `run_ingest` within the
same wall-clock second silently overwrites the first run's timestamped report and produces
indistinguishable `ingested_at` values in `games.parquet`. The full pipeline currently
completes in under 2 seconds, so back-to-back invocations plausibly collide.
**Fix:** Append a short random/monotonic suffix (e.g. `-%f` microseconds or a 4-hex
token) to `run_id`.

### IN-04: Empty-RESULT notice undercounts rows with null `down`

**File:** `src/flag_football_ep/ingest/hudl.py:299-301`
**Issue:** `empty_non_pat` filters on `pl.col("down") != 0`; a row whose `DN` failed the
non-strict cast has null `down`, and `null != 0` is null, so the row is excluded from the
count — an empty-RESULT play with a bad `DN` cell produces neither notice.
**Fix:** `(pl.col("down") != 0).fill_null(True)` (a null down is certainly not a PAT), or
`pl.col("down").ne_missing(0)`.

### IN-05: Genuine zero-row (forfeit) games vanish from `games.parquet`

**File:** `src/flag_football_ep/pipeline.py:400-401`, `src/flag_football_ep/ingest/ifaf.py:449-451`
**Issue:** The IFAF module documents an empty play array as "a genuine zero-row game …
not a skip", but `run_ingest` drops zero-height frames before `run_checks`, so a forfeit
produces no `GameResult` and no `games.parquet` row — it is only visible if its notice key
happens to land in the report's "Skipped files" section (which, for a clean forfeit with
no notices, it does not). The game silently disappears from all artifacts.
**Fix:** Either emit a games-table row with `n_plays = 0` and a "forfeit/empty" status, or
record an explicit source notice for every zero-row non-skipped game.

### IN-06: `score_plays` preconditions undocumented; re-scoring a scored frame raises

**File:** `src/flag_football_ep/model/score.py:193-251`
**Issue:** (a) `add_ep_variables`/`add_wp_variables` require the input frame to be
chronologically ordered within each game (their `shift(-1)`/`backward_fill()` operate on
row order), but `score_plays`'s docstring never states this — a caller passing a
re-sorted/filtered frame gets silently wrong `epa`/`wpa`. (b) An input frame that already
contains `_score_row_id` or any of the probability columns (e.g. feeding
`plays_scored.parquet` back in from a notebook) fails on `with_row_index` /
`hstack` with an opaque duplicate-column error.
**Fix:** Document the ordering precondition in the docstring (or defensively
`sort(["game_id", "play_id"])` up front), and either drop/reject pre-existing score
columns with a clear `MissingScoreColumns`-style message.

### IN-07: `first_down` uses `>` where the domain rule is `>=` (port-preserved)

**File:** `src/flag_football_ep/ingest/hudl.py:529`, `src/flag_football_ep/ingest/sportapp.py:541-542`
**Issue:** `yards_gained > yards_to_go` marks a first down only when the gain *exceeds*
the distance; gaining exactly the needed yards (the common conversion case) yields
`first_down = 0`. Both sources share the off-by-one. This is ported verbatim from the
notebook (in scope to preserve per the migration policy), but it is a real
domain-correctness issue in a canonical column, distinct from the frozen model
methodology.
**Fix:** Record it in the phase-1.3 "revisit" list (alongside PAT baselines) so the
port-preservation rationale does not fossilize it; change to `>=` when the baseline
freeze is lifted.

### IN-08: `docs/pipeline.md` misstates the missing-half-boundary consequence

**File:** `docs/pipeline.md:93`
**Issue:** The reference table says a missing `half_boundaries.csv` row means "the
affected game's `half` column cannot be derived *past halftime*" — but
`hudl.derive_half` sets `half` to null for **every** row of the game (there is no partial
first-half derivation), and `half_assigned` fails on all rows.
**Fix:** Reword to "the affected game's `half` column is entirely null".

### IN-09: `Total_W_Scaled` min-max scaling has no degenerate-range guard

**File:** `src/flag_football_ep/features/mutations.py:566-568`
**Issue:** `DegenerateWeightRange` guards `Drive_Score_Dist` and `score_differential`
individually, but `Total_W_Scaled = (Total_W - min) / (max - min)` is not guarded — if
`Total_W` happens to be constant while both components vary (offsetting variation), the
division yields NaN silently, which is exactly the failure mode the guard class was
introduced for (RESEARCH Pitfall 4).
**Fix:** Apply the same max==min check to `Total_W` before scaling.
