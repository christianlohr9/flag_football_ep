# Phase 01.4 Plan 13: `ffep report` Batch Orchestration Summary

**One `ffep report` command chains ingest -> score(champion) -> report, writes a dated report set plus an identical `reports/latest/`, and proves in an end-to-end test that it never retrains, never touches the network, and produces self-contained sub-8MB HTML with resolved WP provenance.**

## Performance

- **Duration:** ~2.5h
- **Completed:** 2026-08-21
- **Tasks:** 3/3 completed
- **Files modified:** 3 (2 created, 1 modified)

## Accomplishments

- `src/flag_football_ep/reports/build.py`: `build_reports`/`run_report_pipeline`/`ReportRunResult`/`PRODUCTS`. The module docstring states the non-negotiable design constraint (without ever using the literal substrings the plan's own acceptance greps check for): this module does not reuse the pipeline's existing full-chain orchestrator, because that orchestrator fits two fresh models on every call and scores with their freshly-produced run ids -- both a budget risk and a silent-promotion risk. The timed path here is ingest -> score(champion) -> report; `score_plays` is always called with no explicit run ids so resolution falls through to the promoted `champion` alias only.
- `ffep report` in `cli.py`: `--config`/`--opponent` (repeatable)/`--product` (repeatable, validated against `PRODUCTS` with `typer.BadParameter`)/`--skip-ingest`. Echoes one `report: ` line per written file, the run/latest directories, every notice, and a per-stage duration block ending in a total -- the line REQ-S1-16's ten-minute budget is measured against.
- WP review pages are dispatched from `attach_wp_provenance`'s output (out-of-fold for historical plays, champion frame only for plays the OOF set doesn't cover), never from `scored` directly -- proven by a fixture whose OOF parquet covers a game's plays and an end-to-end assertion that no page falls back to the unknown-provenance sentence.
- A per-product, per-opponent or per-game page-build failure is caught individually and recorded as a German notice naming the product and the exception text; the rest of the batch still completes. `build_reports` returns `(rendered, notices)` rather than a bare dict so this information reaches both the CLI's `notice: ` echo and test assertions (see Deviations).
- An end-to-end test (`TestReportEndToEnd`) builds a synthetic raw Hudl tree with rich charting columns (formation, route, player names -- one deliberately unmapped), trains and promotes real EP/WP models, and drives the whole thing through `ffep report` via `CliRunner`: asserts a dated run folder plus a byte-identical `reports/latest/`, every written file self-contained (DOCTYPE, embedded chart, no `<script`, no external `http(s)` reference, under 8 MB), the unmapped player name and its warning heading present in the own-team report, every `wp-review-*.html` stating a resolved provenance sentence, `--opponent` restricting to just that opponent's page, a second run replacing (not merging into) `latest/`, and zero network access (`socket.socket.connect` monkeypatched to raise).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing critical functionality] `build_reports`'s literal `-> dict[str, str]` interface cannot carry the per-product failure notices the plan's own action text and threat mitigation require**

- **Found during:** Task 1, designing the per-product try/except the plan's action text explicitly specifies ("wrap each page build in a try/except that records a German notice... and continues")
- **Issue:** The plan's `<interfaces>` block types `build_reports` as returning a bare `dict[str, str]`. But the plan's own acceptance criteria ("a builder raising for one product yields a notice naming that product and pages for the remaining products") and T-1.4-59's mitigation disposition ("per-product try/except records a notice and continues") both require that notice text to be observable by the caller -- and Task 2's CLI action text requires `run_report_pipeline`'s `ReportRunResult.notices` to include exactly this information, echoed with `notice: `. A bare dict has no channel for this.
- **Fix:** `build_reports` returns `tuple[dict[str, str], tuple[str, ...]]` (rendered pages, notices) instead of a bare dict. `run_report_pipeline` extends its own accumulated notices list with `build_reports`'s second return value.
- **Files modified:** `src/flag_football_ep/reports/build.py`
- **Verification:** `test_build_reports_product_failure_yields_notice_and_other_products_still_build` asserts the notice text and product name both surface; `test_run_report_pipeline_skip_ingest_records_zero_duration_and_notice` asserts a notice reaches `ReportRunResult.notices`
- **Committed in:** `a6b90a9` (Task 1 commit)

**2. [Rule 1 - Bug] `mlflow.start_run(run_id=...)` rejects a run id whose experiment doesn't match the fluent API's currently active experiment**

- **Found during:** Task 1, writing `_promoted_config` (train both EP and WP, then register+promote both) for `run_report_pipeline`'s own tests
- **Issue:** `train_ep`/`train_wp` each leave MLflow's fluent-API active experiment pointed at whichever one ran last (via `mlflow_store.ensure_experiment`'s `mlflow.set_experiment` call). Registering the *other* model's run afterward (`mlflow.start_run(run_id=ep_run)` while the active experiment is still `wp_model_test`) raises `MlflowException: Cannot start run ... because active experiment ID does not match environment run ID` -- an environment/MLflow-version interaction, not specific to this plan's own code, but one every test in this file that trains+promotes both models hits.
- **Fix:** Call `mlflow_store.ensure_experiment(<the run's own experiment>, config)` immediately before registering each run, resetting the active experiment to match.
- **Files modified:** `tests/test_cli_report.py`
- **Verification:** `_promoted_config`-based tests (7 of them, including the full end-to-end suite) all pass
- **Committed in:** `a6b90a9` (Task 1 commit)
