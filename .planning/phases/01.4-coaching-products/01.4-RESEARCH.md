## User Constraints (from CONTEXT.md)

### Locked Decisions

**Report format & delivery**
- **Output format:** Self-contained HTML — one standalone `.html` file per report with all images embedded; opens in any browser offline. Browser print-to-PDF covers the PDF half of REQ-S1-12; no native PDF dependency.
- **Charts:** Static matplotlib/seaborn images (reuse the headless-Agg convention from `charts/pat_breakeven.py` / `model/evaluate.py`). No plotly/interactivity — primary consumption device is a **tablet**, so layout must be tablet-friendly: large fonts, charts sized to screen width, no horizontally-scrolling tables; pinch-zoom on images is the zoom story.
- **File structure:** One file per opponent; own-team report, decision cheat sheet, and WP game reviews are separate files. No monolithic dossier, no index page requirement.
- **Language:** German prose and labels (football terms like Blitz, Coverage, 4th down stay English as usual).
- **Density:** One-pager-first — each opponent report opens with a compact summary block (top tendencies in plain sentences, key rates) that stands alone in 30 seconds; full tables/charts follow below.
- **Decision charts:** A standalone "game decisions" cheat-sheet page — PAT break-even + 4th-down chart together, printable, camp-ready, usable without the other reports.
- **WP review chart:** Annotated WP line per game — curve with markers on the biggest swings (top-EPA plays, scores, turnovers) with short play captions. Synthetic-time flag must be visible on the chart (C-08 / REQ-S1-02 outcome).
- **Style:** Clean neutral — white background, one accent color, no logos. Details are Claude's discretion within readability-on-tablet-and-print.

**Tendency report content**
- **Data scope:** All sources with graceful degradation — formation/route/coverage-dependent sections use Hudl-charted games only (the fields exist only there); down/distance, play-call, 4th-down and PAT behavior also pull from sportapp + IFAF PBP. Each report section states its game basis (which games, which source).
- **Field zones:** 3 zones + explicit red-zone bucket (~last 10 yards) over `yardline_50` ∈ [0, 50].
- **Small samples:** Show everything, always with n — every rate carries its play count (e.g. "78% Pass (n=9)"); cells under a threshold are visually muted, never hidden.
- **Score state:** Three buckets by margin — trailing / close (within one score, ±6) / leading by more.

**Own-team report & player identity**
- **Player names:** Maintained roster reference CSV under `data/reference/` (same pattern as `team_mapping.csv`) mapping every source spelling/jersey to one canonical player. Unmapped names appear as-is with a prominent warning listing them — the report never breaks on an unmapped name. (This resolves the cross-source player-mapping decision deferred from Phase 1.2.)
- **Timeframe:** Current cycle by default for player tables; formation/play-call/route EPA shown for the current cycle with all-time as a comparison column. (Exact cycle definition — season boundary vs date — is Claude's discretion, documented in the report.)
- **Drive success:** Points per drive as headline plus a drive-outcome breakdown (TD / turnover / downs / half-end).
- **Defense:** Offense views per REQ-S1-13 **plus a basic defense section** — EPA/play allowed by `DEF FRONT`/`COVERAGE` and takeaways. Kept small; it extends REQ-S1-13, it does not redefine it.
- **EPA source:** Own-team EPA uses the persisted out-of-fold predictions from 1.3 for historical plays (locked 1.3 decision); new games are scored with the refit champion model.

**Report CLI & <10-minute flow**
- **Command shape:** One batch command — `ffep report` builds everything by default (all group-opponent pages, own-team report, decision cheat sheet, WP charts), with flags to build a single product or team (e.g. `--opponent FRA`).
- **Timed path (REQ-S1-16):** ingest → score (promoted champion via registry alias) → report. Training/promotion stays a separate deliberate step (`ffep train` + `ffep promote`) outside the 10-minute clock — no silent model changes.
- **Outputs:** Dated run folder (e.g. `reports/2026-08-19/…`) per generation, plus a `reports/latest/` copy always holding the newest set.
- **Group opponents:** A small maintained reference file (`data/reference/` pattern) lists the upcoming tournament's group opponents; edited once per tournament, read by `ffep report`. No API coupling at report time.

## Summary

Phase 1.4 turns Phase 1.3's scored plays and out-of-fold predictions into five families of
self-contained, offline-capable HTML reports (opponent tendency, own-team efficiency,
decision cheat sheet, WP game review) reachable in under 10 minutes from raw exports. This is
a well-trodden pattern — Jinja2 template + base64-embedded matplotlib PNGs — with no exotic
technology risk. The one new runtime dependency, Jinja2, is **already installed** in this
project's virtualenv (pulled in transitively by MLflow's Flask dependency, currently at
3.1.6) but is not yet a declared direct dependency in `pyproject.toml`; it should be added
explicitly rather than relied on transitively.

The larger risk in this phase is not templating — it's **wiring the timed path correctly**.
`pipeline.run_all` (the function behind `ffep run`) always retrains both models
(`train_ep`/`train_wp`) before scoring with the freshly trained (non-champion) run ids. That
directly conflicts with the locked decision "Training/promotion stays a separate deliberate
step... outside the 10-minute clock — no silent model changes." The REQ-S1-16 timed path
(`ingest → score (champion alias) → report`) must NOT reuse `run_all` as-is; it needs its own
lightweight orchestration that skips train entirely and calls `score_plays(plays, config)`
with no explicit run ids (which already resolves the `champion` alias via
`model.registry.resolve_champion`). This is flagged as a Common Pitfall below and must be a
locked design decision going into planning, not something a plan discovers mid-implementation.

**Primary recommendation:** Build a new `reports/` package (aggregation + Jinja2 assembly +
base64 embedding) alongside the existing `charts/` package (pure `Figure`-returning
renderers, matching `charts/pat_breakeven.py`'s established shape); add two new chart
renderers (4th-down conversion, annotated WP line) to `charts/`; wire `ffep report` as an
independent ingest→score(champion)→report chain, distinct from `ffep run`'s
ingest→train→train→score chain.

### Pattern 1: Headless chart → base64 data URI (no temp files)
**What:** Render a matplotlib `Figure` in memory, save to a `BytesIO` buffer as PNG, base64-encode, embed as a `data:` URI — never write an intermediate PNG file to disk.
**When to use:** Every chart embedded in a report. PNG-on-disk is still useful for the standalone `ffep pat-breakeven` CLI command (unchanged), but the *report* pipeline should embed in-memory to avoid a second I/O round-trip and to keep report generation atomic (one `.html` file, no sidecar image folder to keep in sync).
**Example:**
```python
# Source: matplotlib.org (Figure.savefig accepts any file-like object) + stdlib base64 docs
import base64
from io import BytesIO
from matplotlib.figure import Figure

def fig_to_data_uri(fig: Figure, *, dpi: int = 150) -> str:
    """Render `fig` to a base64 PNG data URI. Closes `fig` afterward (Agg backend,
    matches the write-once-then-close discipline in charts/pat_breakeven.py)."""
    buf = BytesIO()
    try:
        fig.savefig(buf, format="png", dpi=dpi, bbox_inches="tight")
        encoded = base64.b64encode(buf.getvalue()).decode("ascii")
    finally:
        import matplotlib.pyplot as plt
        plt.close(fig)
    return f"data:image/png;base64,{encoded}"
```

### Pattern 2: Jinja2 Environment for a standalone (non-web) tool
**What:** A module-level `Environment` with `PackageLoader` + `select_autoescape`, not Flask's implicit app-bound environment.
**When to use:** Every report renderer in `reports/render.py`.
**Example:**
```python
# Source: jinja.palletsprojects.com/en/stable/api/ (Environment, PackageLoader, select_autoescape)
from jinja2 import Environment, PackageLoader, select_autoescape

def build_environment() -> Environment:
    return Environment(
        loader=PackageLoader("flag_football_ep", "templates"),
        autoescape=select_autoescape(["html", "htm", "xml"]),
        trim_blocks=True,
        lstrip_blocks=True,
    )
```
`select_autoescape` matters even though this tool has no untrusted external input today: a
`thrown_by`/`received_by` value that contains `<`/`&` from a hand-charted Hudl export would
otherwise corrupt the rendered HTML rather than displaying literally. Default Jinja2
`autoescape` is `False` — it must be turned on explicitly.

### Pattern 3: Tablet/print-friendly base template CSS
**What:** A single `base.html.j2` with print media rules, so every report inherits the same
tablet-legible, print-safe layout without repeating CSS in four templates.
**Example:**

### Anti-Patterns to Avoid
- **Writing chart PNGs to a temp directory then reading them back for embedding:** unnecessary I/O and a cleanup burden; go straight from `Figure` to `BytesIO` to base64 (Pattern 1).
- **Reusing `pipeline.run_all` unmodified as the REQ-S1-16 timed path:** it retrains both models every call — see Common Pitfalls.
- **Rendering Jinja2 templates with `autoescape=False` (or omitting it):** default is off; must be set explicitly (Pattern 2).
- **Hand-rolling confidence intervals for small-sample tendency cells:** reuse `scipy.stats.binomtest(...).proportion_ci()`, the exact pattern `estimate_pat_baselines` already established for this codebase's small-n problem.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| HTML escaping of charted free-text fields (player names, play descriptions) | Manual `.replace("<", "&lt;")` | Jinja2 `select_autoescape` | Jinja2's escaping is context-correct and already a project dependency (transitively); a hand-rolled replace misses attribute contexts and quoting edge cases |
| Base64 image embedding | A third-party "html report" library (`html-reports`, `reportlib` on PyPI) | stdlib `base64` + `io.BytesIO` (Pattern 1) | The operation is two stdlib calls; pulling in a whole report-generation framework adds dependency surface for zero benefit and would fight the codebase's existing chart-module convention |
| Small-sample confidence intervals | Normal approximation (`p ± 1.96·sqrt(p(1-p)/n)`) | `scipy.stats.binomtest(...).proportion_ci()` (already the codebase's PAT-baseline pattern) | This dataset's per-cell counts are frequently in the tens, sometimes near 0% or 100% — normal approximation is known to break down exactly there; Clopper-Pearson doesn't |
| Cross-source player name matching | Fuzzy string matching (`fuzzywuzzy`/`rapidfuzz`) | A maintained CSV mapping table (locked decision) | The user explicitly locked "maintained roster reference CSV... mapping every source spelling/jersey to one canonical player" — fuzzy matching would silently merge or split players and contradicts the chosen approach |
| PDF generation | WeasyPrint / ReportLab / pdfkit | Browser print-to-PDF (locked decision) | Explicitly ruled out: "Browser print-to-PDF covers the PDF half of REQ-S1-12; no native PDF dependency" |

**Key insight:** every "don't hand-roll" item in this phase already has a project-internal
precedent (the PAT-baseline CI pattern, the `charts/` Figure-returning convention, the
`data/reference/` CSV-mapping convention) — the discipline here is *reuse the codebase's own
prior art*, not reach for a new external library.

## Common Pitfalls

### Pitfall 1: `ffep run` retrains models — it is not the REQ-S1-16 timed path
**What goes wrong:** A plan wires `ffep report` to call (or extend) `pipeline.run_all`,
assuming "the chain" already does ingest→score→(now report). But `run_all` unconditionally
calls `train_ep` and `train_wp` before `score_plays(plays, config, ep_run, wp_run)` — passing
the freshly trained run ids explicitly, **not** resolving the `champion` alias. Timing the
"10-minute" budget against this path measures training time (which can be arbitrarily long,
especially with `--tune`), and worse, silently promotes a never-reviewed model into the
scoring path every time a report is generated — exactly the "no silent model changes"
outcome CONTEXT.md locks against.
**Why it happens:** `run_all` was built in Phase 1.2/1.3 for a different purpose (exercising
the full pipeline in one command, including retraining) before REQ-S1-16's specific
"ingest → score (champion) → report, training is separate" contract existed.
**How to avoid:** Give `ffep report`'s timed path its own orchestration
(`reports/build.py::run_ingest_score_report` or similar) that calls `run_ingest` then
`score_plays(plays, config)` with **no** `ep_run`/`wp_run` arguments (so `resolve_run` falls
through to `registry.resolve_champion`), then the report builders — never `run_all`. Time
this new path's stages with the same `time.perf_counter()` convention `run_all` already uses.
**Warning signs:** A plan task that says "extend `ffep run`" or "add a `--report` flag to
`ffep run`" without also removing/skipping the two `train_*` calls on that path.

### Pitfall 2: `roster.csv` exists but is not the locked player-mapping table
**What goes wrong:** `data/reference/roster.csv` (645 rows: `team_id, team_name, player_id,
player_name, player_jersey, position, club`) already exists on disk and looks like it could
be "the" roster reference CONTEXT.md asks for. It is not loaded by any code today (no
`load_roster*` function in `reference.py`, no `roster` key in `ReferenceFiles`/`ffep.toml`),
and — critically — it has **no `source` column**, so it cannot yet express "Hudl spells this
player X, sportapp spells them Y, canonical is Z" (the actual locked requirement: "mapping
every source spelling/jersey to one canonical player").
**Why it happens:** `roster.csv` looks like it was populated from a single source (likely an
IFAF/competition roster dump) as raw reference data, not built as the cross-source mapping
table this phase needs.
**How to avoid:** Plan either (a) a new `data/reference/player_mapping.csv` with a
`team_mapping.csv`-shaped schema (`source, source_name_or_jersey, canonical_player_id`) that
references `roster.csv`'s `player_id` as the canonical key, or (b) extend `roster.csv` itself
with a `source`/`source_name` column set. Either way, this is new schema design work, not a
"just wire up the existing file" task — flag it explicitly in the plan.
**Warning signs:** A plan step that says "load `roster.csv`" as if the mapping problem is
already solved.

### Pitfall 3: Config dataclasses require touching four places, not one
**What goes wrong:** `Config`/`Paths`/`ReferenceFiles` in `config.py` are frozen dataclasses
built from fixed key tuples (`_PATH_KEYS`, `_REFERENCE_KEYS`) — adding a new path (`reports`)
or reference file (`roster`, `group_opponents`) means updating: (1) the dataclass field, (2)
the key tuple, (3) `ffep.toml`, and (4) the test helpers `test_pipeline_ingest.py::_make_config`
and `_write_toml_config`, which construct `Paths`/`ReferenceFiles` explicitly by keyword and
will raise a `TypeError` (missing/unexpected keyword) the moment the dataclass shape changes,
breaking every existing test file that imports them (e.g. `test_charts_pat_breakeven.py`
already does `import test_pipeline_ingest as tpi`).
**Why it happens:** The config module intentionally has no dict-based fallback — every field
is required, by design, to fail loudly on a missing key rather than silently defaulting.
**How to avoid:** Any plan task that adds a new config field must include: `config.py`
dataclass field, `ffep.toml` entry, and both `tests/test_pipeline_ingest.py` helper updates,
in the same task — never split across tasks in a way that leaves the test helpers stale.
**Warning signs:** Any new `Config`/`Paths`/`ReferenceFiles` field added without a
corresponding edit inside `test_pipeline_ingest.py`.

### Pitfall 4: `drive_success` (canonical column) ≠ the drive-outcome breakdown this phase needs
**What goes wrong:** `canonical.py` already declares a `drive_success` Int32 column, and
`ingest/legacy.py` maps a raw "Drive Success" Hudl column onto it — but it's populated only
for the `legacy` source and its semantics (a single success/fail flag) don't match the
locked requirement of a four-way categorical breakdown ("TD / turnover / downs / half-end").
A plan that assumes `drive_success` already carries this breakdown will produce nulls for
every non-legacy game (the majority of the corpus).
**Why it happens:** `drive_success` predates this phase and was ported from a different,
narrower notebook concept.
**How to avoid:** Derive the TD/turnover/downs/half-end breakdown fresh, per drive, from the
existing play-level flags (`touchdown`, `interception`, `down`==4 non-conversion, `half`
boundary) grouped by `drive_id` within `game_id` — do not reuse `drive_success` as an input.
**Warning signs:** A plan task that says "aggregate `drive_success`" as the own-team drive
breakdown's data source.

### Pitfall 5: Base64 image bloat inflates HTML file size and tablet load time
**What goes wrong:** A single embedded PNG at reasonable chart size/dpi is typically 40–150
KB before base64 (which adds ~33% overhead). An opponent tendency report with 8–12 charts can
reach several MB. On a tablet browser opening a `file://` URL from local storage this is
usually fine, but it compounds badly with `dpi` values chosen for print crispness (300 dpi)
rather than screen display.
**Why it happens:** matplotlib's default figure export dpi (100) is fine for screen but
"print-ready" instincts push toward 300 dpi, and every doubling of dpi roughly quadruples PNG
size.
**How to avoid:** Use dpi ≈150 for embedded charts (readable at both tablet-screen and
browser-print resolution — verified against MDN/print-CSS guidance that most browsers rasterize
`<img>` print output from the DOM-resident bitmap, so print sharpness is bounded by whatever
dpi was embedded, not by print settings) and `bbox_inches="tight"` to avoid wasted margin
pixels. Measure total `.html` file size in the wave-boundary verification for REQ-S1-16 (part
of the <10-minute, tablet-usable acceptance bar) — flag if any single report exceeds a few MB.
**Warning signs:** No dpi/size check in the plan's verification steps for the report-writing
tasks.

### Pitfall 6: `plt.close(fig)` discipline must survive four new render functions
**What goes wrong:** `charts/pat_breakeven.py`'s `write_pat_breakeven` closes its figure in a
`finally` block after saving. A batch report run generates dozens of figures per invocation
(one tendency report × N opponents × several charts each); any renderer that forgets to close
its figure leaks matplotlib `Figure`/`Axes` objects for the whole `ffep report` process
lifetime, which — with the `Agg` backend still tracking every unclosed figure in
`pyplot`'s global figure registry — can slow down or memory-balloon a large batch run.
**Why it happens:** Easy to omit when copy-adapting the base64-embed pattern (Pattern 1) if
the `try/finally` around `plt.close(fig)` isn't kept.
**How to avoid:** Centralize `fig_to_data_uri` (Pattern 1) as the *only* path from a rendered
`Figure` to embedded HTML, so `plt.close` discipline lives in one place, not four.
**Warning signs:** A report builder calling `fig.savefig(...)` directly instead of the shared
`fig_to_data_uri` helper.

## Code Examples

### Batch-writing a dated run folder + `latest/` copy
```python
# Source: codebase convention (pipeline._atomic_write_parquet's "never leave prior output
# half-written" discipline), adapted for a directory of HTML files per CONTEXT.md's explicit
# "copy" wording (not a symlink)
import shutil
from datetime import date
from pathlib import Path

def write_report_run(rendered: dict[str, str], reports_root: Path) -> tuple[Path, Path]:
    """Write each `{filename: html}` pair under a dated run folder, then copy the whole
    folder onto `reports/latest/` (removing any prior `latest/` first)."""
    run_dir = reports_root / date.today().isoformat()
    run_dir.mkdir(parents=True, exist_ok=True)
    for filename, html in rendered.items():
        (run_dir / filename).write_text(html, encoding="utf-8")

    latest_dir = reports_root / "latest"
    if latest_dir.exists():
        shutil.rmtree(latest_dir)
    shutil.copytree(run_dir, latest_dir)
    return run_dir, latest_dir
```

### Timed ingest → score(champion) → report chain (REQ-S1-16), distinct from `ffep run`
```python
# Source: mirrors pipeline.run_all's time.perf_counter() convention (src/flag_football_ep/
# pipeline.py:502-536), but omits train_ep/train_wp entirely (Pitfall 1)
import time
import polars as pl
from flag_football_ep.pipeline import run_ingest
from flag_football_ep.model.score import score_plays

def run_report_pipeline(config) -> dict[str, float]:
    durations: dict[str, float] = {}

    start = time.perf_counter()
    ingest_result = run_ingest(config, ["hudl", "legacy", "sportapp", "ifaf"])
    durations["ingest"] = time.perf_counter() - start

    plays = pl.read_parquet(ingest_result.plays_path)

    start = time.perf_counter()
    scored = score_plays(plays, config)  # no ep_run/wp_run -> champion alias only
    durations["score"] = time.perf_counter() - start

    start = time.perf_counter()
    # dispatch to reports/build.py's per-product builders here
    durations["report"] = time.perf_counter() - start

    return durations
```
