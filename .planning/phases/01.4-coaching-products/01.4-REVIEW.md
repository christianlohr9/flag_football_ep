# Phase 01.4: Code Review Report

**Reviewed:** 2026-08-22T08:38:17Z

## Summary

Reviewed the Phase 1.4 coaching-product stack: aggregation vocabulary (`reports/aggregate.py`), the four page builders (`opponent.py`, `own_team.py`, `decisions.py`, `reports/wp_review.py`), the chart renderers (`charts/fourth_down.py`, `charts/tendency.py`, `charts/wp_review.py`), the render/write layer (`reports/render.py`), batch orchestration (`reports/build.py`), the `ffep report` CLI command, the five Jinja templates, and the supporting `config.py` / `features/mutations.py` / `reference.py` changes. The listed test file `tests/test_reports_build_smoke_does_not_exist.py` does not exist and was skipped; `tests/test_cli_report.py` and `tests/test_reports_aggregate.py` were read as usage context.

The overall structure is disciplined (single write point, autoescape on, allow-listed filenames, per-product try/except), but two Critical defects break contracts the modules themselves document: the wp-review product's provenance attach runs outside the per-product isolation and can abort the entire batch, and `attach_epa`'s `scored=None` path leaks backfill-fabricated EPA values onto rows that are supposed to carry null EPA — silently wrong numbers in a coaching report. Several secondary defects cluster around partial OOF coverage (which is provably possible: the training pipeline `drop_nulls()`s the model frame, so `oof_predictions_*.parquet` can cover only part of a game) and inconsistent validation layers around filenames.

Note on test coverage: the only isolation test in `tests/test_cli_report.py` monkeypatches `build_decisions_page`; the `attach_wp_provenance` failure path (CR-01) and the `scored=None` path of `attach_epa` (CR-02) are untested.

## Critical Issues

### CR-01: wp-review provenance attach runs outside per-product isolation and can abort the whole batch

**File:** `src/flag_football_ep/reports/build.py:160-164`
**Issue:** `build_reports`'s docstring (and T-1.4-59) locks per-product failure isolation: "a per-product ... page-build failure is recorded as a German notice ... and does not abort the rest of the batch". But for the `wp-review` product, `attach_wp_provenance(...)` and `sorted(wp_frame["game_id"].unique().to_list())` execute *outside* any try/except — only the per-game page build is guarded. `attach_wp_provenance` has several realistic failure modes: a corrupt or schema-drifted `oof_predictions_wp.parquet` (`_resolve_oof_wp` does `pl.read_parquet(...).select(*keys, "wp")` — a missing column raises `ColumnNotFoundError`), or an input frame missing a column `prepare_wp_data`/`add_wp_variables` requires. Any of these propagates out of `build_reports`, through `run_report_pipeline`, before `write_report_run` is ever called — so a single bad WP OOF file destroys the *entire* report run, including the opponent/own-team/decisions pages that were already rendered successfully. This is exactly the "run that produces none" outcome the docstring says the design exists to prevent, at the worst possible moment (evening before a tournament, after minutes of ingest+score work).
**Fix:**
```python
if "wp-review" in resolved_products:
    try:
        wp_frame = attach_wp_provenance(
            plays, processed_dir=config.paths.processed, scored=scored
        )
        game_ids = sorted(wp_frame["game_id"].unique().to_list())
    except Exception as exc:  # noqa: BLE001 - per-product isolation
        notices.append(f"WP-Review-Vorbereitung fehlgeschlagen: {exc}")
        game_ids = []
        wp_frame = None
    for game_id in game_ids:
        try:
            ...
```

### CR-02: `attach_epa` with `scored=None` leaves fabricated non-null EPA on rows with no EPA source

**File:** `src/flag_football_ep/reports/own_team.py:157-186` (specifically the `else` branch at line 179)
**Issue:** The docstring guarantees: "A row matched by neither keeps null EPA columns and a null `epa_source`; it is excluded from every EPA rollup downstream." That guarantee is broken. When `ep_path` exists, `oof_ep_values` (line 125) carries derived `ep`/`epa` for **every** row — including OOF-unmatched rows, whose `ep` was `backward_fill()`ed inside `add_ep_variables` from a later matched row's probabilities, producing a non-null, meaningless `epa`. The champion branch correctly discards these via `remainder.drop(schema_cols)` (line 169), but the `else` branch (`scored is None`) only sets `epa_source` to null and **keeps** the fabricated `ep`/`epa`/`wp`/`home_wp`/`wpa` values. Downstream, every rollup filters on `epa.is_not_null()` (`efficiency_by_call` line 256, `defense_section` line 587), so these source-less rows are *included* in the EPA tables the coaching staff reads — while the page's own provenance sentence simultaneously counts them as `n_epa_none` ("ohne EPA-Quelle"). The report is internally inconsistent and numerically wrong. `scored=None` is the *default* of the public `build_own_team_data(plays, *, config, scored=None)` signature, so any caller that omits `scored` hits this silently. (Same leak applies to the WP columns: `add_wp_variables` backward-fills `wp` over unmatched rows. Contrast `attach_wp_provenance`, which handles its `scored is None` branch correctly with explicit null literals at `reports/wp_review.py:353-355`.)
**Fix:**
```python
else:
    remainder = remainder.with_columns(
        [pl.lit(None, dtype=pl.Float64).alias(c) for c in schema_cols]
        + [pl.lit(None, dtype=pl.Utf8).alias("epa_source")]
    )
```

## Warnings

### WR-01: `_resolve_oof_wp` derives WP variables on the OOF-matched subset, not the full game context

**File:** `src/flag_football_ep/reports/wp_review.py:295-300`
**Issue:** `_resolve_oof_wp` inner-joins the OOF file onto `working` and then runs `add_wp_variables(prepare_wp_data(context))` on **only the matched rows**. Partial per-game OOF coverage is not hypothetical: `model/train.py:229` builds the model frame with `.drop_nulls()`, so any play with a null feature is absent from `oof_predictions_wp.parquet` while present in `plays.parquet`. On such a game the derivation is wrong three ways: (a) the synthetic clock (`1200 / max(play_id_half)`) is recomputed over the truncated subset, (b) `_mark_half_end` marks the subset's last second-half row as `game_end`, so `add_wp_variables` pins `home_wp` to the final result (1/0/0.5) at a play that is not actually the game's last play, and (c) `wpa = shift(-1)` spans the skipped plays, attributing multi-play swings to one play. `attach_epa` (`own_team.py:117-124`) does this correctly — prepare on the *full* frame, left-join the probabilities, then derive — and its docstring explicitly warns that deriving on a filtered subset "would silently corrupt every EPA value by skipping over the ... intervening snaps". The WP twin violates the same rule its EP twin documents.
**Fix:** Mirror `attach_epa`: `prepare_wp_data` on the full `working` frame, left-join the OOF `wp` column on `(game_id, play_id)`, run `add_wp_variables` on that full frame, then select the WP value columns only for rows where the joined `wp` was non-null (the match flag), instead of inner-joining first.

### WR-02: `render_wp_review` crashes on an annotated event play with null `home_wp`

**File:** `src/flag_football_ep/charts/wp_review.py:168-186`
**Issue:** `select_wp_annotations` unions every scoring/turnover row into the candidate set regardless of WP coverage — `_annotation_label` (line 52) explicitly handles `row["wpa"] is None`, so null-WP event rows are an anticipated input. But the chart then calls `ax.annotate(..., xy=(row["play_id"], row["home_wp"]))` with `home_wp=None`, which raises `TypeError` inside matplotlib. Concretely: a game where a touchdown play has `wp_source=None` (not in OOF, not champion-covered — e.g. the play was dropped from the model frame, see WR-01) but at least two other plays carry `home_wp` passes the `non_null_wp.height < 2` guard and then crashes mid-render. The per-game try/except in `build.py` turns that into a lost review page for exactly the game with a scoring play worth reviewing.
**Fix:** Skip (or plot at the nearest known WP) annotation rows whose `home_wp` is null:
```python
for i, row in enumerate(annotations.iter_rows(named=True)):
    if row["home_wp"] is None:
        continue
    ...
```
and filter the marker `ax.plot` input the same way.

### WR-03: slug allow-lists permit interior `..`, which `write_report_run` then rejects — whole run aborts after all rendering

**File:** `src/flag_football_ep/reports/opponent.py:550-582`, `src/flag_football_ep/reports/wp_review.py:47-78`, `src/flag_football_ep/reports/render.py:114-115`
**Issue:** `team_slug`/`game_slug` allow `.` in the output (`[A-Za-z0-9._-]`) and only strip *leading* dots, so an interior `..` survives sanitisation. Hudl `game_id`s are export filename stems verbatim (`canonical.make_game_id`, `canonical.py:156-157`) — a file named `GER vs. AUT ..final.csv` yields the slug `GER-vs.-AUT-..final`. `write_report_run` then rejects any filename containing `..` with `ValueError` — raised *after* every page in the batch has been rendered and *before* any file is written, so one oddly-named export destroys the entire run's output. The two validation layers disagree: interior `..` in a plain filename is not a traversal risk (only a full `..` path segment is), yet the write layer treats it as one, while the slug layer that is supposed to be the belt-and-braces guarantee lets it through. Either way the batch dies on legal input.
**Fix:** Collapse dot-runs in the slug functions the same way dash-runs are collapsed (e.g. `re.sub(r"\.{2,}", ".", ...)`) so a slug can never contain `..`, keeping the write-layer check as the unreachable backstop.

### WR-04: `player_efficiency` raises `ColumnNotFoundError` on frames with a partial player-column set

**File:** `src/flag_football_ep/reports/own_team.py:358-373, 402`
**Issue:** The guard at line 358 — `not any(c in canon.columns for c in _PLAYER_SOURCE_COLUMNS)` — explicitly anticipates frames carrying only a subset of `("qb", "thrown_by", "received_by", "target")` (and `_canonicalise_players` filters to columns actually present, line 318). But the body then unconditionally references `pl.col("thrown_by")`, `pl.col("qb")` (line 370) and `pl.col("received_by")` (line 402). A frame with, say, only `received_by` (or only `qb`) passes the `any()` guard and then raises `ColumnNotFoundError` inside `with_columns`/`filter`, which surfaces as the whole own-team product failing (`build.py` notice) instead of the graceful per-column degradation the guard implies. Either the guard should require all three used columns (making the `any()` semantics honest), or missing columns should be materialised as nulls.
**Fix:**
```python
for col in ("thrown_by", "qb", "received_by"):
    if col not in canon.columns:
        canon = canon.with_columns(pl.lit(None, dtype=pl.Utf8).alias(col))
```

### WR-05: defense takeaway counts are computed and broadcast but never rendered anywhere

**File:** `src/flag_football_ep/reports/own_team.py:589-612` vs `936-962`
**Issue:** `defense_section`'s docstring promises "EPA/play allowed by `def_front` and `coverage`, **plus takeaway counts**", and the function computes `interceptions_n`/`def_touchdowns_n` and broadcasts them onto every table row. But `_defense_section_context` builds cells only from `dimension`/`wert`/`epa_play_allowed` (headers: "Dimension", "Wert", "EPA/Play erlaubt"), and no template context field carries the takeaway counts — they never appear on the page. The data is dead weight in the table schema and the documented section content is silently missing from the deliverable. Additionally, when no charted rows exist the counts are lost entirely (empty table), even though they are computed from the full `defteam == team` frame and could still be shown.
**Fix:** Surface the counts in `_defense_section_context` — e.g. a caption line `chart_caption=f"Takeaways: {interceptions_n} Interceptions, {def_touchdowns_n} Defensive Touchdowns"` read from the first table row, or add them to `ReportSection`-level context so they render even when the charted table is empty.

### WR-06: `playcall_by_score_state` silently drops null-`down` rows, breaking its own reconciliation claim

**File:** `src/flag_football_ep/reports/opponent.py:181-184`
**Issue:** The PAT exclusion `df.filter(pl.col("down") != 0)` also drops every row with a **null** `down` (`null != 0` evaluates to null, which `filter` removes). Null `down` is an expected corpus shape — `aggregate.share_table`'s own comment (line 350-351) says "real corpora carry null group keys (e.g. `down` on un-charted rows)" and adds `join_nulls=True` specifically to keep them. The section docstring claims a null `score_state` becomes an explicit `"unbekannt"` group "so the section's play counts reconcile with the section's own basis" — but the basis (`section_basis(df)`, line 179) is computed on the full frame including null-down rows, while the table excludes them, so the counts do not reconcile and the rows vanish without an "unbekannt" bucket, contrary to the module-wide shown-never-hidden rule.
**Fix:** `df.filter(pl.col("down").is_null() | (pl.col("down") != 0))` and let the null `down` flow into the grouping (rendered as "unbekannt" via the existing null handling), or exclude null-down rows from the basis too and say so.

## Info

### IN-01: `.env` is resolved relative to CWD while everything else is config-relative

**File:** `src/flag_football_ep/config.py:159, 208`
**Issue:** `load_config` documents that behaviour "is the same regardless of where `ffep` is invoked from", and resolves all paths against the config file's directory — but `load_dotenv()` is called with its default `Path(".env")`, i.e. the process CWD. Running `ffep --config /path/to/ffep.toml` from another directory silently skips the project's `.env`, producing confusing "environment variable is not set" failures.
**Fix:** Call `load_dotenv(path.resolve().parent / ".env")` inside `load_config`.

### IN-02: slug collisions silently overwrite pages in the rendered dict

**File:** `src/flag_football_ep/reports/build.py:139-140, 167`
**Issue:** Two distinct team codes (or game ids) that sanitise to the same slug (e.g. `A/B` and `A-B` both become `A-B`) produce the same `rendered` key; the second silently replaces the first and one report vanishes without a notice.
**Fix:** Detect a pre-existing key before assignment and append a notice naming both inputs.

### IN-03: dead filter in `formation_tendencies`

**File:** `src/flag_football_ep/reports/opponent.py:74`
**Issue:** `table.filter(pl.col("group_n") > 0)` is a no-op: `share_table` builds `group_n` as `pl.len()` per group, which is always >= 1. Dead code that suggests a condition that cannot occur.
**Fix:** Drop the filter, keep the sort.

### IN-04: `plays_scored.parquet` written non-atomically in the report pipeline

**File:** `src/flag_football_ep/reports/build.py:219`
**Issue:** `scored.write_parquet(...)` writes in place, while the repo convention for this exact artifact class is tmp-then-`Path.replace` (`pipeline._atomic_write_parquet`, `model/evaluate.py::write_oof_predictions`). A crash mid-write leaves a corrupt `plays_scored.parquet` for the next consumer.
**Fix:** Reuse the atomic-write helper.

### IN-05: `latest/` can be left half-written on a `copytree` failure, despite the docstring's claim

**File:** `src/flag_football_ep/reports/render.py:124-127`
**Issue:** The docstring says a half-written run "can therefore never be presented as `latest/`", but the `rmtree(latest_dir)` + `copytree` sequence is not atomic: a failure during `copytree` (disk full, permission) leaves `latest/` partially populated — or absent entirely between the two calls.
**Fix:** Copy to `reports_root/"latest.tmp"`, then `rmtree` the old `latest` and `Path.rename` the tmp into place.

### IN-06: WP review page renders literal `None` for null scores/teams

**File:** `src/flag_football_ep/reports/wp_review.py:163-199`, `src/flag_football_ep/templates/wp_review.html.j2:7, 13`
**Issue:** `_header_summary` guards only on `home_wp` coverage; `home_team`/`home_score`/`away_score` taken from the last row may be null, and Jinja renders them as the string `None` ("Endstand: None None : None None"). Same for `row.posteam` in the swing table and the `Win Probability None` y-label in `charts/wp_review.py:190` when `home_team` is null.
**Fix:** Substitute a placeholder (e.g. `"–"`/`"unbekannt"`) for null values before they reach the template, consistent with `_format_pct`.

### IN-07: decisions page claims "no PAT data" when only one PAT type has zero attempts

**File:** `src/flag_football_ep/reports/decisions.py:60-64`, `src/flag_football_ep/features/mutations.py:154-163`
**Issue:** `estimate_pat_baselines` raises `InsufficientPatAttempts` when *either* type has zero attempts. `build_decisions_page` catches this and renders the blanket German notice "Für PAT-Versuche liegen ... keine Daten vor" — misleading when, say, 40 one-point attempts exist and only the two-point count is zero. The available half is discarded.
**Fix:** Distinguish the two cases (the exception message already names the type), or render the populated type with a per-type notice.

### IN-08: all-null-`wpa` branch of `select_wp_annotations` drops scoring/turnover plays the footnote promises

**File:** `src/flag_football_ep/charts/wp_review.py:81-84`, `src/flag_football_ep/templates/wp_review.html.j2:68-69`
**Issue:** When every `wpa` is null, `select_wp_annotations` returns `head(0)`, discarding scoring/turnover event rows entirely — while the page footnote states the selection is "die betragsmäßig größten WP-Swings **plus alle Score- und Turnover-Plays**". Documented in the docstring, but the rendered promise and the behaviour disagree in this edge.
**Fix:** In that branch, return the event rows (with null-wpa labels, which `_annotation_label` already supports) instead of an empty frame — subject to the WR-02 fix for null `home_wp`.

### IN-09: `fetch-sportapp --games-file` reads the file without an existence check

**File:** `src/flag_football_ep/cli.py:88-92`
**Issue:** `games_file.read_text(...)` on a nonexistent path surfaces a raw `FileNotFoundError` traceback instead of a `typer.BadParameter`. (Pre-existing command, noted since `cli.py` is in scope.)
