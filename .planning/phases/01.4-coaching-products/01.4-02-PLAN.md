<objective>
Build the shared rendering machinery every Phase 1.4 report product sits on: the Jinja2
environment, the in-memory chart-to-data-URI embed helper, the tablet-and-print base template,
and the dated-run-folder writer.

Purpose: four report families (opponent, own-team, decisions, WP review) share one layout
shell, one escaping policy and one figure-closing discipline. Centralising all four here is
what stops a per-product builder from leaking matplotlib figures (RESEARCH Pitfall 6) or
rendering unescaped charted free text (Security Domain row 1).
Output: an importable `flag_football_ep.reports` package with `render.py`, a `base.html.j2`
template, and jinja2 as an explicit dependency.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| charted export free text → rendered HTML → HC's browser | player names, play descriptions and team labels come from hand-charted Hudl/PBP exports and are interpolated into a document the HC opens in a browser |
| caller-supplied filename key → filesystem path under `reports/` | a team code or game id derived from data becomes part of an output filename |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-1.4-05 | Tampering | `reports/render.py` Jinja2 environment | mitigate | `select_autoescape(["html","htm","xml"])` set explicitly (Jinja2 defaults autoescape OFF); tested with a `<script>` payload asserting `&lt;script&gt;` in output |
| T-1.4-06 | Tampering | `write_report_run` filename keys | mitigate | reject keys containing a path separator, `..` or a null byte with `ValueError` before any write |
| T-1.4-07 | Denial of service | batch run leaking matplotlib figures across dozens of charts | mitigate | `fig_to_data_uri` is the single Figure→HTML path and closes in `finally`; tested including the savefig-raises case |
| T-1.4-SC | Tampering | `uv add jinja2` | mitigate | RESEARCH Package Legitimacy Audit records jinja2 as `[OK]`/Approved (Pallets, ~18 yrs, top-50 PyPI, github.com/pallets/jinja); no `[ASSUMED]`/`[SUS]` packages in this phase, so no blocking legitimacy checkpoint is required |
